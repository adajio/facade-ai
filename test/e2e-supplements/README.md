# Досылка в двух сеансах

Проверка запускается с отдельной чистой БД и каталогом объектов. Использует настоящий HTTP, PostgreSQL, S3 и Chromium. Два независимых контекста Chromium входят через штатный маршрут сеансов и выполняют запросы со страницы того же origin. Входы синтетические. Worker остаётся выключен. Для оценки подаются управляемые опоры, полученные штатным PDF reader с настоящих байтов. Внешних отправок писем и платных вызовов нет.

Из корня репозитория после сборки `npm run build:server` выполните:

```bash
db_env="$(infra/test-stand/stand new-db step7)"
source "$db_env"
export HOST=127.0.0.1 PORT=18087
export FACADE_E2E_BASE_URL="http://$HOST:$PORT"
export FACADE_E2E_OUTPUT="$TMPDIR/step7-evidence"
mkdir -p "$FACADE_E2E_OUTPUT"
npm run migrate
node dist/apps/api/src/main.js > "$FACADE_E2E_OUTPUT/api.log" 2>&1 &
api_pid=$!
trap 'kill "$api_pid" 2>/dev/null || true' EXIT
for attempt in {1..100}; do
  curl --fail --silent -o /dev/null "$FACADE_E2E_BASE_URL/readyz" && break
  kill -0 "$api_pid" || exit 1
  sleep 0.2
done
curl --fail --silent -o /dev/null "$FACADE_E2E_BASE_URL/readyz"
node --test test/e2e-supplements/stand.test.mjs
```

Если API запущен владельцем стенда, в `FACADE_E2E_BASE_URL` укажите выданный адрес. `DATABASE_URL`, `FACADE_DATA_DIR` и настройки объектов должны относиться к той же отдельной тестовой БД и хранилищу. Для установленного Chrome задайте `FACADE_E2E_BROWSER_CHANNEL=chrome`. Для HTTPS с локальным сертификатом передайте `FACADE_E2E_STAND_TLS_CERT` с путём к сертификату стенда. Браузер доверяет закреплённому открытому ключу. Для повторов в одной выделенной БД можно задать `FACADE_E2E_FIXTURE_ACCOUNT` с путём внутри приватного каталога `$TMPDIR`. Сценарий создаёт файл с синтетической учётной записью с правами `0600` и выделяет новый проект на каждый повтор.

Проверка фиксирует допуск при обоих порядках ожидания на одном advisory lock, блокировку старых подтверждения и URL, сужение на одну область, две одновременные причины, отмену пустой декларации, незапущенный импорт по ссылке, запись ранее совершённой тестовой отправки, точную связь с пунктом и сохранение его старых адресов после смены каталога. Отдельно проверяет публикацию после фактической фиксации, снимок при параллельном commit, откат, повтор, истечение курсора и выход из одного сеанса. Сохраняются экспорты TXT/DOCX до и после досылки и снимки с составом и идентификаторами. Для браузерного интерфейса компонентный сценарий и состояние редактирования ведёт шаг 13.

## Стыки для общего прогона

- После появления окна браузера и готовой сборки нужны API, отдельные БД и бакет одного прогона, выключенный worker и доступ к учётным записям загрузки стенда через его штатное окружение. `readyz` проверяется перед запуском сценария.
- Шаг 13. Для пользовательского сценария нужно вызвать `PATCH .../supplements/holds/:holdId` и `POST .../resolve` из интерфейса классификации и проверки влияния. Список событий отдаётся страницами. Если `hasMore=true`, дочитывайте страницу после `cursor` перед переходом на `head.cursor`, чтобы сохранить события, полученные за время разрыва. [HTTP](../../src/modules/supplements/README.md)
- Шаг 12. Если подтверждённое влияние поступления вычисляет worker, завершение той же причины проходит через `resolveSupplementImpact`. При вызове передаются версия, поколение и подтверждённые опоры. Пока потребитель использует самостоятельный `applyAssessmentUpdate`, открытая причина остаётся действующей до команды разрешения.
