# Автоматическая приёмка Facade AI 1.1

Шаг 15 плана `42ed7fc`. [Матрица и текущий допуск](../../docs/implementation/acceptance.md)

## Проверки без стенда

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s test/acceptance -v
```

Тесты оценивают искусственные записи. Для отрицательного контроля удаляют критическую строку из копии итогового результата. В одном случае остаются исходные TXT и DOCX, в другом письмо ожидаемо отсутствует. В обеих проверках AC03 теряет обязательное место, а вердикт AC06 сохраняется.

## Загрузка на стенд

1. Зафиксировать образ и манифест исходников стенда, список миграций, версии reader и каталог. Использовать отдельную тестовую БД стенда и тестовый проект, доступный тестовой учётной записи. Проверить, что сборка и тома приложения не включают каталог закрытой разметки.
2. До загрузки выбрать режим. Для управляемого транспорта требуется подтверждённая конфигурация без внешнего модельного выхода. Для холодного и тёплого испытаний требуется допуск из матрицы. Для replay требуется отключённая сеть провайдера. Сценарий загрузки сам режим шлюза не меняет.
3. Указать учётные данные тестового пользователя в окружении `FACADE_ACCEPTANCE_LOGIN` и `FACADE_ACCEPTANCE_PASSWORD`. Использовать отдельную папку результата на каждый прогон. Указывать только каталог исходников одного пакета и замороженный манифест путей и хэшей. До первой команды сверяются все файлы, включая отсутствие лишних. Технический корпус хранится вне сборочного контекста.
4. Создать проект и закрепить каталог можно штатными командами через этот же скрипт: вместо `--project` и `--inputs` задайте `--setup` с отдельным публичным профилем `{catalog, project, scopes}`. Он описывает область, этап и предметные требования без ожидаемых значений и адресов. Загрузка выполняется отдельным запуском с выданным ID.
5. Через API принимаются исходные байты, декларации путей и хэши. Части передаются по контракту intake. Область, ожидаемые значения, вопросы из эталона и целевые окна в запросы не добавляются. Проверить опись и фактически сохранённые оригиналы в авторизованном браузере. Для 10 ГиБ использовать испытание шага 14.

```sh
PYTHONDONTWRITEBYTECODE=1 python3 test/acceptance/intake.py \
  --origin https://127.0.0.1:18443 --ca-file "$stand_certificate" --project "$test_project_id" \
  --inputs "$private_input_dir" --manifest "$private_original_manifest" --evidence "$private_evidence_dir"
```

Для TLS указать адрес стенда и `--ca-file` с публичным сертификатом стенда. Проверка сертификата включена. Скрипт сохраняет историю HTTP, полученную опись и хэши оригиналов, заново скачанных по авторизованным маршрутам. Если исход команды неизвестен, сначала открыть квитанцию уже начатого поступления. Инструмент загрузки выполняет одну попытку и сохраняет `receipt.json` для адресного продолжения.

## Снимок для оценки

До открытия эталона выгрузить журнал приложения, состояния, оригиналы по штатным авторизованным ссылкам, собственные обращения A и B, снимок итоговой карточки без ручной правки, решения тестового инженера и фактические TXT/DOCX. Зафиксировать исходный снимок хэшами. После фиксации составить `observations.json` из сохранённых первичных результатов. Там, где публичный интерфейс пока не выдаёт доказательство, источник и соответствующая проверка остаются открытыми.

Схема представления для оценщика:

- `originals` отображает пути входного пакета в SHA-256. Рядом с наблюдением хранится `files` с SHA-256 сырых журналов, карточек и скачанных экспортов. Эти относительные пути разрешаются только внутри каталога доказательств.
- `tracks` содержит `A`, `B` и `merged`. У каждой записи в `shown`, `opened` и `readings` есть `originalSha256` и `address`. В `address.unit` передаётся физический идентификатор. Для PDF `address.box` использует точки от левого верхнего угла повёрнутого листа. Сохраняются раздельно показанный обзор и фактический запрос к своему инструменту. Для этих двух наблюдений допустимо окно, полностью содержащее эталонное место. Флаг `address.wholeUnit` используется только после подтверждённой доставки всей физической единицы. Для чтения применяется точный допуск к краям окна. У запроса должны быть `ownOpening` и `receiptId`. Для чтения передаются `scope`, `revision`, `citationId`, `originalVerified`, `reading` со значением и единицей в канонической записи эталона, после сверки с исходной единицей либо `limitation`, а для сохранённого места в карточке ещё `presentInCard`. Флаг проверки оригинала выставляется после открытия авторизованной цитаты и сверки байтов, адреса и фактически поданных моделям строк или пикселей.
- `letter.decisions` содержит элементы `{id, decision, sources}`, где `sources` перечисляет места эталона, сопоставленные по оригиналу и адресу. Неразрешённая ссылка остаётся в списке под собственной наблюдаемой меткой, чтобы выявить лишнее основание. `letter.requests` перечисляет фактические пункты письма с повторениями. `letter.exports` отображает `txt` и `docx` в пути оригинальных скачиваний. Для пустой выборки фиксируются оба пустых значения, `emptyCreateStatus: 422`, `newLetterCount: 0` и `letterNumber: null`. Доказываются ответ и список писем до и после проверки.
- Эталон содержит `places` с `id`, `format`, `originalSha256`, `address`, `scope`, `revision`, `critical`, `readability`, `required` (подмножество трёх треков) и допустимыми парами `variants`. Требуемые границы адресного окна и допуск для каждого края задаются до запуска. Эталон письма хранит полный ожидаемый текст, основания и состав запросов для фиксированного шаблона и адресата.

```sh
PYTHONDONTWRITEBYTECODE=1 python3 test/acceptance/score.py \
  "$private_oracle" "$private_evidence_dir/observations.json" "$private_input_dir" \
  > "$private_evidence_dir/verdict.json"
```

В протоколе показываются все места по формату и треку, включая места с нулём показов и открытий. Нечитаемая запись даёт адресуемое ограничение. Полный текст сравнивается в обоих форматах с нормализацией переноса строк и одного завершающего перевода строки. Для сравнения по времени нужны отдельные доказательства браузера, worker и шлюза.

## Сводка монотонной трассы

`summarize_trace.py` принимает один JSON-протокол с единой монотонной шкалой наблюдения. Поля запуска включают `startedNs`, `observedUntilNs`, замороженные `plannedPackageIds` и `packages`. У каждого пакета есть `id`, `startedNs`, `workloadClass`, `mode`, `routeRevision`, `projectCount`, `phasesNs`, `state` и `attempts`. Завершённый пакет включает этапы из константы `PHASES`. Остальные сохраняют наблюдаемую причину в `reason`.

В попытках указываются `id`, `state`, `spentNanos`, `reservedNanos`, `promptTokens`, `completionTokens` и при наличии `httpStatus`, `timedOut`. Неизвестные числа токенов задаются `null` и считаются в отдельной колонке. Сводку собирать по сохранённым первичным измерениям и единому реестру попыток.

```sh
PYTHONDONTWRITEBYTECODE=1 python3 test/acceptance/summarize_trace.py "$private_monotonic_trace"
```

## Управляемый прогон собранного приложения

`managed.mjs` запускается из точного Linux-образа стенда, с отдельными тестовой БД, S3 и журналом, уже прошедшими миграции. Он использует скомпилированные модули образа и отправляет исходные байты через штатный HTTP-интерфейс на loopback этого контейнера. Входы, конфигурация каталога и манифест оригиналов монтируются на чтение под `/acceptance/input`, `/acceptance/config`, `/acceptance/manifests`. Для записи результатов монтируется пустой отдельный каталог под `/acceptance/evidence`. Каталоги эталона не монтируются.

`STEP15_RUN_ID` задаёт имя прогона, `STEP15_CASES` — имена пакетов через запятую. Встроенный управляемый транспорт отвечает по тексту, адресам и данным фактически переданной репрезентации. Определение области использует имя папки. Нативные и растровые запросы, фиксация находок, сверки и файл письма проходят через рабочий код. Результаты такой серии характеризуют технический контур и работу симулятора. Доступ OpenRouter в контейнере отключён.

Холодная фаза использует новую БД с исходным каталогом. Тёплая сохраняет версии поступивших оригиналов и производные и закрепляет новую версию того же каталога. Offline-фаза останавливает транспорт и worker, затем открывает прежний снимок после запуска worker. `STEP15_CHECKPOINT_REPLAY=1` дополнительно сохраняет копию хвоста журнала одного завершённого синтетического задания и в выделенной БД восстанавливает положение непосредственно перед последним полученным ответом. Прежде сохранённая квитанция шлюза остаётся. Успех требует возвращения того же `attemptId` и `requestHash` без нового обращения. Протокол различает этот контроль и простое перечитывание сохранившегося снимка.

`STEP15_CASES=mixed-followup` проверяет смешанный пакет и затем отдельное поступление N06 в том же проекте. Смонтируйте публичный `mixed.json`, манифесты `mixed.json` и `mixed-followup.json`, оригиналы из одноимённых каталогов. Сценарий сохраняет `mixed-cold-machine.json` с независимыми наблюдениями A/B. Тестовый инженер открывает опоры, оставляет неподтверждённые вопросы внутренними и сохраняет отдельное заключение о начале работ. Для принятого исходного письма создаётся тестовая запись отправки по штатному API без передачи внешнему адресату. При открытой досылке фиксируются текущие и исторические ссылки. Новый машинный снимок сохраняется до инженерской классификации влияния. Отдельная сессия проверяет первое решение со старой версией. После повторного заключения сценарий открывает исторический отправленный снимок, старое заключение, обе исходные опоры и сверяет хэши исторических TXT и DOCX. Эталон сравнивается вне контейнера.

`STEP15_CASES=mixed-regression` выполняет ту же проверку с историей подтверждённой редакции, сохраняя журнал отправок без новой записи. После фиксации исходной досылки тестовый администратор закрепляет отдельную версию каталога с `txt` как эквивалентом для зазора. Этот контроль формата хранится отдельно от слепого исхода и не объявляет старые источники замещёнными. После прогона проверьте адресную регрессию. Код 1 означает несовпадение хотя бы одного условия. Критерии полного AC06/AC07 оцениваются отдельно.

```sh
PYTHONDONTWRITEBYTECODE=1 python3 test/acceptance/followup_regression.py "$run_evidence_dir"
```
