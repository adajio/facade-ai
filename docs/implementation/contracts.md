# Контракты реализации Facade AI 1.1

Срез требований `42ed7fc`. Контракт подключения модулей шага 1. Продуктовые поля и маршруты уточняют исполнители соответствующих шагов по [приложению Б](../v1.1/backend.md).

## Процессы и сборка

- Node.js 24 LTS, npm, TypeScript strict, ESM (NodeNext). В TS используем относительные импорты с окончанием `.js`, соответствующие исходникам `.ts`. Корневой `npm ci` включает workspaces `src/modules/*`; модуль объявляет свои дополнительные зависимости в собственном `package.json`. Корневой lock обновляет исполнитель шага 1.
- API запускается из `apps/api/src/main.ts`, worker — из `apps/worker/src/main.ts`. Модуль публикует `src/modules/<module>/index.ts` и именованный `export async function register(app: FastifyInstance): Promise<void>`. Чисто фоновый модуль может экспортировать только `startWorker` из `src/modules/harness/index.ts`. API загружает модули по имени каталога в отдельных Fastify-плагинах. `access` регистрируется на корневом экземпляре, чтобы проверки Origin и CSRF действовали на маршрутах всех модулей. Для межмодульного взаимодействия используйте явный импорт или контракт БД.
- `converter-port` — библиотека. Её `index.ts` остаётся точкой импорта для потребителей. Загрузчик API пропускает её до импорта по списку `libraryModules` в [src/platform/modules.ts](../../src/platform/modules.ts). В этом же списке указываются другие библиотеки. Остальные точки входа считаются модулями API, с исключением `harness` для фонового режима. Ошибка импорта, отсутствие `register(app)` или ошибка регистрации модуля API прерывают запуск.
- `app.db` — общий `pg.Pool`; `app.config` — конфигурация из `src/platform/config.ts` с `databaseUrl`, `dataDir`, `host`, `port`. Префикс `/api` входит в маршруты, объявляемые модулями, например `app.get('/api/me', …)`. Загрузчик дополнительный префикс не навешивает. `GET /healthz` проверяет живость, `GET /readyz` проверяет доступность PostgreSQL.
- Harness экспортирует `startWorker(context: WorkerContext): Promise<void>` из своего `index.ts`. Тип из `src/platform/worker-context.ts`: `{ db: Pool; config: AppConfig; signal: AbortSignal; logger: Logger }`. Promise живёт до остановки worker. Worker по SIGTERM/SIGINT прерывает signal, ожидает возврата из harness и закрывает пул. Отсутствие harness завершает процесс с ошибкой запуска. Шаг 9 владеет диспетчером из `intake_reader_jobs` и подключением `startImports`.
- API и worker требуют `DATABASE_URL` и `FACADE_DATA_DIR` (абсолютный путь либо путь от рабочего каталога). `HOST` по умолчанию `127.0.0.1`, `PORT` — `3000`. В контейнере явно задайте `HOST=0.0.0.0`. Команды выполняются из корня. `npm run build` компилирует сервер в `dist/` и frontend в `web/dist/`; `npm run typecheck`, `npm test`, `npm run migrate`, `npm run start:api`, `npm run start:worker`. Миграции запускаются перед стартом сборки на новом стенде.
- Svelte/Vite живёт в отдельном пакете `web/`. Установка `npm --prefix web ci` перед корневой сборкой. API обслуживает `web/dist` с того же origin, вызовы клиента идут по относительным `/api/…`. Каталог приложения выбирается независимо от текущего URL. Несуществующий маршрут API возвращает JSON 404.
- SQL принадлежит исполнителю соответствующего шага. Именование `db/migrations/NN_*.sql` или `NN-*.sql`, где `NN` — двузначный номер шага; одного номера может быть несколько. После создания реестра полное имя определяет идентичность и лексикографический порядок применения. Миграция транзакционна, исполняется под общим PostgreSQL advisory lock; учёт по имени и SHA-256 в `public.facade_schema_migrations`. После применения файл неизменяем. Транзакцией управляет runner. Если внутри шага нужен порядок, укажите его в имени и закрепите зависимости.
- После добавления workspace или изменения его зависимостей исполнитель шага 1 обновляет корневой lock командой `npm install`. Стенд использует этот lock через `npm ci`; web устанавливается отдельно из `web/package-lock.json`. В образе сохраняются `node_modules` и `src/modules`, включая вложенные `node_modules` отдельных пакетов: сборка связывает их с соответствующими каталогами `dist/src/modules`. Для синтетической проверки PostgreSQL используйте отдельную базу из [инструкции стенда](../../infra/test-stand/README.md).
- Для собранного модуля intake стенду нужны закрытый S3-совместимый бакет, `FACADE_S3_ENDPOINT`, `FACADE_S3_BUCKET` и AWS-учётные данные сервисной роли. Права выдаются для конкретного бакета. `FACADE_DATA_DIR` хранит временные части и иные локальные данные процесса.
- Общая ошибка API имеет поля `code`, `message`, `requestId`; модуль при необходимости дополняет её ссылкой на доступный объект и сведениями о продолжении. Мутации используют `Idempotency-Key` и `If-Match` по контракту команды. Контракт тел конкретных маршрутов публикует владелец модуля.

## Идентичности и доступ

- Сущности имеют устойчивые UUID. Логин изменяемый, нормализованный, с уникальностью в БД; история ссылается на ID пользователя. Область доступа задаётся организацией и проектом. Область оценки, поколение входов, версия документа и версия правки самостоятельны. SHA-256 относится к байтам и служит проверкой целостности, а правами управляет ссылка из проекта на конкретную версию.
- Шаг 2 владеет таблицами учётных записей, сеансов, организаций, проектов, членства и каталогов. Модули используют `requireAccess` для чтений и `executeCommand` для прикладных мутаций. Фактические SQL-имена и параметры проверок закреплены в [контракте модуля доступа](../../src/modules/access/README.md).
- Владелец управляет членством и каталогом; инженер работает в выделенной области; наблюдатель читает предоставленное; оператор получает обезличенную диагностику; администратору содержимое доступно только по явному допуску. Вход через серверный сеанс, cookie HttpOnly, SameSite и Secure в TLS-установке; мутации с CSRF. Каждый запрос к объекту разрешается по серверному членству, включая прямые URL, версии и историю. При повторе команды право проверяется до выдачи сохранённой квитанции. Защищённые ответы и Range используют `Cache-Control: no-store`.
- Секреты поступают из окружения стенда. Тесты используют синтетические данные и управляемый транспорт; внешние платные вызовы допускаются только на шаге 15.

## Приёмочные материалы

Входы под `test/fixtures/input/`, независимый эталон под `test/fixtures/gold/`. Эталон не передаётся читателям. AC03 измеряется по всем ожидаемым местам отдельно для A, B и результата до правок, включая растровую таблицу с нулём текстовых кандидатов и адресуемую нечитаемость. AC06 отдельно сверяет решение, полный текст TXT/DOCX и отсутствие письма при пустой выборке. Отрицательный контроль удаляет критическую таблицу из наблюдений без изменения решения и письма. Ожидается провал AC03 при совпадении AC06.

## Команды проверки

| Команда | Предусловия и область |
|---|---|
| `npm test` | Корневой `npm ci`, Node.js, Python 3, Poppler и Tesseract с языками из [профиля reader](../../src/modules/pdf/README.md). Серверная сборка, локальные Node-тесты, тесты workspace, учебного корпуса и оценщика. Стендовые сценарии в смешанных файлах получают статус `SKIP`. |
| `npm run test:stand:intake` | Серверная сборка, свежая **немигрированная** выделенная БД `test_step3…`, закрытый S3-бакет и права на него. Сценарий сам создаёт свою схему. [Проверка приёмки](../../src/modules/intake/README.md) |
| `npm run test:stand:supplements` | Серверная сборка, `npm --prefix web ci`, Chromium или Chrome, мигрированная выделенная БД с соответствующим работающим API, закрытый S3-бакет, `FACADE_E2E_BASE_URL` и доступный для записи `FACADE_E2E_OUTPUT`. [Проверка досылки](../../test/e2e-supplements/README.md) |
| `npm --prefix web test` | Отдельные браузерные проверки интерфейса по условиям его тестов. |

Для каждой стендовой команды загрузите собственное окружение. Обе команды требуют `DATABASE_URL`, `FACADE_DATA_DIR`, `FACADE_S3_ENDPOINT` и `FACADE_S3_BUCKET`. Отсутствующие переменные дают `NOT CONFIGURED` и код 2. При запуске выводятся `RUN` и итог `PASS` или `FAIL`; ошибка теста сохраняет ненулевой код Node. Точечные проверки остальных модулей описаны в их README.
