# Очередь межисточниковой сверки

Очередь сохраняет задачи, обнаруженные при приёме или чтении пакета. Задача содержит область, редакцию пакета, две закреплённые единицы чтения, причины постановки и идентификаторы независимых читателей. Для `compare_sources` порядок двух единиц не влияет на идентификатор. Точная повторная доставка причины оставляет одну запись. Причины от независимых ветвей и от обработки описи сохраняют своё происхождение.

## Работа с очередью

1. Вызвать `discover(scope=…, package_revision=…, left=…, right=…, reasons=…, readers=…)` для пары, которую требуется сверить. Каждая причина содержит `kind`, `origin` и `reference` на сигнал, а также может содержать контекст. `left` и `right` — идентификаторы единиц в закреплённой редакции. Список читателей сохраняется при первой постановке.
2. Вызвать `assign(task_id, worker=…, lease_seconds=…)` для открытой задачи. Только один исполнитель получает активную аренду и `attempt_id`. Время аренды задаёт вызывающая сторона. `get(task_id)` и `list_tasks(scope=…, package_revision=…)` возвращают причины, состояние и историю попыток.
3. Вызвать `complete(task_id, attempt_id, outcome=…, evidence=…)` после сверки. Каждая квитанция содержит `reader`, `unit`, `receipt` и адрес в оригинале `location`. Закрытие требует адресованных материалов от каждого назначенного читателя по обеим единицам. Одна квитанция может подтверждать несколько мест в пределах одной пары «читатель — единица».
4. Вызвать `fail(task_id, attempt_id, reason=…, evidence=…)` при отказе или недостаточном основании. Попытка сохраняет причину и доступные частичные квитанции, задача снова доступна для назначения. Если исполнитель остановился без ответа, новая аренда доступна после истечения прежней. При смене попытки старый исполнитель теряет право записать исход. Точный повтор ранее принятого исхода возвращает текущее состояние задачи.

Новая причина в той же редакции открывает уже завершённую задачу с сохранением исхода прежней попытки. Если причина поступила во время чтения, закрыть задачу сможет следующая попытка с полным набором причин. Исполнитель завершает текущую попытку через `fail` и передаёт доступные квитанции.

## Границы испытательного профиля

Доверенный адаптер проверяет, что единицы принадлежат редакции, читатели работали независимо, квитанции действительно выданы и исход сравнения основан на прочитанных материалах. Очередь проверяет состав адресованных квитанций и записывает принятый исход сверки. Решение о комплектности и внешнем запросе оформляется в инженерном контуре. Новый `attempt_id` даёт аренду локальной задачи. Допуск к повторной отправке при неизвестном исходе проверяет шлюз обращений. [Квитанции и восстановление](agent-workflow.md#доставка-пакетная-проверка-и-сохранение-при-отказе) · [Инженерная запись](engineer-fact-delivery.md)

Испытательная реализация использует стандартный модуль SQLite текущего Python-harness. Таблицы можно создать рядом с таблицами существующего журнала. На каждый поток открывается своя `ReconciliationQueue` с общим путём к базе. Конкретный механизм продуктовой очереди определяет профиль приложения. [Реализация](../experiments/package_review/reconciliation_queue.py) · [Профиль проекта](project-profile.md)

## Проверка

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest -v experiments.package_review.test_reconciliation_queue
```

Синтетический пакет музейной ссуды содержит реестр и упаковочную опись с расхождением числа креплений. Контроли проверяют объединение сигналов, границу редакции и области, отказы при недостатке квитанций, восстановление после известного отказа и истечения аренды, конкурентное назначение и работу с уже созданным журналом.
