# Обычная загрузка и автоматическая сверка источников

Редакция 0.15. Входом служат оригиналы и область инженерной оценки. Пользователь загружает пакет один раз. В форме приёмки нет поля для предполагаемого вида расхождения, номера листа или искомой позиции.

## Кто отвечает за переход

Во время первичного просмотра модель может убедительно описать два источника и всё же закончить сеанс до их сопоставления. Запись наблюдения в реестр сохраняет прочитанное. Для совместной проверки нужна отдельная сохраняемая запись с владельцем, основанием и двумя адресами. Обработка загрузки сама создаёт её. Приложение отвечает за выдачу, повторное назначение и доставку результата. Читатели отвечают за выбор дополнительных мест и содержание утверждений. Инженер устанавливает пригодность для стадии и решает вопрос об отправке.

| Событие | Что делает система | Что остается проверить |
|---|---|---|
| Приняты оригиналы | Вычисляет хэши байтов, фиксирует состав редакции, единицы чтения и связь каждой с оригиналом. Кеш преобразования привязан к байтам и версии reader. | Файлы без полноценного представления видны в охвате. |
| Есть признаки общей темы | По всему пакету сопоставляет редкие сочетания слов, обозначения и физически выровненные поля. Ранжирует пары внутри каждой пары разных оригиналов. Лучшее структурное совпадение проходит совместное чтение, остальные кандидаты доступны модели. | Общая шапка может совпасть у совершенно разных объектов. |
| Читатель нашёл смысловую связь | Может предложить два адреса и основание из полученного материала независимо от лексического рейтинга. Для пар без структурных признаков предусмотрен отдельный смысловой просмотр, в том числе по изображениям. Непросмотренные пары видны инженеру. | Разные обозначения, синонимы и растровые материалы требуют измерения отдельно. |

| Оба читателя получили задание | Каждый независимо открывает источники, различает общий объект и область, сохраняет адресное чтение каждой стороны. При неполной выборке записывает границы просмотра. | Отрицательный вывод о комплектности требует охвата применимых источников и обязательства предоставить конкретное сведение. |

При неизвестном исходе оплаченного запроса сверяет журнал перед повторной отправкой. | Частичный ответ может инициировать дочитывание. Для принятия составного тезиса нужны все опоры. |

## Граница Mastra и прикладной очереди

Хранилище приложения владеет оригиналами, версиями, единицами, попытками, фактами, состоянием выдачи и решениями человека. Два экземпляра агентной сессии могут работать с разными поставщиками. Mastra либо иной клиент модели получает технический контракт инструментов, контекст своего задания и способы попросить дополнительные материалы. Он возвращает наблюдения и запросы на продолжение. Подтверждение чтения привязано к фактически доставленному материалу. При смене поставщика работоспособность проверяется на тех же исходниках и отрицательных контролях.

В целевом сервере запись основания и уведомление исполнителя фиксируются в одной транзакции PostgreSQL. После перезапуска исполнитель выбирает открытые поручения и истёкшие аренды по редакции. Итог попытки с устаревшим токеном сохраняется для разбора и не меняет новый результат. Выгрузка содержит идентификатор версии и ссылки на факты и их собственные проверки. Это контракт серверной поставки. Локальный профиль использует Python, SQLite, файловые квитанции и внедряемые адаптеры.

## Проверка границ решения

Маршрут от загрузки проверяется отдельно от точности чтения. Контроль обнаружения состоит из пары с общим кодом, пары без общего кода и ложного совпадения шапки. Для числового расхождения отдельно проверяются обе исходные строки, их привязка и инженерный смысл. Переименование файлов, перестановка листов, отказ читателя, повтор доставки, изменение исходных байтов и прекращение работы между получением доказательства и публикацией образуют контроли восстановления. Один успешный пример не определяет качество по другим классам входов.

Исполняемые части профиля: [приёмка загрузки](../experiments/package_review/ordinary_intake.py), [структурный поиск](../experiments/package_review/source_relations.py), [очередь](reconciliation-queue.md), [восстановление оборванного чтения](../experiments/package_review/assessment_prefix.py), [дочерняя работа](../experiments/package_review/comparison_work.py), [критерии слепой оценки](ordinary-intake-acceptance.md).

## Если сведения распределены по нескольким заданиям

У каждого адресного наблюдения остаются собственные редакция, источник, строки или область изображения, читатель и квитанция, даже когда общая сверка прервалась. В картотеке инженера можно увидеть чтение первого оригинала из одного задания и чтение другого оригинала из другого. Объединение по исходному обозначению служит указателем для сверки. Статус сопоставимости требует предметного решения с доказательствами с двух сторон. После такой сверки реестр отделяет подтверждённый общий объём, спорные исполнения и возможные последствия по стадиям. [Сборка картотеки чтений](../experiments/package_review/intake_export.py)

Очередь детализации может также получить задание напрямую из исходных строк двух уже поставленных в работу единиц. Если в обеих есть общий буквальный вариант и дополнительные варианты различаются, приложение фиксирует весь список заданий до первого сетевого обращения. Перерыв оставляет хвост открытым. Каждый последующий исполнитель выбирает доступные поручения, одновременно соблюдая сверку неизвестных оплат. [Регистрация дочерних заданий](../experiments/package_review/comparison_work.py) · [Проверка происхождения ответа читателя](../experiments/package_review/comparison_reader.py)

## Контекст перечисления и исправление статуса

При чтении отдельного пункта списка reader передаёт заголовок и вводящую фразу из того же оригинала, в том числе при разбиении на разные единицы чтения. Читатели различают перечисление фактически приложенных документов, историю предыдущего запроса, требования и планируемую поставку. Утверждение о наличии документа в данной поставке требует связи с её описью и оригиналом. До разрешения контекста фразу можно предъявить как цитату. Оспаривание уже проверенного тезиса фиксируется с редакцией, точным текстом и адресами доказательств. Новая инженерная выдача показывает спорный статус и отзывает основанные на нём проекты вопросов. [Обработка оспоренного тезиса](../experiments/package_review/intake_export.py)

## Сверка по чтениям из разных заданий, редакция 0.14

При обычной загрузке профиль межзаданных сверок получает ту же проверенную опись и оригиналы. Единицей первичной работы служит окно одного источника. Каждое принятое наблюдение содержит редакцию поставки, хэш оригинала, адрес единицы и строки, идентификатор задания, модель, исходное обозначение, буквальное чтение и квитанцию фактического запроса. Роль записи показывает, прочитана ли содержательная характеристика или только упоминание. Допустимо опубликовать наблюдение по одному источнику, когда второго ещё нет.

**Событие постановки.** При записи наблюдения приложение ищет в той же редакции ранее полученное чтение другого оригинала и другого задания с общим предметным ключом. Запись наблюдения и постановка или обновление сверки фиксируются одной транзакцией. Можно начать с любого из источников. Сходство исходных файлов влияет на порядок первичного чтения. Для события достаточно самих двух адресных чтений. В карточке навсегда остаются идентификаторы двух чтений, впервые давших основание; у каждой попытки есть полный снимок её собственных оснований. [Доменная операция](../experiments/package_review/cross_read.py)

**Граница алгоритма.** В исполняемом профиле ключ берётся из дословной фразы или семейства исходных обозначений. Основа марки и её помеченное исполнение различаются при проверке цитаты. Семейство используется для маршрутизации. Одинаковые названия разных объектов, одинаковые числа и повтор страницы ещё требуют проверки контекста. Одинаковый оригинал, повтор квитанции, другая редакция и результат одной работы не порождают независимую междокументную сверку. Синонимы без общего текста остаются задачей смыслового поиска.

**Исполнение.** Два читателя независимо получают оригинальные места, соседние строки и шапки. Каждый может запросить расширение области или следующие строки. Они возвращают область применимости, чтение каждой стороны, состав и сумму по адресным строкам, вывод для стадии и существенные сомнения. Если появляется новый материал, сохраняются предыдущий исход и новая версия задания. Регистрация сверок идёт одновременно с первичным чтением. Сетевое исполнение сверок за общий бюджет допускается после обработки всех первичных обязательств. [Порядок допуска и состояния охвата](reading-coverage.md) Достигнутый денежный предел оставляет неоплаченные обязательства в состоянии ожидания. При известной отсрочке и разрешённом продолжении можно повторно назначить ту же версию; неизвестный сетевой исход сначала сверяет шлюз. [Планирование и возобновление](../experiments/package_review/reading_flow.py)

**Выдача.** Инженеру доступны исходные наблюдения, причины постановки, состав каждой сравниваемой группы, покомпонентные результаты обеих моделей, расхождения и состояние охвата каждого оригинала. Автоматически предложенный пункт о противоречии требует двух исходных мест, совместимой области и стадии, обоснованной необходимости решения и адресной повторной проверки текста вопроса обеими ветвями. Расхождение числовых раскладок при одинаковой сумме удерживает пункт на внутренней проверке. Для подтверждённой нехватки сохраняется прежнее отдельное требование доказать обязанность предоставить сведения и достаточность осмотра. Текущий детектор межисточниковых противоречий сам по себе не доказывает отсутствие. Сборку и отправку итогового письма утверждает инженер. [Сборка выдачи](../experiments/package_review/cross_read_delivery.py)

В испытании исходная сортировка по силе пересечения отложила два оригинала до исчерпания денег. В редакции 0.14 после испытания ввели чередование оригиналов. Редакция 0.15 также чередует физические единицы внутри оригиналов и отдельно назначает дополнительные окна и вторых читателей. Входной адаптер принимает также номер строки с дословно возвращённой строкой или последовательностью её полных ячеек. При составном названии может выделять начальный код физического поля из предъявленных строк, сохраняя всю исходную формулировку модели. Эти варианты допуска проверяют происхождение наблюдения. Правильность его чисел, областей и подытогов проверяется отдельно.

## Обычная загрузка с инженерным профилем · 0.16

Настроенный профиль ищет адресные основания во всех поступлениях проекта по каждому вопросу и области. Роли документов дают контекст для сверки переформулированных сведений без общего обозначения. Подтверждённые основания и все рассмотренные кандидаты видны отдельно. [Контракт и воспроизводимая проверка](engineering-questions.md)
