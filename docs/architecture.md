# Архитектурные правила

Сохранённые разделы 2–4 стандарта v0.2. Применяются только к нужным проекту частям. Порядок исполнения определяет workflow.md; прежний обязательный процесс v0.2 не переносится. Явно выбранный владельцем серверный профиль, включая Axum или Actix Web, сохраняется. Если профиль не выбран, его выбирают в рамках задачи; шаблон не устанавливает зависимости и не закрепляет их версии.

## 2. Профили проектов

| Профиль | Базовая реализация | Подключаемые части | Дополнительные доказательства готовности |
|---|---|---|---|
| Библиотека / SDK | Rust crate; публичный API отделён от приложений | Обвязки для TypeScript/Python по требованиям потребителей | Проверены публичный контракт, ошибки, примеры использования и совместимость затронутых потребителей |
| CLI / локальная утилита | Rust; вычисления и команды разделены | Локальное хранение или удалённый API при необходимости | Проверены коды завершения, stdout/stderr, ошибочные входы и сохранность пользовательских файлов |
| API / серверный сервис | Rust; модульный монолит | Supabase/PostgreSQL для постоянных данных; Auth/Storage по потребности | Проверены контракты API, доступ, миграции, перезапуск и восстановление применимого состояния |
| Веб-приложение | Svelte + TypeScript; Rust API для серверной предметной логики | SvelteKit по требованиям маршрутизации/рендеринга; Supabase для данных | Пройден основной пользовательский путь, включая авторизованное состояние, ошибки и согласованные размеры экрана |
| Настольное приложение | Tauri + Svelte + TypeScript; Rust для локальных операций | Rust API и серверные данные, если нужна облачная часть | Проверены пакет на целевой ОС, разрешения, IPC, ошибки файловых операций и перезапуск |
| Обработчик задач / данных / AI | Rust для управления задачами и предметных правил | Python для специализированных библиотек; хранение и внешние провайдеры по требованиям | Проверены сбой, повтор, отмена при её наличии, сохранение результата и качество на контрольных данных |

Для веб-проекта без серверной предметной логики Rust-сервис не создаётся ради формального присутствия языка. При появлении такой логики применяется правило Rust по умолчанию.

Для настольного профиля в паспорте обязательно выбрать режим: автономный, клиент сервера или локальный с последующей синхронизацией. Последний требует отдельного контракта конфликтов, повторов и восстановления. Само использование Tauri не подтверждает работу без сети.

SvelteKit в Tauri собирается как статический фронтенд; серверные обработчики SvelteKit не считаются частью такого пакета. Это ограничение описано в [документации Tauri](https://v2.tauri.app/start/frontend/sveltekit/).

## 3. Приоритет Rust и правила исключений

### 3.1. Базовое правило

Новая предметная логика, вычисления, проверки, обработка файлов, серверные компоненты и CLI разрабатываются на Rust по умолчанию. Приоритет применяется к собственному коду проекта; зрелые внешние продукты используются через их штатные интерфейсы.

| Ситуация | Правило |
|---|---|
| UI в браузере или WebView | Svelte + TypeScript; отдельное исключение не требуется |
| SQL-схемы, миграции, ограничения целостности и RLS | SQL в составе слоя данных; отдельное исключение не требуется |
| Генерируемые клиенты, сборочная конфигурация, декларативные файлы | Язык соответствующего инструмента; новая предметная логика подчиняется базовому правилу |
| ML/OCR, научная или предметная библиотека с существенно лучшей поддержкой в Python | Ограниченное исключение для Python с фиксированной границей |
| Требуемый SDK или среда исполнения не поддерживает Rust в нужном объёме | Обвязка на поддерживаемом языке; граница и объём исключения записываются |
| Convex становится основным серверным слоем | Архитектурное исключение: функции и часть логики переходят в TypeScript |
| Проверочный одноразовый эксперимент | Разрешён подходящий язык; перед переносом в продукт выбор пересматривается |
| Уже проверенный собственный компонент на другом языке | Допустимо повторное использование после оценки совместимости, поддержки и стоимости переписывания |

Знакомство агента с языком, размер обучающей выборки, число строк кода или формальное стремление увеличить долю Rust сами по себе не определяют решение. Экономическое основание допустимо, если сравнение учитывает интеграцию, эксплуатацию и поддержку, а не только скорость первой реализации.

### 3.2. Содержание решения об исключении

До зависимой реализации решение должно содержать:

- конкретный компонент, выбранный язык и границу исключения;
- требуемую возможность и проверяемое ограничение варианта на Rust;
- рассмотренную Rust-альтернативу и причину отказа;
- влияние на контракты, поставку, лицензии и эксплуатацию, если оно существенно;
- способ проверки результата и ответственного за поддержку;
- характер решения: постоянное либо временное; для временного — событие пересмотра;
- основание принятия: решение владельца либо делегированные полномочия в согласованном плане.

Если существенно сравнение производительности, стоимости или качества, приводится измерение либо обозначается непроверенная оценка. При `NOT_RUN` нельзя описывать сравнение как измеренный результат.

### 3.3. Границы исключения

Python-компонент получает определённый вход, выход, модель ошибок и способ запуска. Предметные правила сохраняются в одном месте. Размещение библиотеки в Python не является основанием перенести туда весь бэкенд.

Способ связи — процесс, HTTP, очередь или FFI — выбирается по задержке, изоляции отказов и поставке. FFI и `unsafe` требуют проверки конкретного контракта памяти и обработки ошибок. Процент Rust-кода не используется как показатель качества.

## 4. Архитектура, данные и контракты

### 4.1. Устройство приложения

По умолчанию приложение начинается как модульный монолит. Отдельный сервис выделяется при конкретной потребности в независимом развёртывании, масштабировании, изоляции или среде исполнения.

Предметное Rust-ядро отделяется от HTTP, Tauri IPC, UI и провайдеров. Адаптеры переводят внешние данные в предметную модель и обратно. Общее ядро переиспользуется через библиотеку; платформенные возможности и авторизация остаются на соответствующей границе исполнения.

Для нового проекта глоссарий располагается в `GLOSSARY.md`. В нём фиксируются предметные термины и различия состояний, влияющие на поведение. Если репозиторий уже объявил другой путь глоссария, используется он; более широкий `CONTEXT.md` сохраняет своё назначение.

### 4.2. Хранение и доступ

Supabase/PostgreSQL — базовый выбор при необходимости серверных постоянных данных. Auth, Storage и Realtime подключаются по требованиям проекта. Конкретный способ подключения Rust и выбранные библиотеки фиксируются при старте; наличие Supabase не обязывает переносить предметную логику в Edge Functions.

Для каждой сущности определены основное хранилище и владелец записи. Поисковые индексы, кэши и графы имеют правила восстановления и обновления. Миграции версионируются; для затронутых существующих данных проверяется переход из предыдущей версии.

Проверка доступа выполняется на доверенной серверной границе. При прямом клиентском доступе к таблицам определяются и проверяются RLS-политики. При использовании серверной роли, обходящей RLS, Rust API сам обеспечивает необходимые проверки. Секреты привилегированного доступа хранятся на сервере; браузер и настольный клиент считаются недоверенными средами. Основание для правил RLS: [Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).

### 4.3. Convex

Convex подключается через ADR с указанием конкретной выгоды реактивной модели, владельца данных и допустимой доли серверной логики на TypeScript. Его модель включает собственную БД и серверные функции; запросы к внешним системам выполняются через actions. См. [обзор Convex](https://docs.convex.dev/understanding/overview) и [actions](https://docs.convex.dev/functions/actions).

Если одновременно используются Supabase и Convex, ADR обязательно задаёт:

1. какие сущности принадлежат каждой системе и в каком направлении передаются изменения;
2. где проверяются права и как передаётся идентичность пользователя;
3. как переживаются частичная запись, повтор, задержка синхронизации и конфликт;
4. как обнаруживается рассогласование и восстанавливается состояние.

Транзакция Convex не считается общей транзакцией с внешним PostgreSQL. Чтение внешней БД не считается автоматически включённым в реактивные подписки Convex.

### 4.4. Межъязыковые контракты

У API, IPC и заданий определены входы, выходы, ошибки, идентификаторы, версии и правила повторов. На недоверенных границах выполняется проверка данных во время исполнения.

Где доступна корректная генерация, типы Rust/TypeScript/Python выводятся из одного определения. Если генерация не покрывает контракт, используются явные преобразования и проверки совместимости. Политика описывает как минимум отсутствие значения, `null`, числа/точность, даты, двоичные данные и идентификаторы, если они присутствуют в обмене.
