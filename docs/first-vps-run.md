# Первый прогон на VPS · редакция 0.9

Редакция 0.19 сохраняет самостоятельные чтения, продолжает незавершённый вопрос на его собственных оригиналах и разрешает расхождение в выборе решающих цитат через проверку пары значений. [Контракт и проверка на Wafer US](reader-continuation.md)

В профиле 0.18 для запроса о непередаче проверяются предмет и адресное свидетельство по текущей поставке. Маршрут Kimi на синтетическом тесте — Relace FP4 с обязательным ZDR. [Правило, испытание и настройки](delivery-proof.md)

## Выбор двух читателей

На 21.11.2026 предлагаем выбрать две производственные API-модели разных разработчиков. Обе получают полное самостоятельное задание на русском по одной версии пакета и одному каталогу. Исполнение моделей внешнее. На VPS работают приложение, Mastra и reader. При испытании за каждой ветвью закрепляется один модельный маршрут.

| Ветвь | Значение параметра `model` | Основание для первого прогона |
|---|---|---|
| A | `qwen/qwen4-max` | У Qwen есть промышленная мультимодальная модель с нативным входом изображений и пользовательскими инструментами. На ней проверяем способность ориентироваться на целом чертеже, самостоятельно выбирать увеличение и связывать пометки с таблицей. [Карточка Qwen4-Max](https://www.alibabacloud.com/help/en/model-studio/qwen4-max) |
| B | `moonshotai/kimi-k3.1-pro` | Модель Moonshot с нативным зрением и многоходовой работой с инструментами. Её обучение для длинных задач с документами делает разумной гипотезу, что она сможет проследить строку ведомости до другого документа и различить проектный лист и коммерческое приложение. [Карточка Kimi K3.1 Pro](https://www.alibabacloud.com/help/en/model-studio/kimi-k3-1-pro) |

Обе ветви проверяют и размеры на листе, и междокументные связи. Покрытие одной ветви, общие пропуски и вклад обсуждения измеряются отдельно. Два семейства дают возможность увидеть различные ошибки. Насколько часто модели ошибаются одинаково на фасадных документах, предстоит измерить. В первом опыте приоритет отдан качеству распознавания. Старшие публичные модели выбраны по подходящим возможностям. Их преимущество по результату инженера остаётся проверяемой гипотезой.

## Рабочий маршрут OpenRouter

Владелец выбрал OpenRouter. Обе ветви вызывают `POST https://openrouter.ai/api/v1/chat/completions` с серверным ключом OpenRouter. Для первого опыта выбираем **Alibaba, обычный endpoint**, у обеих моделей. Так при сравнении сохраняются общий шлюз и поставщик инференса. Прямой аккаунт Model Studio не требуется. По открытому каталогу 21.11.2026 у этих двух записей заявлены изображения, `tools` и свободный выбор `tool_choice: auto`. [Endpoints Qwen](https://openrouter.ai/api/v1/models/qwen/qwen4-max/endpoints) · [Endpoints Kimi](https://openrouter.ai/api/v1/models/moonshotai/kimi-k3.1-pro/endpoints)

Фрагменты двух **отдельных** запросов (контекст и определения инструментов добавляет worker):

```json
{
  "model": "qwen/qwen4-max",
  "tool_choice": "auto",
  "provider": {"only": ["alibaba"], "allow_fallbacks": false, "require_parameters": true}
}
```

```json
{
  "model": "moonshotai/kimi-k3.1-pro",
  "tool_choice": "auto",
  "provider": {"only": ["alibaba"], "ignore": ["alibaba/prime"], "allow_fallbacks": false, "require_parameters": true}
}
```

Базовый slug `alibaba` допускает варианты провайдера. В проверенном каталоге Qwen был один соответствующий тег. Для Kimi опубликованы `alibaba` и `alibaba/prime`. Поэтому у Kimi задано явное исключение. Перед серией сохранить снимок каталога и проверить, что фильтры для каждой модели оставляют единственный допустимый тег `alibaba`. Если появился другой вариант или исчез выбранный, обновить фильтры под тот же целевой тег и проверить профиль до измерения. Запросы используют один ID модели без списка замен. При недоступности выбранного маршрута в отчёте фиксируется технический исход соответствующей ветви. [Семантика фильтров OpenRouter](https://openrouter.ai/docs/guides/routing/provider-selection)

**Учёт каждого обращения.** Сохранить конфигурацию и хэш исходящего запроса, версии worker, reader и реестра инструментов, ID ветви, время и ID генерации. Запросить `X-OpenRouter-Metadata: enabled`, сверить поле модели, фактического провайдера и сведения о попытках, когда доступны. Использовать карточку генерации при необходимости. Видимое название Alibaba одинаково у нескольких endpoint, поэтому раздельно фиксируются заданное ограничение, снимок каталога и факты из ответа. Тег, географию инференса, точную сборку весов и квантизацию из одного имени провайдера не выводить. Ветви продолжают собственный диалог через согласованный формат истории OpenRouter. [Метаданные ответа](https://openrouter.ai/docs/api/api-reference/chat/create-a-chat-completion) · [Карточка генерации](https://openrouter.ai/docs/api/api-reference/generations/get-request-&-usage-metadata-for-a-generation)

## Передача приближения и допуск пары

Основной способ доставки — сообщение `role: tool` с ID исходного модельного вызова и частью изображения `image_url` в виде встроенного Data URI. Проверяется окончательный запрос адаптера к **OpenRouter**, включая имя модели, tool ID, размеры и хэш декодированных пикселей. На синтетике при доступном потоковом debug-режиме сверить также преобразованный запрос, показанный шлюзом. Если доступен только исходящий запрос worker, эта квитанция удостоверяет именно эту границу. Сохранить фрагмент протокола без ключей. Правильность прочтения устанавливается по отдельному ответу модели. [OpenAPI OpenRouter](https://openrouter.ai/openapi.json) · [Квитанция визуального входа](../contracts/model-input-receipt.v1.schema.json)

Если native tool-image не проходит через фактический адаптер, второй кандидат упаковки — строковый tool-result с тем же ID и реальный кроп в техническом мультимодальном сообщении `user` того же следующего запроса. Адрес остаётся выбранным моделью. В сообщение не добавляют подсказки или следующий вопрос оператора. Вариант упаковки закрепить до измерения, полностью проверить на обеих ветвях и указать в результате. Если подходящая упаковка различается, сравниваются две связки модели и адаптера.

Каждая ветвь отдельно проходит [слепое испытание самостоятельного увеличения](openrouter-zoom-test.md). Только после положительного результата обеих ветвей переходят к прежнему пакету. Документы заказчика для испытания увеличения не нужны.

## Испытание на прежнем пакете

1. **Зафиксировать исходники и ожидания.** Испытатель сверяет семь оригиналов с закрытым манифестом. По каждому обязательному факту инженер до запуска фиксирует допустимые физические места, контекст, альтернативные опоры и критичность. Отдельные строки покрывают границы доказуемого и запрещённые выводы. В набор включаются места без машинных кандидатов. Архивные находки двух рецензентов помогают составить карту, подпись инженера и предметная проверка требуются отдельно.
2. **Сначала дать целый пакет.** Создать две изолированные ветви в чистом проекте. На входе обычные имена, содержимое, область и стадия работ. Карта испытателя, старые результаты, наводящие запросы, номера нужных листов и готовые вырезки недоступны обеим ветвям. Обычный перечень листов и результаты выбранных моделью поисков доступны. Ведение трассы не меняет подсказки модели.
3. **Снять результат до обсуждения.** Для каждого контрольного места различить четыре наблюдения: место автоматически показано в обзоре, ветвь сама выбрала новое место, ветвь верно прочла факт с открываемым адресом, факт сохранился в машинной матрице. Если факт верно прочитан на стартовом обзоре, засчитать распознавание. Самостоятельный переход требует сохранённого вызова модели. У одного факта может быть несколько допустимых адресов. По общему пропуску сохранить две пустые первичные записи с исходным знаменателем.
4. **После фиксации карт дать возражения.** Повторное открытие места по замечанию второй ветви получает отдельную метку. Проверить, сохранилось ли верное одиночное наблюдение и исправилось ли ошибочное согласие. Инженеру предъявляются области достаточности, подтверждённые проблемы, непроверенные места и актуальность среза. Письмо формируется по подтверждённым инженером основаниям.
5. **Локализовать потери отдельным опытом.** На каждой пропущенной или искажённой критичной строке взять независимое проверенное изображение оригинала и продукционный результат reader, предъявить их обеим моделям в чистых сессиях с одинаковым нейтральным вопросом. Сохранить байты и геометрию, сравнить с входом после адаптера. Затем довести один сохранённый сырой ответ через нормализацию и матрицу без нового вызова модели. В случае неоднозначности записать участок неопределённости и конкурирующие причины. Диагностические ответы не изменяют результат самостоятельного прогона. [Матрица диагностики и правил зачёта](vps-quality.md)

**Пример для испытателя.** Общая ведомость в одном файле и три строки исполнений в другом образуют один вопрос о комплектации. Ход «выделила марку на листе → сама искала её в пакете → открыла заголовок и строки второго листа» подтверждает самостоятельный поиск. Для вывода требуются также арифметика, обозначения изделий и граница актуальности. Если вторую таблицу обеим ветвям впервые предъявили по адресу испытателя, даже безупречное чтение в этом опыте доказывает только чтение по подсказке. Точные страницы, значения и карточка оценки реального набора доступны только в закрытом контуре испытателя.

**Решение по первому прогону.** Для каждого обязательного места предъявить самостоятельные исходы A/B, их фактический источник, объединение до обсуждения и исход после него. Отдельно посчитать общие пропуски, новые и потерянные верные факты, ошибочные запросы, попадание в верный адрес и правильность итогов по стадии. Обязательные факты и запреты применяются к конечному результату по программе приёмки, исходы отдельных читателей сохраняются даже при успешной совместной работе. Этот пакет покажет, воспроизводятся ли известные находки у указанной пары. Перенос на новые поступления требует независимых закрытых семейств.
