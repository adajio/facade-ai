# Mastra harness · шаг 9

Точка входа worker — `startWorker(context: WorkerContext): Promise<void>`. Зависимости для общего lock описаны в package.json этого workspace.

## Контракты для интеграции

- Шаг 3 публикует `intake_reader_jobs`. Диспетчер harness читает строки, закрепляет поколения через gateway и ставит первичные обязанности по фактическим физическим окнам. Запись `dispatched_at` входит в транзакцию постановки.
- Шаг 4/11. Harness требует серверные порты описи единиц, обзора, масштаба, извлечения текста, OCR и поиска. Область каждого запроса строится из доверенного задания. Для результата нужны идентификатор фактической выдачи, оригинал/версия и адрес, хэш оригинала, версия reader, ограничения, адресные строки и/или точные байты представления. Подготовка вызова получает устойчивый ключ эффекта. Запись наблюдения выполняется внутри переданной транзакции.
- Шаг 5/12. После проверки доказательства harness записывает первичное наблюдение через reader и в той же транзакции публикует его для карточки/сверки. При споре для ведущего требуется задание с двумя закреплёнными несовместимыми цитатами. Предложение ведущего проверяется обеими ветвями по оригиналам. Событие публикуется под устойчивым ключом в той же транзакции.
- Шаг 8. Для каждой попытки требуется шлюз с разрешениями, резервом, идентичностью эффекта, повторной выдачей сохранённого ответа и проверкой актуальной пары для всех ходов ведущего и обеих перепроверок. Запись checkpoint и публикация эффекта выполняются под проверкой актуальной аренды в транзакции планировщика. Сеть открывает только шлюз. Шлюз должен принимать точное тело OpenRouter Chat Completions, включая изображения в следовавшем за результатом инструмента мультимодальном сообщении.
- Шаг 13. Браузер читает карточки, оригиналы и состояния через модули reader, assessment и progress. Тестовые сценарии для worker находятся в этом модуле. Журнал запросов с полным контекстом доступен только серверному исполнителю.

## Рабочий запуск

Штатный `npm run start:worker` запускает диспетчер версий, исследования A/B, поиск по сохранённым опорам и `startImports` с общим сигналом остановки. Диспетчер фиксирует карту версии и переводит `intake_reader_jobs.dispatched_at` внутри транзакции с постановкой работ. Поколение оценки учитывает опись и ожидающие финализации. Готовые выводы с неизменным назначением и профилем переиспользуются. Изменение применимого входа или каталога отзывает текущее поколение шлюза внутри той же транзакции.

При отключённом шлюзе worker продолжает вести опись и ставит модельные задания на удержание. При запуске с допущенным маршрутом и доступным журналом он возвращает задания из восстановимых удержаний в очередь. Исходы с неизвестной оплатой остаются на адресной сверке.

Управляемый транспорт подключается из отдельного тестового процесса. Изолированный тест обычной загрузки запускается командой `FACADE_HARNESS_INTEGRATION=1 node --test src/modules/harness/worker.integration.test.mjs`. Ему нужны чистая БД приложения `test_*` с миграциями, отдельная пустая БД журнала и тестовый бакет. Подготовка внешних скриптов для контейнера и проверка состава образа описаны в [инструкции приёмки](../../../test/acceptance/README.md#управляемый-прогон-собранного-приложения).

`FACADE_HARNESS_PROFILE` — объект `{ A, B, lead }` с полями `routeId, model, dataClass, maxTokens, maxTurns, maxKnownRejections` и опциональным `toolChoice` (`required` по умолчанию). A и B требуют разных моделей и маршрутов. Значение `FACADE_GATEWAY_LIVE_MODE=step-15` открывает конфигурацию живого шлюза только при наличии отдельного журнала, ключа в `FACADE_GATEWAY_OPENROUTER_KEY` и разрешённых профилей в `FACADE_GATEWAY_STEP15_PROFILES`. Это условие запуска, разрешения и бюджет модели проверяет gateway. Строгая политика по умолчанию `FACADE_HARNESS_LIVE_POLICY=strict-zdr` требует ZDR для каждого маршрута. Режим `synthetic-research` требует синтетический класс для всех трёх маршрутов. Для Kimi обязателен ZDR. Wafer доступен через точный тег `wafer/us`. Decart доступен только для `moonshotai/kimi-k3.1-pro` через `decart/mxfp4` в `synthetic-research` с `toolChoice: "auto"`. Для Qwen в `synthetic-research` используется закреплённый Alibaba. В `FACADE_GATEWAY_STEP15_PROFILES` для каждого синтетического маршрута укажите `syntheticScopes: [{ projectId, scopeId, approvalRef, originalSha256s }]`. Для ведущего и перепроверки пара проходит тот же допуск по обоим оригиналам. Для архивных детей внесите каждый хэш отдельно. Имена политик и маршрутные поля совпадают с `OpenRouterProfile` шага 8. Ключ и настройки журнала остаются в окружении стенда.

Читатели получают отдельные контексты. Закреплённая опора с новой выдачей публикуется через штатный порт questions. Локальная постановка ведущего, карточка assessment и checkpoint записываются в одной транзакции. Поисковому модулю передаётся связь с вопросом. Спор виден сразу. Пара независимых оригиналов поступает ведущему до завершения несвязанных первичных задач. Шлюз проверяет актуальную пару на каждом вызове. Ведущий и обе проверки используют адресные цитаты об исполнении, редакции, применимости и сопоставимости. Неустановленный критерий остаётся открытым. После предложения две отдельные проверки с исходными профилями A/B заново открывают каждый оригинал. Отказ по конкретному месту, незавершённый вопрос и неоднозначные символы остаются видимыми ограничениями. После изменения локального предела ходов оператор возобновляет прежнее задание с его checkpoint. Готовность первичного прочтения означает завершение назначенного места, а решение инженера и выдача письма продолжают проверять собственные полномочия и удержания.

## Независимый допуск A/B · шаг 15

В `FACADE_HARNESS_PROFILE` указываются только доступные настройки `A`, `B` и `lead`. Например, для разрешённой B достаточно объекта `{ B: { routeId, model, dataClass, maxTokens, maxTurns, maxKnownRejections } }` и одного соответствующего действующего допуска в `FACADE_GATEWAY_STEP15_PROFILES`. Профили проверяются по слотам. Недоступный или испорченный соседний слот оставляет свою обязанность `pending` с причиной в очереди. При нуле допусков worker сохраняет работу с описью и формирует именованные удержания. При первом появлении допустимой конфигурации исходное задание получает устойчивую привязку к маршруту. Для уже связанных заданий сохраняются модель и маршрут, поэтому смена настроек требует согласованного нового назначения.

Шлюз отдельно проверяет разрешение проекта на каждый вызов. Отзыв переводит зависимую ветвь в `route_denied`. Сверка и письмо используют прежние условия полноты и проверок. Профиль Qwen с `maxImages=0` предназначен для допустимых текстовых входов. PNG остаётся за пределами этого допуска. После сборки примените миграции, включая `09_harness_z_route_bindings.sql`. Для проверки на двух изолированных тестовых БД используйте `FACADE_HARNESS_LIVE_STUB_TEST=1 node --test src/modules/harness/live-policy.integration.test.mjs`. Этот тест перехватывает внешний HTTP-вызов внутри процесса.

Для сравнения Kimi используйте два отдельных назначения с чистыми контекстами, одинаковым синтетическим входом, точными разрешениями шагов 8/15 и `toolChoice: "auto"` у обоих маршрутов. Режим `toolChoice` закрепляется вместе с заданием. Сохранённые настройки без этого поля означают `required`. Свободный ответ в `auto` сохраняется как ход модели, после чего harness просит продолжить через инструмент в пределах лимита ходов. Выполняются только вызовы из `message.tool_calls`. Их `id` связывает сохранённый ход, намерение и результат; утверждение можно открыть по ID наблюдения и связанной выдачи. ## Аргументы инструментов чтения

Договор составных опор и восстановления исследования описан в [контракте producer и downstream](../../../docs/implementation/compound-reader-contract.md).

Первичные A/B вызывают `survey` с `{}`. `zoom`, `extract`, `ocr` и `search` принимают только аргументы соответствующей операции. Исходник и место задаёт серверное назначение. Ведущий и перепроверка передают обязательный `support: "A" | "B"` для открытия одной из двух закреплённых опор. Ошибочный `support` в первичном задании получает ответ с указанием, как повторить вызов; документ при этом не открывается.

Новый ход уже начатого задания использует схему своей роли. Для сохранённых отказов в новом запросе добавляется инструкция под тем же `tool_call_id`. Журнал остаётся источником исходной истории. При конфликте с ID уже зарегистрированной попытки harness передаёт шлюзу прежний запрос с тем же ключом эффекта. Шлюз сверяет исходный хэш перед восстановлением ответа или допуском повторной отправки.

`save_observation` различает измерение, ограничение и утверждение о передаче в протоколе 2. Измерение требует `evidenceId`, дословную `quote`, находящееся в ней `value` и исходную `unit`. Текстовая единица подтверждается в строке самого значения, соседней ячейке единицы или заголовке его столбца в той же выдаче. Цитата и `lineId` относятся к одной строке. Визуальная цитата содержит значение и единицу, указывает `box` и обходится без `lineId`. Если значение или единица недоказуемы, передайте адресное `limitation` без числовых полей. `alternatives` допустимы вместе с `limitation`; контекстное измерение с ограничением сохраняется без квалификации. Аргументы подтверждают структуру наблюдения, а reader отдельно проверяет принадлежность выдачи заданию, рамку и дословную цитату.

`finish_reading` для PDF требует ранее полученный обзор. `covered` опирается на квалифицированное наблюдение, `unreadable` — на сохранённое ограничение, `no_match` — на осмотр с полученной выдачей и без наблюдений. `partial` продолжает то же место. Результат `no_match` описывает осмотр. Самостоятельное утверждение о непередаче подаётся по контракту ниже. Проверка спора принимает `supported` только с выдачами по обеим закреплённым опорам.

## Утверждение о передаче · шаги 5 и 15

В протоколе нового задания A/B `save_observation` принимает `{ evidenceId, lineId?, quote, sourceRole, box?, deliveryStatement: { status: "delivered" | "not_delivered", item, context?: { lineId, quote } } }`. Передавайте дословное утверждение целиком и дословное название предмета. Для описи используйте роль `inventory`. Контекст может цитировать дополнительную строку той же выдачи. У визуальной цитаты укажите рамку. Извлечённая строка, контекст и предмет проверяются по уже поданной ветви выдаче. Утверждение можно открыть по `GET /api/v1/observations/:id`, а строки и пиксели — по связанному `evidenceId`. Пустая выдача OCR, поиск без совпадений и `finish_reading(no_match)` сохраняют только исход обхода.

Для отрицательного утверждения harness публикует `finding.kind="absence"` и `nonDelivery: { kind: "explicit_non_delivery", subjectQuote, questionId, receiptId }` в `harness_observations.finding` и `applyAssessmentUpdate`. ID вопроса берётся из задания, ID поступления — из сохранённого адреса. Review содержит `researchGenerationId`. Положительное утверждение идёт как `kind="delivery"` с неизвестной применимостью до проверки фактически полученного оригинала. Assessment владеет квалификацией двух ветвей, применимости и альтернативных источников. Предмет может находиться в самой цитате или в дословной контекстной строке той же выдачи.

Новые первичные задания используют `observationProtocol: 2`. Уже поставленные задания продолжают прежний протокол с исходной схемой вызова. Старые наблюдения читаются и повторно закрепляются с прежним ключом операции. Новое поле опционально в том же JSON наблюдения. Адресный прогон вместе с обычной загрузкой на двух чистых БД запускается через `FACADE_HARNESS_INTEGRATION=1 FACADE_HARNESS_STATEMENTS_ONLY=1 node --test src/modules/harness/worker.integration.test.mjs`.

## Первичное чтение без каталога

Worker подхватывает принятые версии новых проектов `mode: "intake"`. Пакетная цель живёт отдельно от целей областей, повторное чтение описи, новые вопросы и редакции каталога сохраняют её идентичность. Планировщик берёт следующие A/B по очереди проектов, начиная с четырёх пар на проект и 48 пар суммарно. Карта хранит остаток независимо от выданных заданий. Обе ветви получают только собственное назначенное окно. Факты и продвижение журнала инструмента фиксируются в одной транзакции.

`readPackageAnalysis` принимает проект и транзакцию. Вызов требует предварительной серверной проверки проектного доступа. Пакетные опоры предъявляются через обычный адрес `/api/v1/evidence/:id` с проектным доступом. Изменение факта, карты или состояния задания публикует событие `package-analysis.changed` без содержимого опоры. Роль, стадия и редакция сохраняются с дословными основаниями. Адресная принадлежность хранит историю, команда инженера `POST /api/projects/:projectId/package-facts/:id/binding` принимает `{state, candidateIds, reason}` и текущую версию связи в `If-Match`. В текущем проекте связь может использовать явно напечатанный ID фасада или сочетание марки с напечатанными корпусом и осями. Простое совпадение марки остаётся отдельным адресным кандидатом.

Физическая граница подтверждается полной картой страниц PDF или сверкой карты с физической структурой оригинала поддерживаемого формата. Предметная граница требует совпавших независимых чтений действующей полной ведомости фасадов, отдельного подтверждения общих материалов и завершения обоих чтений окон. Остальные случаи сохраняют открытые границы. Вероятное расхождение по адресно связанной области и свойству поступает ведущему. Ведущий и обе проверяющие ветви могут открыть соседние окна только этих двух редакций. Проекция подтверждает пару после трёх совпавших сверок с повторным открытием обеих опор, явно действующими редакциями и совпавшим исполнением.

## Точечный переход существующего проекта

1. Зафиксировать сборку, текущие ID карт, работ и эффекты, состояние журнала и неизменяемых оригиналов. Остановить прежние процессы worker, чтобы они не выдавали задания по прежнему протоколу в момент перехода. API и рабочие данные сохраняются.
2. Применить добавочные миграции gateway и harness штатной командой `npm run migrate`.
3. Запустить новый worker с `FACADE_HARNESS_PACKAGE_PROJECTS=<uuid проекта>` и `FACADE_HARNESS_REPLAY_ONLY=1`. При нескольких отдельно согласованных проектах UUID указать через запятую. Использовать прежний внешний журнал с тем же ID, ключами маршрутов и утверждённым профилем, если нужны точные квитанции. Выбранный проект фиксируется до открытия первой карты. Повторный запуск с тем же UUID переиспользует его пакетную цель. Новый worker не отправляет модельные запросы и не обращается к провайдеру за поиском квитанций в режиме replay. Профиль без транспорта строит карты и сохраняет ожидание. Нужен записанный ответ на точный запрос для восстановления уже оплаченного хода.
4. Проверить `readPackageAnalysis`, историю прежних областей, оригиналы и журнал. Результаты с предыдущим предметным протоколом остаются по своим прежним адресам. При несовместимости первичного контракта оплаченное, подготовленное или неясное окно удерживается с указанием исходной работы. Смена профиля reader создаёт собственный остаток покрытия, сохраняя старые доказательства. Сверка неизвестного исхода выполняется отдельно с исходной попыткой.
5. Сборку с пакетными целями можно перевести в паузу через `FACADE_HARNESS_PACKAGE_PRIMARY=legacy` и `FACADE_HARNESS_REPLAY_ONLY=1`, сохраняя добавленную схему и данные. Для продолжения вернуться к совместимой сборке с пакетными целями. Старый бинарный worker, выпущенный до этих миграций, использовать только до появления пакетных записей.
6. Передача пакета моделям требует отдельного допуска. `FACADE_HARNESS_PACKAGE_EFFECTS=enabled` открывает только разрешённые работы с действующим профилем, подходящими грантами, авторизованными исходниками и журналом. На пассивном стенде переменная выключена.

Сквозная синтетическая проверка запускается через `FACADE_PACKAGE_INTEGRATION=1 node --test src/modules/harness/package-worker.integration.test.mjs` после сборки, штатных миграций тестовой БД с именем `test_*` и подключения отдельного пустого журнала и изолированного бакета. Значение `walk` запускает только адресный обход и дочитывание каталога, `legacy` — прежний маршрут и переход существующей очереди. Проверка поднимает локальный HTTP-транспорт с нулевой стоимостью квитанций.

## Адресный обход пакета

`FACADE_HARNESS_PACKAGE_WALK=1` задаёт новый контракт для первичных работ, созданных после запуска worker. Уже назначенные работы продолжаются в закреплённом контракте. Новый пакет поступает через обычную загрузку. Worker по очереди строит карту, индексирует оригиналы и готовит структуру окна. Эти локальные операции делят общий тяжёлый слот.

- `context_inventory` и `open_context` предъявляют выбранные соседние окна той же принятой версии. `save_compound_observation` принимает отдельно закреплённые фрагменты и `package.references` с индексами компонентов для атрибута, роли, стадии, редакции и принадлежности. Нечисловое значение может иметь составную опору без единицы. Для сравнения разных ролей требуются явно опубликованное правило каталога, совпавшая функция значения, стадия и равный приоритет.
- `inspect_structure` перечисляет блоки порциями. `record_blocks` связывает рассмотренный блок с представлением, реально выданным этой ветви. Агент выбирает области и масштаб. Команда `finish_reading` фиксирует исход сеанса. Остаток блоков и `semanticChecks` — самостоятельные проекции.
- При пропусках обеих ветвей или совпавшем отсутствии кандидатов worker ставит отдельное дочитывание. Следующее структурное задание получает оставшиеся блоки после появления хотя бы одной новой принятой квитанции. Повторы без прогресса остаются видимым остатком. Квитанция может опираться на совместимые проверки той же ветви и карты из нескольких заданий. Задание по каталогу берет до трёх позиций. В текущей версии применимости очередь переходит к ещё не назначенным позициям, а назначенные позиции без квитанции остаются открытыми. Смена каталога, стадии или привязки позволяет поставить новое адресное задание.
- Первичный предел ходов даёт одну версионируемую остановку с последним запросом. Инженер продолжает через штатный `research-stops/:id/resume` с `If-Match`. Дополнение ограничено четырьмя ходами, дочитывание ограничено восемью ходами на одно задание. Идентичность запроса остаётся закреплена журналом. Состояния `sending` и `unknown` ожидают учётной сверки.

Для разрешённого живого чтения оператор подключает существующий профиль Step 15, соответствующие гранты, внешний журнал и квалифицированные маршруты. Допуск пакетных внешних эффектов задаёт `FACADE_HARNESS_PACKAGE_EFFECTS=enabled`. Пассивное воспроизведение использует `FACADE_HARNESS_REPLAY_ONLY=1`. Помощник использует отдельный `FACADE_COPILOT_PROFILE` с полями `routeId`, `model`, `dataClass`, `maxTokens` и необязательным `toolChoice`. Он делит тот же шлюз, журнал и разрешения. Исполняемый имитатор находится в тестовом каталоге.
