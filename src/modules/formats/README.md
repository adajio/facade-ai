# Reader форматов · шаг 11

Единая точка интеграции — reader шага 4. Шаг 11 экспортирует `createFormatAdapters()` из
`src/modules/formats/index.ts`. Выбор адаптера производится по расширению исходного имени
без учёта регистра; адаптер `unknown` выдаёт исход «только оригинал». PDF обслуживает шаг 4.
Сервис передаёт адаптеру уже проверенный временный файл конкретной версии. Продолжение,
учёт фактической доставки, закрепление и HTTP просмотра идут через тот же reader, что и PDF.
Регистрация маршрутов и запись квитанций принадлежат общему reader.

### Независимая сверка физических мест

Профиль `formats-1.1.3` сопоставляет адреса карты с физическим перечнем оригинала.
Для XLSX он проверяет состав объявленных листов, записанные строки, ячейки и
объединения. Для DOCX он проверяет абзацы основного текста, таблицы с их
строками и ячейками, а также абзацы поддерживаемых вспомогательных частей.
Для TXT, CSV и TSV он сверяет физические строки, включая пустые. Для
текстового DXF он сверяет пространства и записи сущностей по handle или
порядковому номеру. Проверка охватывает только графику, представимую штатным
адаптером. Непредставимая графика и структура дают код ограничения, сохраняя
доступные места. Кэш формулы XLSX может быть непроверенным при проверенных
физических адресах.

Reader сохраняет свидетельство в карте конкретной версии. `verifyPhysicalInventory(map)`
повторно проверяет SHA-256, профиль и весь список адресов. Выданный `basisId`
воспроизводится по сохранённой карте этой версии. У старых карт без
свидетельства остаётся ограничение до сверки под новым профилем. Границы
предметного вывода и завершённость чтения A/B оцениваются отдельно.

Для DOC, XLS и DWG разметка конвертера описывает производную. Для IFC
доступны адреса STEP при ограничении по геометрии. Самостоятельные растровые
изображения доступны как оригинал с кодом `image_reader_unsupported`.

Для шага 9. Обходить каждую единицу карты, включая пустые и удержанные. Использовать
`unitId` и выбранный `locator`; для подтверждения указывать ID квитанции фактической выдачи.
Отсутствие представления или частичный охват остаются внутренним ограничением. Сначала фиксируется обязанность обхода, затем выдаются совпадения поиска. Карта и цитаты другой ветви закрыты до завершения первичного чтения.

Для шага 13. Использовать маршруты `/api/v1/.../reader/units` и `/api/v1/evidence/:id[/content]`
из [контракта шага 4](../pdf/README.md). Показывать физическую единицу и поля адреса исходного
формата из `locator`. Ссылка «Оригинал» относится к `documentId` и `versionId` квитанции.
Адрес старого DOC/XLS/DWG уточняет место в производной, связанной с оригиналом. SHA-256
представления и закреплённая квитанция позволяют проверить его после перезапуска.

### Вход адресного инструмента worker

В `ReadRequest.address.locator` передаются поля выбранного места, перечисленные ниже. Только `unitId` читает окно целиком. При выборе CAD-объекта `render` возвращает PNG с окружением, `native` возвращает точную строку. Для XLSX, DOCX, TXT и IFC обзор делается как `native`. `ocr` относится к PDF. Поля `coverage`, `candidateCount` и `limitations` доступны в карте; `held` и `original_only` требуют учёта по месту без модельного запроса. Пустая пригодная единица сохраняет обязанность обхода.

| Формат | Поля выбранного места |
| --- | --- |
| DOCX/DOC | `paragraph` либо `table, row, column`; у строки может быть путь `section` |
| XLSX/XLS | `sheet, cell` (например, `C3`) либо `sheet, range` (например, `A1:C4` в одном окне) |
| TXT/CSV/TSV | `line` с 1 |
| DXF | `space, handle`, при выборе именованного вида `view`, при геометрическом открытии также `box` |
| DWG | `space, derivativeHandle` при доступной конвертации |
| IFC | `step` (например, `#42`), при наличии `globalId` |
| RVT, неизвестный | `unitId: "original"`, исходный оригинал и код причины |

Для выбора через Mastra порт шага 9 должен передать JSON-объект `locator` от инструмента в
`service.open(… { address: { unitId, box, locator } })`. Область, версия и SHA берутся из
назначения; locator проверяется адаптером. При чтении целого окна строка возвращает собственные
`locator` и `id`. Для двух буквально одинаковых цитат при записи передаётся `lineId`. Для
проверки сохранённой опоры публикуется эффективный `evidence.address.locator` и адрес строки из
`observation.address.locator`.

### Конвертация и развёртывание

DOC, XLS и DWG используют [порт конвертеров](../converter-port/README.md).
В worker передаётся путь к Unix-сокету через `FACADE_CONVERTER_SOCKET`.
Владелец стенда закрепляет образ `office` или DWG-обёртку
[oda.Dockerfile](oda.Dockerfile) в брокере. Штатный DWG-профиль использует
ODA File Converter 27.10. Поставка монтируется в контейнер только для
чтения из закрытого каталога владельца. DOC и XLS сохраняют вход и результат до 16 МиБ, 512 МиБ RAM
и 35 с на конвертацию. DWG использует потоковый вход до 10 ГиБ поступления
и дисковую производную с бюджетом свободного места. Изолированный профиль
DWG по умолчанию допускает 1536 МиБ RAM и 420 с. ODA запрашивает
текстовый DXF R2013 с audit=0 и recursion=0. Явный профиль
`FACADE_DWG_ENGINE=libredwg` использует прежний образ, режим R2013 для AC1027
и восстановление JSON при неполном DXF. Одноразовый `/tmp` конвертера
остаётся 96 МиБ. Контейнер получает один вход только для чтения.

Приложение связывает ID образа и SHA-256 производной с выданным представлением.
DWG reader версии `formats-1.1.4` обходит DXF потоком. Каждая сущность
`ENTITIES` входит в одну основную часть. Часть ограничена 512 строками,
6000 фигурами и 2 МиБ проекции строк. ID одиночного пространства сохраняется.
Части многосоставного пространства различаются порядковым суффиксом.
Именованные виды используют наложение на части Model. При совпадающих
handle строка получает глобальный `entityOrdinal`. Хэш DXF и хэш части
закреплены в карте. Ограничения неподдерживаемых сущностей сохраняются
в их строках. Метки `derivativeHandle` и `cad_converted_handle_unverified`
по-прежнему относятся к производной.

Worker атомарно публикует закрытый SQLite-индекс под
`FACADE_DATA_DIR/dwg-index`. API и worker на одной установке используют
этот каталог совместно. Перед выдачей проверяются право на проект и
версию оригинала, существование оригинала в хранилище, версия карты и
SHA-256 частей. Временные сборки очищаются при завершении работы.
Опубликованные индексы остаются в закрытых данных установки. Если индекс
пропал, reader повторяет конвертацию на проверенном оригинале. Другая
производная даёт `dwg_index_identity_changed` до публикации. Повреждение
индекса даёт `dwg_index_invalid`. Для повтора оператор закрывает процессы,
уводит конкретный повреждённый файл индекса из рабочего каталога и вновь
открывает часть. Оставшиеся после аварии каталоги `.dwg-*` можно убрать
после остановки процессов. Без рабочего постоянного каталога пакет
чтения использует один временный индекс и один проход конвертации.

Смена образа или закреплённой поставки ODA применяется после перезапуска
брокера и reader. Новый вызов `map` строит
карту того же оригинала под новым `readerVersion`. Запрос live-открытия с
прежней версией получает `409 reader_profile_changed`. Для нового чтения
требуется карта нового профиля и повторное закрепление опор. Сохранённые
карты и уже записанные доказательства принадлежат своим версиям.

- LibreOffice поставляется по MPL 2.0, новый код проекта доступен также по LGPL 3.0+. [Условия проекта](https://www.libreoffice.org/licenses/).
- GNU LibreDWG поставляется по GPLv3+. Dockerfile закрепляет SHA-256 бинарного архива, а манифест сборки указывает архив исходников. [GNU LibreDWG](https://www.gnu.org/software/libredwg/manual/html_node/Overview.html).

### Готовый вход для стенда шага 14 · DWG

`dwg` упаковывает тот же проверенный JLL-бинарник GNU LibreDWG 0.13.4+0
с glibc. ARM64 и AMD64 имеют отдельные закреплённые SHA-256, а упаковка
выбирает один архив для целевой архитектуры. В образ входят `dwg2dxf`,
его библиотека и текст GPLv3+. [Манифест JLL](https://raw.githubusercontent.com/JuliaBinaryWrappers/LibreDWG_jll.jl/LibreDWG-v0.13.4%2B0/Artifacts.toml) ·
[Исходник и рецепт сборки JLL](https://github.com/JuliaBinaryWrappers/LibreDWG_jll.jl/tree/LibreDWG-v0.13.4%2B0).

Команды для владельца [стенда](../../../infra/test-stand/README.md) в Docker-контексте OrbStack
на внешнем SSD. На Mac ARM64 явно выбран `linux/arm64`. Для будущего x86-64
профиля подставляется `linux/amd64`.

```bash
docker --context orbstack build --platform linux/arm64 --target dwg \
  --tag facade-ai-dwg:0.13.4-jll src/modules/formats
dwg_image_id="$(docker --context orbstack image inspect --format '{{.Id}}' facade-ai-dwg:0.13.4-jll)"
docker --context orbstack run --rm --pull=never --network=none --read-only \
  "$dwg_image_id" version-dwg
```

Передайте `dwg_image_id` в `FACADE_DWG_IMAGE` брокера шага 14, подключите его
Unix-сокет к worker и перезапустите worker. В новую синтетическую область
загрузите [schedule.dwg](test/fixtures/schedule.dwg) обычным API или через
интерфейс. Ожидаются две физические единицы Model и Paper и два независимых
чтения Model. Контроль Model — B и C с разными составами и одинаковым
итогом 70 mm. При чтении B исходный путь доступен через `versionId`, адрес
производной — `space: Model, derivativeHandle: 2E`. Открытие возвращает
`cad_converted_handle_unverified` и карту подстановки шрифта для этой фикстуры.
Управляемый маршрут можно контролировать по выдаче с типом
`application/json` и закреплённому PNG. Проверяйте назначенные места и
фактическую выдачу с исходным SHA-256, затем карточку. У запуска с
недоступным образом ожидается адресное удержание `dwg_converter_unavailable`.

### Адресная диагностика после слепого прогона

Поддержка DOC, DWG и DXF в `formats-1.1.1` сохраняет таблицу старого DOC при
провале обычного импорта, текст DWG при обрыве DXF-экспорта и CAD-объекты
без подтверждённых handle. Для DXF запасной селектор — `entityOrdinal`
(номер записи в исходной секции `ENTITIES`, с 1). У DWG аналогичный
селектор относится к производной. При восстановлении DWG через JSON
у единицы `derivative: dwg-json`, подтверждённый адрес выдачи сохраняется
как `derivativeHandle`. [Поиск причины и адресные проверки](test/postblind-201dc93.md).

### Шрифты схемы DWG

`FACADE_DWG_FONT_DIR` задаёт отдельный каталог лицензированных файлов `.ttf` и
Unicode SHX `AutoCAD-86 unifont 1.0`. Монтируйте его только для чтения в worker и
API с одинаковым содержимым. Установка шрифтов в систему и в образ не нужна.
Индекс и версия reader закрепляют SHA-256 набора. После изменения набора
перезапустите оба процесса и постройте актуальную карту. Сохранённые доказательства
читаются по своей версии.

Чтение использует плоский каталог одобренных оператором файлов. Имена DWG/DXF
участвуют в выборе зарегистрированного файла или начертания. Символические ссылки
и неоднозначные TTF-начертания отклоняются. В native-открытии поле `details.fonts`
содержит SHA-256 применимых файлов и отмечает подстановку. Для вставки список
охватывает подписи её достижимых определений. Масштаб текущего окна влияет на
видимость подписи. Кнопка «Приблизить подпись» запрашивает PNG для выбранного
адреса и SHA-256 шрифта. Обзор сохраняет часть, адрес и порядок отрисовки.
Big Font и SHX-наборы фигур требуют отдельного профиля.
