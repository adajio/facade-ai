## Реальный исход карточки и D9

Первый запуск сохранил обе опоры и четыре завершённые обязанности.
Ожидание `covered` из прежнего теста разошлось с результатом
`needs_review / review_incomplete`. Запись первого опыта сохранена.
Срез БД показывает для обеих строк `subjectVerified=false`,
`applicability=unknown`, роль `design`, действующую редакцию и
закрытую генерацию. В точной строке с итогом `70 mm` источник не
связывает значение с общим требованием `Panel schedule`.
`questions/subject-evidence.ts` проверяет адресную привязку атрибута.
`assessment/domain.ts` удерживает вывод при неизвестной применимости.
Причина этого удержания установлена независимо от отметки о handle.

В повторе штатные маршруты managed lead, A и B разрешены для цели
`review`. Выдано 4 первичных задания и 0 review-заданий.
У двух опор один исходный SHA-256, одна версия, один адрес и одно
значение. В текущем коде спор формируется из активных несовпадающих
опор, а независимость дополнительно требует разных версий и SHA-256.
Роли D9 на этой паре закономерно остались без назначения. Для
положительного контроля нужны две действующие независимые опоры
одного исполнения и атрибута с проверенной областью, редакциями,
единицами и различным значением. После штатного назначения ведущий
и обе перепроверки должны независимо открыть обе опоры, а затем
подтвердить одинаковое доказательство сопоставимости. Локальный
браузерный опыт показал 0 допустимых пунктов письма.

## Предварительная заморозка обычного зачёта

D10 закрепляет РД и один тип НВФ, выбираемый по доступным обычным
пакетам и инженеру, утверждающему требования. В проверенных источниках
проектной записи и доступных протоколах выбор типа и разрешение на
четыре обычных пакета не подтверждены. `corpus.json` содержит
синтетику. Архив слепых проверок содержит раскрытый синтетический
пакет, а записи ручного пилота и ёмкости описывают исторические опыты
на иных входах. Клиентские оригиналы не извлекались из хранилищ.
[Исторический замер реального пакета](../../../../../docs/v1.1/capacity.md) ·
[Слепой синтетический прогон](../../../../../docs/implementation/live-blind-run.md)

До открытия результатов для каждого файла требуется запись со
следующими данными:

- Допуск, пакет, стадия РД, утверждённый тип, фасад, область и
  инженер-оценщик. Размер, SHA-256, версия DWG, роль, редакция и
  источники XREF с хэшами, путями и принадлежностью к комплекту.
- Для каждого факта — обязательность, критичность D4, утверждение,
  значение, исходная единица, марка, исполнение, применимость,
  точная цитата и адрес в оригинале. Лист, пространство, слой,
  объект/блок/видовой экран и способ независимой сверки адреса.
- Для D9 — ожидаемая сопоставимость, основание сравнения и
  корректный переход к ведущему/двум независимым перепроверкам.
  Для письма — обязательные пункты и исходы, при которых письмо
  удерживается. Для ограничений — ожидаемая причина, сохранность
  оригинала и способ адресного повтора.
- До конвертации зафиксировать знаменатель для каждого формата,
  пакета и ветви. Считать попадание только при верной цитате,
  адресе и контексте оригинала. По D6 требуется минимум 85% по каждому
  из PDF/XLSX/DWG, все критичные опоры DWG, ноль ложных и пропущенных
  обязательных пунктов письма. Удержанные и непрочитанные места
  остаются в знаменателе. Для сканов отдельный зачёт.

В отдельном [парном опыте Linux x86-64](paired-linux-x64.md) восемь
синтетических входов проверены обоими конвертерами. Для обычного
корпуса нужны его хэш-пинованные файлы, согласованная разметка,
разрешение на обработку и повтор на целевой установке.
Согласование тяжёлого слота требуется после внешнего S3/PG для
целевой установки и ресурсных измерений согласованного корпуса.
Текущий синтетический опыт не даёт оценки D6 и итогового выбора.

## Воспроизведение и локальные доказательства

Для браузерного теста нужны сборки `npm run build:server` и
`npm run build:web`, Chrome, новый локальный PostgreSQL с отдельными
приложением и журналом. Выполнить `npm run migrate` для приложения,
применить `src/modules/gateway/journal.sql` к журналу, создать
закреплённый `gateway_external_ledger` и запечатать обе БД скриптом
`test/fixtures/provision-managed-test.mjs`. Процедура использует
`DATABASE_URL`, `FACADE_GATEWAY_JOURNAL_URL`,
`FACADE_MANAGED_TEST_RUN_ID` и `FACADE_GATEWAY_LEDGER_ID`.
Путь вывода и каталог данных — новые отдельные каталоги на SSD.
API и HTTP-имитаторы слушают только loopback.

```sh
FACADE_DWG_CARD=1 FACADE_DWG_CARD_OUTPUT="$out" \
FACADE_DWG_REFERENCE_DXF="$schedule_dxf" FACADE_DATA_DIR="$out/data" \
HOST=127.0.0.1 PORT=18479 node --test src/modules/formats/test/dwg-d4/card.test.mjs
```

В режиме без `FACADE_DWG_REFERENCE_DXF` требуется выделенный штатный
Unix-брокер с тем же готовым образом. Локальный прогон использовал
`schedule.dxf` с закреплённым хэшем
`2b925bb26c32b15237eebac4612e54efe0bacd091d79fc3b2346cb3dbafac47f`.
Логи, HTTP-трасса, сохранённый первый вывод, браузерные снимки и
итоговый JSON находятся в `.local/w34-cont`; первая стадия порта
и Linux-производные — в `.local/w34`. Внешний расход — 0.
