# D4 · начальная квалификация DWG

База Facade AI — `e35fdde989147ec8b87dabda9722b895eb826d2e`. Проверка использует
синтетические оригиналы в [манифесте](corpus.json). Каждое плечо получает
файл с тем же SHA-256. Сборки приложения и порта остаются профилем 1.1.
Условия применения ODA вынесены в [лицензионную запись](oda-terms.md).
Продолжение сквозной квалификации, границы D6 и D9 — в [паспорте DWG](pasport-dwg.md).
Результаты восьми пар, диагностики и контроля ODA — в [протоколе Linux x86-64](paired-linux-x64.md).

## Подготовка пары

Из корня репозитория, в отдельном рабочем дереве:

```sh
npm run build:server
mkdir -p .local/d4
node src/modules/formats/test/dwg-d4/pair.mjs "$PWD/.local/d4/pair"
```

Сценарий создаёт новые входные каталоги с одним `original.dwg` и пустой
выходной каталог на файл. `pair-plan.json` хранит размер, сигнатуру,
SHA-256 обеих копий и подготовленные поля CLI. Поля описаны ODA, позиционный
синтаксис и значение `ACAD2000` требуют сверки с разрешённым точным пакетом.
Подготовка проверяет файлы на диске и оставляет статус `not_run`.
Для штатного LibreDWG проверка ниже использует те же закреплённые байты.
[Описание CLI ODA](https://www.opendesign.com/guestfiles/oda_file_converter)

## Потоковый предел порта

```sh
npm run build:server
node --test src/modules/formats/test/dwg-d4/limits.test.mjs
```

Настоящие DWG-адаптер, порт и брокер обмениваются по отдельному Unix-сокету.
Управляемый Docker CLI выдаёт валидный DXF. Проверка принимает по
16 777 217 байт на каждой стороне и открывает запись с адресом производной.
Отдельные случаи проверяют незавершённый ответ, отсутствие файла, отказ
по диску, точный размер входа, отмену выдачи, повтор и уборку scratch.
Работу Linux-конвертера на реальных DWG проверяет отдельный прогон.

## LibreDWG через штатный порт

В `dwg_image` передайте локальный образ из цели `dwg` текущего Dockerfile с выходом в `/out/derivative`. Команды ниже
поднимают отдельный DWG-брокер на хосте. Для виртуального Docker путь scratch
должен быть виден Docker. Способ открытия и восстановления сокета описан
в [порте конвертеров](../../../converter-port/README.md).

```sh
export FACADE_DWG_ENGINE=libredwg
export FACADE_DWG_IMAGE="$(docker image inspect "$dwg_image" --format '{{.Id}}')"
export FACADE_CONVERTER_SCRATCH="$PWD/.local/d4"
socket_dir="$(mktemp -d /tmp/facade-d4.XXXXXXXX)"
export FACADE_CONVERTER_SOCKET="$socket_dir/b.sock"
node infra/converters/broker.mjs
```

В другом терминале с теми же `FACADE_DWG_IMAGE` и `FACADE_CONVERTER_SOCKET`
после `converter broker ready`:

```sh
node infra/converters/smoke.mjs dwg
node src/modules/formats/test/dwg-d4/live.mjs "$PWD/.local/d4/libredwg-live"
FACADE_STEP11_DWG=1 FACADE_STEP11_RECOVERY=1 node --test src/modules/formats/test/adapters.test.mjs
```

Профиль `live.mjs` сверяет полноту ASCII DXF, обе строки 70 mm, частичное
восстановление текстовой строки через JSON и отказ для неверной сигнатуры.
Для XREF проверяются флаг блока 4, имя `xref-target.dwg`, собственный текст
хоста и отсутствие текста дочерних оригиналов в его производной. Варианты
имеют один SHA-256 хоста и одинаковое имя ссылки. Вход хоста передаётся
штатным потоком порта с одним файлом.

| Состояние рядом с хостом | Контроль оригинала ссылки | Проверка при будущем разрешении XREF |
| --- | --- | --- |
| Цель отсутствует | Собственная опора хоста — `70 mm` | Удержать опору, зависящую от ссылки |
| Принятая редакция из комплекта | `42 mm`, модель, размещение INSERT (25, 40) | Подтвердить связь с обеими версиями, исходным SHA-256 и преобразованным местом |
| Устаревшая редакция с тем же именем | `41 mm` | Удержать зависимую опору по несовпадению редакции или SHA-256 |
| Чужой файл с тем же именем | `99 mm` | Удержать зависимую опору по отсутствию допуска в манифесте |

Нынешний контейнер брокера получает только хост. Наличие соседнего файла
на машине вызова не меняет вход операции. Этот контроль характеризует
изоляцию порта. Проверка разрешения ссылки по манифесту требует реализации
передачи принятых редакций. Генератор [синтетики XREF](generate-xref.c)
использует LibreDWG 0.14 Write API и R2000. Для повторения опыта используйте
закреплённые DWG. Новая генерация требует нового манифеста хэшей.

Для отдельной локализации с тем же Linux-бинарником `linux-reference.sh`
запускает все маленькие входы в одном временном контейнере. Смонтируйте
`test/fixtures` на `/baseline`, `test/dwg-d4/fixtures` на `/fixtures` и сам
скрипт на `/reference.sh`, всё с доступом только на чтение. Запускайте
`--entrypoint /bin/sh` с аргументом `/reference.sh` из того же образа,
без сети, c приватным tmpfs `/tmp`. Выход — tar производных на stdout,
диагностика на stderr. Это измерение поведения утилиты.

## Сравнение после допуска ODA

На одном Linux x86-64 закрепите пакеты и версии обоих кандидатов, образ
среды, шрифты, лимиты, SHA-256 входов и свободное место. Используйте
ASCII DXF R2000 (`AC1015`) в обеих ветках. В LibreDWG вручную укажите
`dwg2dxf --as r2000 -o <output.dxf> <libreInput>`. В ODA используйте
поля `odaArgs` после проверки синтаксиса версии, аудит и рекурсия выключены.
В базовом парном опыте входные каталоги содержат по одному оригиналу.
Варианты XREF с наличием соседнего файла запускайте как отдельный опыт,
с закрытым списком разрешённых входов. Восстановление LibreDWG через JSON
и ODA с audit учитываются в отдельных опытах.

Для обоих выходов на одном входе:

```sh
node src/modules/formats/test/dwg-d4/probe-pair.mjs \
  .local/d4/pair/pair-plan.json schedule "$libre_output" "$oda_output"
```

Проверка повторно сверяет хэши входов, проверяет `AC1015`, целостность
до `EOF` и открывает оба выхода парсером Facade AI. Она выводит листы,
строки, геометрию, границы, адреса производной и ограничения. Отдельно
записывайте исход процесса, stderr, размеры, время и peak RSS/cgroup.
Обрыв или JSON учитываются в соответствующей ветке со своим видом
выхода и причиной. Адреса сверяются с замороженной разметкой оригинала,
включая видовые экраны, блоки, единицы, SHX и кириллицу. Полная проверка
обычного корпуса, порогов D4/D6 и пути до карточки требует разметки и
разрешённого парного прогона.

## Локальный результат 24.11.2026

- Штатный smoke с LibreDWG 0.13.4 Linux ARM64 подтвердил выдачу DXF для
  `schedule.dwg`, проверку идентичности образа и отказ для неверной сигнатуры.
  SHA-256 скрипта в образе совпал с исходником
  `113b3789d4f597ca0d8be7c9497f1be581aa5520e8a3b1a80f4a9b6c4195b88e`.
- На точной границе успешно прошли обе операции с 16 777 216 байтами.
  Превышение на один байт дало ожидаемые коды. Следующий запрос прошёл.
  Штатный `readInput` отдельно вернул `format_input_limit` при 16 777 217 байтах.
- XREF-хост прошёл через штатный Linux-брокер. SHA-256 его 13 256 байт DXF —
  `4cbf6505e76a66915f5dcbe503e7cef66367a7a681060984e5ec25a52973d65c`.
  Прямой запуск того же бинарника выдал этот же хэш для всех четырёх
  условий. Дочерние DWG, открытые отдельно, дали контрольные 42, 41 и
  99 mm. Экспортер сообщил о предупреждениях чтения синтетических
  XREF-файлов. Reader при повторе записанных DXF-байтов вернул частичную
  выдачу: `W34 HOST | 70 mm`, Model, `derivativeHandle: 2C`,
  `cad_external_reference`, без дочерних строк.
- Для файла восстановления прямой `dwg2dxf` завершился с кодом 0 и выдал
  6195 байт без `EOF`. Штатный Linux-брокер с тем же оригиналом вернул
  10 935 байт JSON, SHA-256
  `dfa012b55a356b55959174ee46f5dd13e787962766e077f923c78093bb533957`,
  побайтно совпавшие с прямым выводом `dwgread`. Reader при повторе подтвердил `Rib L2 | 13.25 mm` с производным адресом и
  `cad_dwg_json_recovery`. Тесты DWG-адаптера прошли 2 из 2 на сохранённых
  байтах Linux. Базовый тест адаптеров прошёл 10 из 10 применимых
  сценариев, четыре опциональных legacy-сценария отключены в том запуске.
- Подготовлены семь пар входов с одинаковыми SHA-256. Калибровка общего
  DXF-пробника дала Model и Paper для одного эталонного DXF на обеих
  позициях и отвергла усечённый контроль. Фактический запуск ODA ожидает
  установления лицензионных условий.

Два расширенных прогона через брокер с Mac завершились на таймауте
`docker container create`. Оставшиеся контейнеры проверены по метке
своих брокеров и удалены. Отдельный Linux-запуск и повтор производных
дают приведённые адресные результаты. Артефакты с логами, хэшами и
выходами собраны локально в `.local/w34` этого рабочего дерева.

## OOM и повтор в брокере Linux

Соберите синтетический образ на уже доступном Linux-образе Node.js 24+.
Добавьте в корень образа [follow-up-dwg.mjs](../../../../../infra/test-stand/follow-up-dwg.mjs)
и настройте `ENTRYPOINT ["node", "/follow-up-dwg.mjs"]`. Для отдельного
экземпляра брокера закрепите этот DWG-образ, образ архивного распаковщика
и установите `FACADE_DWG_ENGINE=libredwg` и `FACADE_DWG_MEMORY_MIB=128`. Фикстура `AC1015!` заполняет память
до завершения контейнера по OOM. Следующая фикстура публикует целый DXF в
`/out/derivative`.

В клиентском контейнере с собранным `/app/dist` и сокетом этого брокера
запустите [follow-up-limits.mjs](../../../../../infra/test-stand/follow-up-limits.mjs).
По пути `/run/fixture.zip` передайте ZIP с одним файлом `fixture.bin` из
262 144 байт значения `0x42`. Проверка подтверждает лимит раскрытия архива,
перевод OOM в `memory_limit` и успешный повтор работы с DWG.
