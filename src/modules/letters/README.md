# Письма · шаг 6 v1.1

HTTP под `/api`; те же операции доступны под `/api/v1`. UUID обозначают проект, область, вопрос, решение, письмо, редакцию, экспорт и отправку. Версия письма — положительное целое, начинается с 1. Для `If-Match` используется ETag вида `"1"`. Списки поддерживают `limit` и `cursor`. Для членства с ограниченной областью укажите `scopeId`.

## Контракт для шага 13

| Метод и путь | Вход и результат |
|---|---|
| GET /projects/:projectId/letters/eligible?scopeId=…&recipient=… | `{ items, holds }`. Фильтр `recipient` необязателен. Пункт содержит `questionId, questionVersion, decisionId, recipient, scopeId, kind, subject, action, sources, basis, wording, alternativeWording`. |
| GET /projects/:projectId/letters?scopeId=… | `{ items, nextCursor }`, сводки `{ id, projectId, scopeId, number, version, revisionId, recipient, status, createdAt }`. |
| POST /projects/:projectId/letters | `{ scopeId, recipient, items: [{ questionId, questionVersion, decisionId }] }`. Массив задаёт порядок. Пустой список либо выбор из одних недопустимых вопросов → 422 `no_eligible_items`. Успех → 201, сводка. |
| GET /letters/:letterId | Сводка и `revisions`, `sent`, `responses`, `exports`. Для редактора служит `revisionId`, допустимость актуального текста устанавливает отдельный запрос. |
| GET /letters/:letterId/revisions/:revisionId | Явная сохранённая редакция. `{ historical: true, id, version, status, recipient, layout, items, text, textSha256, createdAt }`. Непроверенный черновик доступен инженеру. |
| PATCH /letters/:letterId | `{ layout?, recipient?, items?: [{ questionId, wording }] }`; массив изменяет указанные пункты, `wording: null` возвращает формулировку из основания. `If-Match`. Любая свободная правка становится черновиком, пока не подтверждена. |
| POST /letters/:letterId/confirm | `{ items: [{ questionId, questionVersion, decisionId }] }` для всего состава. `If-Match`. Для авторского текста элемент содержит `review` по контракту ниже. |
| GET /letters/:letterId/current-text | `If-Match` версии, `{ revisionId, version, text, textSha256 }` для предпросмотра и копирования. |
| POST /letters/:letterId/exports | `{ format: "txt" \| "docx" }`, `If-Match`. Возвращает `{ id, revisionId, version, format, url, historicalUrl }`. |
| GET /letters/:letterId/exports/:exportId | Текущие байты. Сервер повторно проверяет допуск исходной редакции даже по старому URL. |
| GET /letters/:letterId/revisions/:revisionId/exports/:exportId | Сохранённые байты. Заголовок `X-Letter-Historical: true`. |
| POST /letters/:letterId/sent | `{ revisionId, itemIds, recipient, text, sentAt }`. Требуется сохранённая подтверждённая редакция. `itemIds` — непустой поднабор `id` её пунктов в порядке отправки. `sentAt` — ISO 8601 с поясом. |
| GET /letters/:letterId/sent/:sentId | Снимок отправки с основаниями, текстом и временем регистрации. |
| GET /letters/:letterId/responses/:responseId | Адрес записи ответа или отказа. |
| POST /letters/:letterId/responses | `{ sentId, itemId, kind: "response" \| "refusal", text, receivedAt }` для пункта отправленного снимка. Регистрация ответа сама не закрывает инженерный вопрос. |

Мутации передают CSRF и `Idempotency-Key`. Повтор возвращает квитанцию после проверки прав, один ключ с другим запросом даёт 409. Текст и байты запрашиваются отдельно с новой проверкой. Новые операции со старой версией получают 412. Все ответы `no-store`. Возможные статусы редакции — `confirmed`, `draft`. Шаблоны `formal` и `brief` меняют оформление. Пока черновик не подтверждён, его текст доступен через маршрут редакции, текущая выдача возвращает 422 `letter_unconfirmed`. При удержании текущие команды возвращают 409 `scope_held`; при изменении инженерного основания — 412 `letter_basis_stale`. Новую версию из изменившегося состава создаёт новая команда формирования. Старые подтверждённые редакции, экспорт и отправка остаются адресуемыми.

## Проверка авторского текста для интерфейса

1. Сохраните `wording` через PATCH. Загрузите сохранённую редакцию и используйте `editedWording` и `wordingSha256` из её пункта. `wording: null` возвращает основную формулировку.
2. Покажите актуальный пункт из `GET /projects/:projectId/letters/eligible` рядом с редактором. Область, предмет и действие берутся из `basis.scope.name`, `subject` и `action`. Для каждого `source` покажите `label`, исходные `address.value` и `address.unit`, открытие оригинала по `address.href` и точный адрес из `address.address`.
3. Дайте инженеру выделить в сохранённом тексте проверенные область, предмет и действие, затем обозначение каждого источника и его значение с единицей. Передайте отметки вместе с ID и версиями актуального решения в POST confirm. Элемент команды имеет следующий вид.

```ts
{
  questionId, questionVersion, decisionId,
  review: {
    wordingSha256,
    scope: { start, end },
    subject: { start, end },
    action: { start, end },
    citations: [
      { observationId, reference: { start, end }, value: { start, end } }
    ]
  }
}
```

Границы считаются в кодовых единицах UTF-16 от начала `editedWording`, начало включено, конец исключён. Используйте смещения из редактора сохранённого текста. Для каждой действующей цитаты нужен её `address.observationId`. Если у цитаты нет значения, передайте только `reference`. Ссылочные фрагменты используют обозначения из `sources[].label`. Значения сверяются вместе с единицами. В авторском тексте числовые данные должны относиться к отмеченным области, предмету, ссылке или значению. В области укажите обозначение из каталога. Для предмета допустима перестановка слов с сохранением обозначения. Распознаваемые глаголы запроса включают «предоставьте» и «направьте» при нехватке, «подтвердите» и «уточните» при противоречии. Для нехватки в выделенном действии укажите допустимые формы из `basis.requiredFormats`. Инженер явно подтверждает смысл всей формулировки по оригиналам.

422 `letter_wording_not_supported` запрашивает предметную сверку авторской правки. 422 `letter_wording_basis_mismatch` указывает `questionId`, `field` и при наличии `observationId`. При смене основания сначала обновите решение в комплектности. Для другого фасада выберите основание и письмо его области. При 412 `letter_wording_review_stale` перечитайте редакцию и повторите выделение. Управляемые формулировки по-прежнему подтверждаются текущими ID без `review`.

Для подтверждённой авторской формулировки сохраняется `wordingApproval` с отметками, автором, временем и хэшами текста и основания. Подтверждение можно переиспользовать для неизменившегося пункта при правке других пунктов. Предпросмотр, копирование и экспорт повторно проверяют хэши и актуальность основания.

## Связь с соседними модулями

- Шаги 3/7. Письма используют `lockScopes` из шага 7. Порядок — `lockIntakeProject` → `lockProjectScopes` → чтение удержаний и оснований. Допуск, версия и чтение неизменяемых байтов находятся внутри одной транзакции. События редакций, отправок и ответов публикуются миграцией шага 7 при commit. Экспорт сохраняется один раз на пару «редакция, формат».
- Шаг 5. `selectConfirmedGrounds(tx, {projectId, scopeId, recipient, items})` принимает `{questionId, questionVersion, decisionId}`. Текст строится из стадии, области, предмета, формы, действия, величин и адресов подтверждённых оснований. В истории сохраняются версия каталога, исходные цитаты и адреса.
- Шаг 7. `getSentItems(tx, projectId, letterId, sentId)` из `index.ts` проверяет связь с проектом и возвращает неизменяемый состав отправки с ID пункта и вопроса, областью и основанием. Вызывающий отвечает за право чтения проекта и области.

## Стадия в письме

Оба оформления нового письма выводят `basis.scope.stage` отдельной строкой перед пунктами. Стадия берётся из сохранённого основания. Предпросмотр, копирование, TXT и DOCX используют текст одной редакции. Старые редакции, выгрузки и снимки отправки возвращают сохранённый текст и байты. При сохранении новой редакции стадия добавляется в её текст.

## Адрес основания

`sources[].label` служит готовой подписью для карточки и предпросмотра. Из адреса цитаты берётся точная строка `locator.line` или строка таблицы `locator.row`; границы выданного текстового окна `firstLine` и `lastLine` не являются адресом цитаты. `sources[].address.documentRevision`, когда доступна, содержит документное обозначение редакции из reader, дословную шапку, её локатор и `evidenceId`. Технический `versionId` по-прежнему закрепляет оригинал. Порт шага 5 получает обозначение из хэш-сверенной сохранённой выдачи reader той же версии. Новый снимок сохраняет всю опору и готовую подпись. История отдаёт ранее записанный текст и байты файлов.

Для одного подтверждённого конфликта пункт содержит все отличающиеся оригиналы и места из `basis.citations`. Повторные чтения A/B одного значения по тому же адресу отображаются одной опорой в `sources`. Источники с одинаковой исходной записью значения и единицы объединяются в одну фразу с отдельным адресом и редакцией каждого оригинала. В `basis.citations` сохраняется исходный список, переданный комплектностью.

## Автоматическая проверка

В корне репозитория после установки зависимостей:

```sh
npm run build:server
node --test src/modules/letters/letters.test.mjs
```

Первый тест извлекает текст непосредственно из WordprocessingML стандартной библиотекой Python 3. Для сценария с настоящим PostgreSQL возьмите индивидуальную БД по инструкции [стенда](../../../infra/test-stand/README.md), примените `npm run migrate` и запустите `LETTERS_TEST_DB=1 node --test src/modules/letters/letters.test.mjs`. Тест использует штатные Fastify-модули доступа, комплектности и писем. Адресные наблюдения закладываются синтетически, без вызовов моделей. Проверка сравнивает полное письмо в трёх представлениях и проверяет отказ для пустой выборки, публикацию авторской формулировки в TXT и DOCX, подмену 2 мм на 20 мм и фасада А на Б, блокировку текущей выдачи, фиксацию старой отправки и отзыв доступа.
