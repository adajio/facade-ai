# Шлюз моделей и очередь · шаг 8

Контракт для worker и Mastra. Импорт из `src/modules/gateway/index.js`. Идентификаторы проекта, области и поколения — UUID. Поколение относится к зафиксированному набору первичных обязанностей. Поколение аренды — отдельный счётчик.

| Операция Gateway | Вызов и результат |
| --- | --- |
| `openGeneration(ref, tx?)` | `{ projectId, scopeId, generationId }`. Вызывается при смене входных данных в транзакции владельца области. |
| `declarePrimary(ref, obligation, tx?)` | `{ id, branch: 'A' \| 'B', place }`. Регистрирует обязанность по точному месту при открытой описи. |
| `sealGeneration(ref, manifest, tx?)` | Замораживает полный манифест обязанностей A/B. |
| `enqueue(input, tx?)` | `{ ...ref, key, kind, purpose, subjectId, obligationId?, payload?, priority? }`. `purpose` принимает `local`, `primary_a`, `primary_b`, `review`. Для первичного задания нужен `obligationId`. Включать постановку задания и исходное событие в транзакцию прикладного модуля. |
| `claim({ workerId, kinds, leaseMs })` | Выдаёт работу с `lease` и последним курсором, либо `null`. |
| `heartbeat(lease, leaseMs)`, `checkpoint(lease, cursor, tx?)` | Вернут `false`, если срок, исполнитель или поколение аренды уже сменились. |
| `finish(lease, result, primary?, tx?)` | Для первичной работы `primary = { state: 'completed' \| 'final_refusal', evidenceRef }`. Фиксирует результат/отказ и outbox атомарно. Публикацию в таблицах своего модуля выполнять в этой же транзакции только при `true`. |
| `suspend(lease, { reason, nextAction, retryAt? })`, `resume(jobId)` | Удержание с адресом продолжения или обратно в очередь к указанному времени. |
| `call({ lease, effectKey, routeId, dataClass, request, inputRefs, retryRejectedAttemptId? })` | Один логический ход Mastra. Ответ `paid` с выходом и квитанцией, `rejected` с доказанным отказом или `held` с кодом и следующим действием. Ввод Mastra и адреса переданных представлений обязаны быть стабильны при повторе хода. |
| `configureRoute(policy)`, `grantRoute(grant)` | Доверенный конфигуратор стенда и проекта. Разрешение привязано к проекту, точному профилю маршрута, классу данных и назначению вызова, включая отдельные ветви A/B. |
| `readOutbox(after, limit)` | Курсор монотонной публикации. Потребитель повторяет применение по ID события. |

`tx` — активный `pg.PoolClient` из общей транзакции. Модуль использует непрозрачные идентификаторы хода и доказательств. Передавайте устойчивый `effectKey` (например ID шага ветви и номер внешнего хода). При потерянном результате используйте прежний ключ и прежний запрос. Технический повтор известного отказа требует явной ссылки `retryRejectedAttemptId` на исходную попытку. Отключите повторы SDK Mastra и привяжите вызов модели к `Gateway.call`.

## Подключение к приложению

`createGateway(db, { journal, transport })` подключает управляемый транспорт. Он реализует `send(attempt, route, request, signal)` с ровно одной отправкой, без скрытых повторов. Сетевую отправку нужно начать до первого `await` в адаптере, чтобы отзыв разрешения и начало отправки имели определённый порядок. Неизвестную оплату возвращайте как `unknown`. `lookup(attempt)` для управляемого провайдера может вернуть положительное доказательство исхода, даже если ответ потерян. Отсутствие записи или сбой поиска сохраняют резерв. Для воспроизведения ответа по прежнему ключу действует текущая аренда. Поздняя квитанция закрывает исходную попытку независимо от аренды. Окончательный отказ остаётся пробелом покрытия. Проверенная приложением адресная пара разных оригиналов допускается независимо от несвязанных первичных задач. Обычный барьер поколения сохраняется для остальных заданий сверки.

`journalFromEnv()` открывает пул по `FACADE_GATEWAY_JOURNAL_URL` и проверяет закреплённый `FACADE_GATEWAY_LEDGER_ID`. На отдельной площадке примените [DDL внешнего журнала](journal.sql) и создайте единственную строку `gateway_external_ledger(ledger_id)` с UUID установки. Проверка фактического разделения доменов отказа относится к эксплуатации. Продакшен требует надёжный PostgreSQL вне VPS. Три базы на одном стендовом экземпляре дают изоляцию реестров для теста, без физической проверки отказа VPS. Все живые проекты и прогоны шага 15 используют один экземпляр и один UUID журнала, включая восстановление. Транзакции журнала подтверждают записи с `synchronous_commit=on`.

`journal.balance()` возвращает один предел 10 000 000 000 нанодолларов США ($10), активный резерв и подтверждённые затраты. Журнал под общей блокировкой проверяет сумму перед резервированием и отправкой. Факт превышения верхней границы либо конфликт подтверждённых квитанций замораживает платный допуск, сохраняя доказанный расход. При неопределённости незакрытый резерв удерживает повтор эффекта и вызовы проекта по затронутому маршруту. Другие проекты могут использовать свободный остаток, когда освобождён сетевой слот.

При восстановлении остановите исполнителей, восстановите БД и проверьте актуальные разрешения и маршрутные профили. Запустите `Gateway.recover()` с прежним журналом и доверенным транспортом. Шлюз поднимает внешние попытки, которые появились после восстановленной точки, и сверяет их по доступным независимым квитанциям. Первый живой вызов после старта также проходит восстановление. Если подтверждена оплата, а тело ответа утрачено, действие `result_missing` ведёт к восстановлению исходного ответа. Новый платный запрос автоматически не создаётся.

### Операторский API

Доступ через серверную роль технического оператора своей организации. Диагностика содержит только служебные идентификаторы, сроки, причины, действия, регистрируемый расход и метаданные квитанций.

- `GET /api/operator/gateway/projects/:projectId` возвращает `{ jobs, attempts }`. Работа показывает состояние, аренду, причину и `nextAction`. Попытка показывает `jobId, routeId, state, reserveUsdNanos, spentUsdNanos, reason, nextAction, providerId, model, provider, routeVerified, promptTokens, completionTokens`.
- `POST /api/operator/gateway/projects/:projectId/attempts/:attemptId/reconcile` принимает `Idempotency-Key`, действующие сессию и CSRF. Поля `reasonRef, state` обязательны. Для `paid` нужны `costUsdNanos, providerId, evidenceRef`. Для `rejected` нужны `code, evidenceRef`. Для `unknown` нужен `code`. Передавайте ссылки на доказательства из операторского реестра.
- Для попытки `unknown` без generation ID этот же POST принимает `{"state":"isolate_unknown","reasonRef":"<ссылка на операторское свидетельство>"}`. Ответ сохраняет `state: "unknown"` и полный резерв, добавляя `routeIsolated: true`. Отметка хранится отдельно от квитанции в аудите внешнего журнала. Повтор с тем же ключом возвращает исходный ответ. Подлинную квитанцию можно сверить позже с новым ключом.
- После отметки перезапустите worker штатным способом для восстановления удержанных заданий маршрута. Шлюз допускает другие задания проекта на том же маршруте по обычным правилам. Та же работа и эффект, ограничение активного слота, другой неизолированный `unknown`, текущая отправка, лимиты и барьер ведущего продолжают блокировать вызовы в соответствующих случаях. Операторская диагностика показывает `routeIsolated` как отметку в истории попытки.
- Квитанция содержит `{ state, reserveUsdNanos, spentUsdNanos, receipt }`. Повтор совпадающей команды возвращает тот же исход после перезапуска. Изменение команды под прежним ключом даёт 409. Автор, право, основание, время, прежний и новый резерв и расход хранятся во внешнем журнале. В служебные проекции и журнал намерений не попадают запрос, оригинал, письмо или ответ модели.

## Профили шага 15

`createStep15Gateway(db, journal, approval)` доступен при `FACADE_GATEWAY_LIVE_MODE=step-15`. Worker шага 9 читает `FACADE_GATEWAY_OPENROUTER_KEY`, `FACADE_GATEWAY_OPENROUTER_ENDPOINT` и массив `FACADE_GATEWAY_STEP15_PROFILES`. Ключ доступен только процессу шлюза. Предусмотрите на уровне развёртывания запрет выхода к провайдеру из других процессов. Целевой endpoint закрепляется, HTTP-перенаправления, автоматические повторы, fallback и маршруты `auto` закрыты.

- `mode: "synthetic-research"` допускает Kimi через `wafer/us` с ZDR и разрешает точный `moonshotai/kimi-k3.1-pro` → `decart/mxfp4` с ZDR для сравнения на согласованной синтетике. Qwen идёт через закреплённый Alibaba. Для каждой области обязательна запись `syntheticScopes: [{ projectId, scopeId, approvalRef, originalSha256s }]` и допуск маршрута с `dataClass: "synthetic"`. Шлюз сверяет PostgreSQL-версии назначенных оригиналов, все принятые хэши проекта и происхождение ссылок на представления текущей работы. Неизвестный хэш, чужая запись доказательства и клиентский класс удерживают отправку.
- `mode: "strict-zdr"` требует `zdrEvidenceRef` для конкретной операции. У Kimi обязателен `wafer/us`. Для Qwen строгий профиль появляется после отдельного подтверждения точного маршрута и модальности.
- Каждый профиль закрепляет `model, provider, expectedResponseProvider, revision, validUntil, boundEvidenceRef` и верхние границы тарифов из `OpenRouterProfile`. `expectedResponseProvider` — наблюдаемое имя провайдера в квитанции Chat Completions. Шлюз сверяет модель и провайдера, регистрирует подтверждённый расход при расхождении и удерживает применение ответа. Подтверждение **точного endpoint** и полный тарифный конверт, включая reasoning, кэш, мультимодальность и дополнительные начисления, нужны перед включением. Адаптер принимает только текст и ограниченные встроенные PNG. Неподтверждённый тариф или отсутствие квалификационного профиля закрывают допуск. [Маршрутизация и предельные цены](https://openrouter.ai/docs/guides/routing/provider-selection) · [Chat Completions](https://openrouter.ai/docs/api/api-reference/chat/create-a-chat-completion)

На момент разработки платный адаптер проверяется с подменой `fetch`. Паспорта сверки:

### Верхняя стоимость мультимодального хода

Контракт шагов 9 и 15. `matchesKimiEndpoint(model, provider, mode)` экспортирует единое правило допуска Kimi для шлюза и worker. Harness передаёт прежние `request` и `inputRefs` через `Gateway.call`. Ввод Mastra с `max_tokens` поддерживается. Для выхода шлюз выбирает ровно один подтверждённый `completionParameter`, а профиль задаёт `outputTokenLimit`. Для планирования до подключения ключа доступна чистая функция `estimateOpenRouterRequest(profile, route, request)`. Она возвращает стоимость входа, выхода с reasoning, изображений, фиксированного запроса, дополнительных начислений и итог `ceilingUsdNanos` либо `null`. Полный тип параметров для запуска — `QualifiedOpenRouterProfile`. Числа из тестов синтетические.

| Компонент | Что должно быть закреплено в профиле |
| --- | --- |
| Вход | `inputTokenUpperBound` ограничивает весь тарифицируемый вход, включая историю, схемы функций и токены визуального представления. Подтвердите на точном endpoint, что объём выше этой границы нельзя принять и оплатить. `RoutePolicy.maxRequestBytes` дополнительно ограничивает фактический JSON с настройкой маршрута. |
| Кэш | `promptNanosPerToken, cacheReadNanosPerToken, cacheWriteNanosPerToken` задаются для самого дорогого допустимого варианта. `cacheBilling: "replaces-input"` берёт максимум трёх цен только при доказанном взаимоисключении. `"supplement"` резервирует их сумму на каждый входной токен. Клиентские директивы кэширования и серверные инструменты шлюз не передаёт. |
| Выход и reasoning | `completionParameter` поддерживается точным endpoint. `completionCapIncludesReasoning: true` требует подтверждения, что переданный предел жёстко ограничивает суммарную генерацию видимого текста, вызовов функций и reasoning. `reasoningBilling: "replaces-output"` берёт максимум `completionNanosPerToken` и `reasoningNanosPerToken`. `"supplement"` берёт сумму. Для Alibaba Qwen4 Max шлюз дополнительно резервирует 10 токенов по допуску поставщика. |
| Изображения | `maxImages, maxImageWidth, maxImageHeight, maxImagePixels, maxImageBytes` ограничивают число, размеры и декодированные байты. Принимается встроенный статический PNG. Каждое вхождение в историю считается отдельно. Визуальные токены входят в полный лимит входа, а `imageNanos` покрывает отдельную плату за изображение. Ноль надо подтвердить для выбранного маршрута и операции. |
| Прочие начисления | `requestNanos, additionalNanos` покрывают фиксированную плату за запрос и прочие подтверждённые начисления. Каждый тариф округляется вверх до целых нанодолларов в своей единице. `provider.max_price` задаёт лимиты `prompt` и `completion` в долларах за миллион токенов и `request` и `image` в долларах за единицу. Кэш и reasoning отдельно закрываются тарифным свидетельством `boundEvidenceRef` с датой `validUntil`. [Документация max_price](https://openrouter.ai/docs/guides/routing/provider-selection#max-price) |

Для коротких вызовов точных маршрутов `moonshotai/kimi-k3.1-pro` → `wafer/us` или `decart/mxfp4`, а также `qwen/qwen4-max` → `alibaba` существует опциональный `inputEnvelope`. Свидетельство `evidenceRef` должно ограничивать все тарифицируемые токены после OpenRouter и провайдера. Укажите `maxWireBytes, maxMessages, maxTools`, целочисленный `tokensPerWireByte` для худшего расширения текста и схем, `templateOverheadTokens` для всех фиксированных добавлений шаблона и при необходимости `maxTokensPerImage` для любого PNG в допущенном диапазоне. Шлюз считает фактические UTF‑8-байты готового HTTP JSON, включая управляющие поля, схемы и корреляцию. Формула `wireBytes × tokensPerWireByte + templateOverheadTokens + images × maxTokensPerImage` применяется в пределах квалифицированной формы и ограничена общим потолком входа. При превышении размеров, числа сообщений или инструментов, либо PNG без доказанного лимита визуальных токенов, используется полный входной потолок. Плата за число изображений и остальные компоненты сохраняются. Малый размер JSON и доступность токенизатора без точного шаблона сами по себе не доказывают этот предел.

Если свидетельство отдельно учитывает PNG и подтверждает, что base64 не превращается в оплачиваемый текст, задайте `maxTextWireBytes` вместе с `maxTokensPerImage`. Для расчёта шлюз вычитает только base64 в проверенных PNG в пользовательских сообщениях и сохраняет в подсчёте остальные поля, включая схемы и заголовки data URL. Фактический wire дополнительно ограничен `maxWireBytes` и `RoutePolicy.maxRequestBytes`. Превышение любого ограничения возвращает прежний полный потолок.

На Kimi K3.1 Pro через `wafer/us` сумма доказанного входа и запрошенного выхода сравнивается с 1 048 576 токенами. При превышении Wafer Chat Completions может повторить запрос без `max_tokens`. Шлюз допускает такой профиль только если `additionalNanos` уже покрывает разницу между запрошенным выходом и опубликованным максимумом OpenRouter 943 718 токенов по верхней ставке выхода с reasoning. Любой запас на прочие начисления добавляется поверх этой разницы. На Alibaba параметр `max_tokens` для Qwen4 Max эквивалентен общему ограничению ответа с reasoning. [Wafer Output length](https://docs.wafer.ai/serverless/chat-completions#output-length) · [Alibaba Chat Completions](https://www.alibabacloud.com/help/en/model-studio/qwen-api-via-openai-chat-completions).

Резерв одной попытки равен сумме компонентов. Общий остаток равен потолку внешнего журнала за вычетом подтверждённой стоимости и всех незакрытых резервов. По умолчанию потолок равен $10, включая журналы прежней схемы. Для нового выделенного журнала потолок можно задать один раз при создании строки `gateway_external_ledger(ledger_id, limit_usd_nanos)`. Передайте то же число в `FACADE_GATEWAY_EXPECTED_JOURNAL_LIMIT_USD_NANOS`, чтобы приложение отклоняло несовпадение с закреплённым журналом, включая старую схему с потолком $10. PostgreSQL дополнительно защищает резервирование и отправку при меньшем потолке, если подключилась прежняя версия приложения.

Настраиваемый потолок маршрута ограничивает максимум одной попытки. Журнал резервирует рассчитанную стоимость конкретного хода в пределах этого потолка. Если ход может поместиться после расчёта по активным резервам, шлюз возвращает `budget_reserve_wait` со временем повтора. Worker возвращает тот же эффект в очередь. Если для хода недостаточно средств даже по этому расчёту, шлюз возвращает `budget_exhausted`. Резервы с неизвестной оплатой и истёкшим сроком отправки сохраняются. Предварительная проверка занятого маршрута выполняется до создания новой попытки. Журнал снова проверяет маршрут и полный бюджет под блокировкой перед отправкой. `journal.balance().remainingUsdNanos` показывает свободный остаток. Отпечаток профиля и рассчитанный резерв закрепляются во внешнем намерении.

### Условия тарификации workspace

Для согласованного прогона в текущем workspace в существующем `boundEvidenceRef` фиксируются применение стандартного тарифа OpenRouter, наблюдаемый нулевой BYOK, размер резерва на расхождения в `additionalNanos` и использованные источники. Отдельное поле о настройках аккаунта не требуется. Каждый небольшой ход отправляется отдельно. Перед следующим сверьте `usage.cost`, generation ID, точный endpoint, изменение `/api/v1/key` и остаток общего журнала. Расхождение с тарифом, неожиданный провайдер или неопределённый расход останавливают прогон до сверки.

Если владелец подтвердил отсутствие списания по конкретной попытке, технический оператор передаёт `state: "rejected"`, `code: "operator_attested_no_charge"` и ссылку на свидетельство владельца в `evidenceRef` через штатный POST сверки. `reasonRef` и постоянный `Idempotency-Key` сохраняют основание и позволяют проверить повторный запрос. Generation ID или квитанция провайдера для такой записи не подставляются.

Шлюз передаёт `enabled: false` для `web`, `file-parser`, `response-healing`, `auto-router`, `pareto-router` и `armor` по типам официальной схемы Chat Completions. Входное тело Mastra не может включить plugin, вариант `:online`, preset, серверный инструмент, удалённый URL изображения или файл для платного парсера. OpenRouter применяет настройки плагинов workspace при отсутствии переопределения и может запретить переопределение. Состояние настроек workspace не выводится из запроса. Alignment и web-fetch не вызываются. Их схемы не поддерживают `enabled: false`. ### Диагностика HTTP 404 для шагов 17 и 15

В `GET /api/operator/gateway/projects/:projectId` у попытки доступно `routerDiagnostic`. Оно содержит HTTP-статус, числовой `error.code`, распознанный `error.metadata.error_type`, распознанный `failed_routing_step`, номер `openrouter_metadata.attempt` и корреляцию. `traceId` совпадает с UUID попытки, который отправлен в `trace.trace_id`. `requestId` доступен при получении идентификатора формата OpenRouter в заголовке `X-Request-Id` или поле `request_id`. Корректный `X-Generation-Id` также виден в `providerId`. Сообщение ошибки, исходный ответ, поля `raw`, данные фильтров, заголовки авторизации и cookies в диагностике не сохраняются. [Ошибки OpenRouter](https://openrouter.ai/docs/api/reference/errors-and-debugging) · [Метаданные маршрутизации](https://openrouter.ai/docs/guides/routing/routers/router-metadata#error-responses)

Для документированного HTTP 404 с `error.code=404` и `attempt=0`, без признаков обращения к провайдеру или generation ID, шлюз сохраняет `stage: "before_provider"`. При признаках обращения сохраняется `provider_attempted`. При отсутствии достаточных метаданных сохраняется `undetermined`. Это диагностика, состояние оплаты определяется прежними правилами допуска и сверки. При `unknown` резерв удерживается. Для операторской команды `rejected` привяжите доказательство к UUID именно этой попытки. У исторической 404, сохранённой без структурных полей, UUID известен, но новая диагностика не восстанавливает прежний ответ. Для неё нужно независимое подтверждение от OpenRouter по корреляции и времени. Наличие `traceId` само по себе не подтверждает наличие поиска по нему.

Синтетический тест подменяет два ответа HTTP 404. Сравнивает внешний журнал, приложение и операторскую проекцию, проверяет очистку чувствительных значений и сохранность диагностики после сверки первой попытки. Вторая попытка удерживает свой резерв.
