# Исследовательские вопросы · шаг 12

Реализация приложения Б11 на срезе `42ed7fc`. Чтения одной области и стадии сопоставляются по предмету, свойству, варианту и роли источника. Найденное место, результат проверки опор и решение инженера хранятся отдельно.

## Подключение соседей

- **4, 9, 11**. Публикация адресного наблюдения вызывает `onObservationPublished(tx, event)` из `../questions/index.js` в транзакции наблюдения. `observationId` неизменяем и уникален. Контракт `ObservationPublication` находится в [domain.ts](domain.ts). Вызывайте с установленными проектом и областью, назначенной действующей ролью места и проверенным SHA-256. Для смены редакции передайте `supersedesVersionIds` только после установления замены в этой области. Событие идемпотентно. Сюда передаётся компактный дескриптор. Текст/пиксели открывает reader на этапе сверки.
- **Worker 4/8/9/11**. Обрабатывайте `processNextInquiry(db, ports, signal)` в имеющемся цикле worker. Возвращает `false`, когда работы нет. `ports.openSupport` должен открыть конкретную версию по ID и SHA-256, разрешить адрес по собственной записи наблюдения и вернуть фактически поданный текст или изображение. `ports.checkMeaning` выполняет смысловую проверку только через действующий шлюз и политику допуска. Локальный вариант возможен для точного совпадения предмета/зарегистрированного синонима на открытых опорах. Для ответа «неясно» передайте `unclear`. Модуль шлюз напрямую не вызывает.
- **5 и 6**. `getCurrentInquiryPairs(tx, projectId, scopeId)` даёт проверенные машинные пары текущего среза для заключения по области, исходные величины и идентификаторы опор. Команда заключения и отбор в письмо проводят свои проверки по удержаниям, обязательности позиции и инженерному подтверждению. Пустой поиск, непроверенный кандидат и исследовательское решение сами по себе не дают внешнего пункта.
- **7**. При адресной публикации сбрасывается поисковая проекция и отмечается затронутое инженерное решение. Worker сверяет материалы конкретной причины, текущие поколения, завершённые оценки и открытые опоры. Затем вызывает `resolveSupplementImpact` с текущими версиями причины и оценок. Уточнение неизвестной области и ручное разрешение открытых ограничений остаются у шага 7.

## HTTP для шага 13

Мутации используют `Idempotency-Key`, CSRF и сеанс шага 2. Решение передаёт сильный `If-Match` из `version`. Защищённые чтения возвращают `Cache-Control: no-store`.

| Маршрут | Вход и результат |
| --- | --- |
| GET /api/projects/:projectId/inquiries?scopeId=… | Список вопросов области, включая вопросы с нулём результатов |
| POST /api/projects/:projectId/inquiries | `{scopeId, sliceId, catalogVersionId, subject, property, variant?}` → `{id, version}`; стадия берётся из области |
| GET /api/inquiries/:id | Вопрос, состояние, ограничения, текущие кандидаты и пары, инженерное решение и история с версиями |
| POST /api/inquiries/:id/decisions | `{action, reason, candidateIds?, answer?}` → `{id, version}`; действия `accept`, `correct`, `reject`. Для исправления нужны ответ и открытая опора. |

`publishReaderObservation(tx, input)` связывает транзакционную запись reader с событием. Передайте `{observation, projectId, scopeId, readerJobId, subject, property, variant?, aliases?, role, revision, priority?, comparableContext?, assessmentQuestionId?, generationId?, replacesConfirmed?}`. Роль, приоритет, сравнимые условия и применимость редакции задаёт проверенная классификация. Пара появляется после открытия обеих опор, при разных задачах и байтах оригиналов, установленных общих условиях сравнения и равном известном приоритете. Неустановленные условия остаются внутренней сверкой.

`createRuntimeInquiryPorts(db, reader, storage.objects, checkMeaning?)` использует общий reader и закрытое хранилище для проверки закреплённого адреса, оригинального SHA-256 и сохранённого представления. На текстовой строке допустима локальная проверка точного имени и зарегистрированного синонима. Для смысловой проверки и пикселей передайте обработчик существующего review-задания с разрешённым gateway и устойчивым ключом эффекта. Без разрешённой или достаточной проверки результат остаётся открытым.

Заключение и допуск в письмо остаются у шагов 5, 6 и 9. Публикация шага 9 в своём текущем поколении проверяет первичные обязанности и исход спора до `applyAssessmentUpdate`. Она исключает отозванные опоры по `inquiry_observations.superseded`; шаг 5 дополнительно сверяет `inquiry_superseded_versions` при разрешении наблюдений. `getCurrentInquiryPairs` возвращает адресные пары для просмотра и продолжения сверки. Сам по себе результат локального поиска не меняет вывод об обязательной позиции и не даёт оснований письма. Для шага 7 тот же scope и транзакционный замок удерживают допуск до пересчёта влияния.

Список возвращает `{sliceId, cursor, projectionVersion, inquiries, nextAfter}`. Для следующей страницы используйте непрозрачный `nextAfter` как значение `after`. Карточка возвращает `state` (`queued`, `searching`, `empty`, `partial`, `verified`), `nextAction`, `limitations`, `candidates[].{reason,applicability,source}`, `pairs[].{left,right,comparison}`, `decision`, `decisionHistory` и `searchHistory`. Закреплённые опоры дают `evidenceHref`, `contentHref`, `originalHref` и `receiptHref` и `correspondenceHref`. Для чтения прежних опор передайте `?searchVersion=…`; версия правки всегда остаётся отдельным полем `version`.

Сценарий для шага 13 и сборки: после миграций в новой синтетической базе с объектным хранилищем выполнить `NODE_ENV=test FACADE_INTAKE_DISK_GUARD_BYTES=0 node --test src/modules/questions/questions.integration.test.mjs`. Для отдельной сборки можно задать `FACADE_TEST_BUILD=/полный/путь/к/dist`. Тест использует реальные маршруты Fastify, SQL и reader, закрепляет синтетические наблюдения обычной прикладной транзакцией и не включает живой транспорт.


## Штатный worker

Для вопроса обязательной части с неясным смыслом и двумя открытыми сопоставимыми опорами разных ветвей модуль использует существующее задание ведущего и две проверки Mastra. При наличии разрешений `review` он ставит задание в очередь gateway или подключается к уже поставленному спору по тем же наблюдениям. Шлюз проверяет поколение, аренду, барьер первичного чтения, разрешения и бюджет. Обе проверки открывают назначенные места. Два результата `supported` текущего поколения запускают повторный поиск и позволяют подтвердить смысл точного наблюдения.

Автоматическая проверка влияния принимает запечатанное поступление с установленными областями. Для каждой области она сверяет действующее поколение, завершённое первичное чтение, текущую оценку и открытые опоры, которые использует этот вывод. Все версии материалов конкретной причины должны иметь установленное влияние. Worker передаёт уже сохранённые версии оценок в шаг 7 в той же транзакции. Неподтверждённые и независимые причины сохраняются.

Сквозной сценарий использует отдельную пустую БД приложения, объектное хранилище и журнал gateway. После миграций и подключения журнала запустите `NODE_ENV=test FACADE_QUESTIONS_WORKER_INTEGRATION=1 FACADE_INTAKE_DISK_GUARD_BYTES=0 node --test --test-name-pattern 'ordinary worker' src/modules/questions/questions.integration.test.mjs`. Транспорт провайдера работает по loopback и возвращает управляемые квитанции с нулевой стоимостью.

## Применимость измерения

Для нового числового наблюдения harness сопоставляет назначенный предмет и атрибут с адресованной строкой. Для табличной ячейки учитываются строка и заголовок её столбца. Для текста соседняя строка даёт контекст, если обе строки указывают на одну позицию. Число с единицей без установленного атрибута остаётся адресуемым кандидатом с `applicability: meaning_unclear`. Такой кандидат допустимого формата оставляет открытый вопрос в оценке. Для прежних наблюдений harness перепроверяет предмет по сохранённой фактической выдаче reader при повторном использовании. Редакция, форматы каталога и полномочия проверяются отдельно.

## Подтверждение применимости и адресная замена

Маршруты используют ID **вопроса комплектности** из `GET /api/projects/{projectId}/assessments/current?scopeId=…`. Права — `project:engineer` по проекту и области, серверный сеанс, CSRF, `Idempotency-Key` и `If-Match` с текущей версией вопроса. Для истории достаточно `project:read`. Все маршруты доступны также под `/api/v1`.

### Подтвердить синоним атрибута

`POST /api/questions/{questionId}/attribute-aliases` принимает подтверждённое инженером полное обозначение, включая идентификатор позиции, и адресные опоры обеих ветвей. Сервер перечитывает представления и сверяет их с байтами оригинала, действующей редакцией и форматом. Нужен различимый атрибут рядом с измерением или в относящемся к нему заголовке. Марка вместе с единицей измерения сама по себе недостаточна.

```json
{
  "alias": "P-22 bracket width",
  "reason": "Проверено соответствие обозначения в CAD назначенному атрибуту",
  "proof": [
    { "observationId": "11111111-1111-4111-8111-111111111111", "evidenceId": "21111111-1111-4111-8111-111111111111", "versionId": "31111111-1111-4111-8111-111111111111" },
    { "observationId": "12222222-2222-4222-8222-222222222222", "evidenceId": "22222222-2222-4222-8222-222222222222", "versionId": "31111111-1111-4111-8111-111111111111" }
  ]
}
```

Подтверждение действует для вопроса, закреплённой версии каталога и версии настроек области. При повторной публикации worker ищет подтверждённое обозначение по фактическому адресу. Слова модели остаются поисковой подсказкой до проверки.

### Заменить основания одного вопроса

`POST /api/questions/{questionId}/source-replacements` принимает явный перечень заменяемых опор текущего вопроса и проверенные опоры обеих ветвей новой редакции. Пример с заменой двух адресов, каждый из которых относится к отдельному прежнему документу.

```json
{
  "reason": "Принята новая редакция значения только для этого вопроса и указанных адресов",
  "replaced": [
    { "observationId": "11111111-1111-4111-8111-111111111111", "evidenceId": "21111111-1111-4111-8111-111111111111", "versionId": "31111111-1111-4111-8111-111111111111" },
    { "observationId": "13333333-3333-4333-8333-333333333333", "evidenceId": "23333333-3333-4333-8333-333333333333", "versionId": "33333333-3333-4333-8333-333333333333" }
  ],
  "replacements": [
    { "observationId": "14444444-4444-4444-8444-444444444444", "evidenceId": "24444444-4444-4444-8444-444444444444", "versionId": "34444444-4444-4444-8444-444444444444" },
    { "observationId": "15555555-5555-4555-8555-555555555555", "evidenceId": "25555555-5555-4555-8555-555555555555", "versionId": "34444444-4444-4444-8444-444444444444" }
  ]
}
```

Обновление оценки, связь адресов, аудит и квитанция фиксируются одной транзакцией. Редакции исходных документов остаются историческими и могут продолжать служить основанием другого вопроса. Состояние удержаний определяет шаг 7. Для TXT действует текущий допуск формата из каталога или требований области.

Обе команды возвращают `201 { id, questionId, version, assessmentVersion }`. Повтор с исходным ключом возвращает ту же квитанцию с `Idempotency-Replayed: true`. Новая команда со старой версией возвращает 412. `422 support_format_not_admitted` означает неподходящий формат, `422 review_incomplete` — отсутствие завершённой проверки текущего поколения, `422 attribute_alias_unverified` — отсутствие отличительного атрибута. `GET /api/questions/{questionId}/applicability` возвращает `{ aliases, replacements }` с автором, причиной, версиями и закреплёнными ID. Для открытия опоры используйте штатный `/api/v1/evidence/{evidenceId}`.
