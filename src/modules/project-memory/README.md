# Адресная память проекта

Память читает принятые оригиналы через штатный Reader. Она сохраняет и
проверяет нативное представление каждого физического окна, исходные адреса
строк и поисковую проекцию. Нативное окно XLSX содержит ячейки, группировку
по строкам и колонкам и признаки объединений. Для PDF остаются рамки строк
и группировка нативного слоя. Адреса CAD сохраняют исходные пространства,
handle и доступные координаты. OCR, графика и потерянные при конвертации
структуры остаются в видимом остатке. Материализация не создаёт наблюдения A/B.

## Контракт приложений

Импорт из `project-memory/index.ts`. Вызывающая сторона получает
`SessionAccount` штатным `readSession`. Память повторно проверяет
актуальность сеанса и членство перед поиском или перечитыванием.

- `searchProjectMemory(db, session, { projectId, scopeId?, query, versionIds?, snapshot?, limit? })`.
  Поиск подстроки с NFC и без учёта регистра сохраняет исходный алфавит
  и исходное написание. Без `versionIds` и `snapshot` используются текущие
  принятые версии. Снимок закрепляет набор версий и обработанный префикс.
  Ответ содержит `version`, `snapshot`, `hits`, `status`, `pendingBlocks`
  и до 100 адресов остатка. Пустая выборка сама по себе не подтверждает отсутствие.
- `readProjectMemory(db, reader, session, { projectId, scopeId?, snapshot, blockId })`.
  У `reader` нужен метод `readMaterializedNative` штатного Reader. В ответе
  есть исходные строки блока, координаты и структурные группы. Для готового
  блока байты повторно проходят проверку SHA‑256. Привязки к предмету и
  техническая интерпретация остаются отдельными результатами исследования.
- При `scopeId` участвуют только действующие выдачи выбранной области.
  В поиск идут только опубликованные цитаты. Обрезки доступны по штатной
  ссылке публикации, остаются в графическом остатке и не раскрывают исходную
  версию. Изменение состава выдач требует нового снимка области.

## Worker и восстановление

Один вызов `indexNextProjectMemory(db, baseReader, signal?)` выполняет
один шаг из существующего цикла worker. Он возвращает `true`, если
продвинул обработку или сохранил причину ожидания, и `false`, если
доступной работы или общего слота Reader сейчас нет. Нужен базовый
`createRuntimePdfService`: consumer использует общий advisory slot.
За шаг открывается одна страница PDF или до восьми структурных окон
под одним проверенным временным оригиналом. Приоритет получают давно
ожидающие версии из разных проектов. Работа подхватывает и уже
диспетчеризированные версии из `intake_reader_jobs`.

Байты хранятся в штатном закрытом адресуемом хранилище Reader. Проекция
блока и продвижение курсора фиксируются в одной транзакции. Сбой после
сохранения объекта оставляет курсор на прежнем месте, а повтор переиспользует
объект по SHA‑256. Версия оригинала и версия контракта памяти входят
в ключи, поэтому поздняя запись прежней версии не меняет результат новой.
Снимки хранят только ссылки на версии и префиксы. Несовместимое изменение
канонического профиля требует новой версии контракта памяти. До этого
несовпадение профиля остаётся видимой причиной ожидания.

Штатный `reader.open` выдаёт свою квитанцию для каждого нового ключа
`runId/branch/operationKey`. Для полного нативного окна того же профиля
он берёт байты из проверенного объекта и указывает `materializedBlockId`.
Чтение рамки, отфильтрованная выдача, другой профиль и задания области
идут обычным путём. Повреждение выбранного объекта даёт ошибку
целостности. Повтор того же ключа получает исходную квитанцию.

## Локальная проверка

`FACADE_MEMORY_TEST_DB=<изолированная БД после штатных миграций> node --test src/modules/project-memory/intake.integration.test.mjs`.
Используются синтетические оригиналы и закрытое тестовое хранилище объектов.
Отдельно включаемый сценарий `FACADE_MEMORY_BOOT_TEST=1` запускает штатную
точку входа worker с локальным тестовым S3, без модельного транспорта.
