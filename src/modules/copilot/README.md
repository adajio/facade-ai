# Помощник инженера · стыки реализации

HTTP: `GET /api/projects/:projectId/copilot/search?q=…&scopeId=…` — явный поиск без модели. Проектный инженер получает исходные представления, участник с доступом на чтение — текущие опубликованные фрагменты своей области. `POST /api/projects/:projectId/copilot/questions` принимает `{ question }` и штатный ключ идемпотентности, возвращает ID. `GET …/questions/:id` — состояние собственного запроса инженера. `GET …/sources/:id` — повторное открытие адреса после проверки доступа. Фрагменты открываются через существующий экран публикаций.

**Память (стык с 16/17).** Нужны поиск по дословным исходным текстам и адресам и повторное открытие по устойчивому UUID в границе проекта. Минимальный договор в `contracts.ts`: `CopilotMemory.search(tx, projectId, query)`, `CopilotMemory.open(tx, projectId, id)`. Открытие возвращает исходную версию, адрес, точный текст, происхождение и ограничения. Поиск возвращает ограниченный список и фактическую границу индекса. Текущая/историческая версия определяется на чтении. Ограниченный доступ обрабатывается отдельно через действующие публикации и не попадает в память модели.

**Worker (стык с 18 и координатором).** Публичная функция модуля `processNextCopilot(runtime)` использует существующий экземпляр Gateway. Runtime включает пул, память, назначенный маршрут или отсутствие допуска и транзакционный порт постановки. Worker должен вызывать функцию даже без сетевого транспорта, чтобы запрос получил явное состояние. Выделенный вид работы `copilot_question`. Модель видит только операции поиска, открытия, адресного исследования и ответа. Для адресного исследования сохраняется точное место и выделяется следующий запуск этой же работы. Лимит и ключи эффектов закрепляются за запросом. Маршрут, транспорт и допуск остаются у шлюза. Публикация результата не затрагивает оценку, пакетные наблюдения и письмо.

Нужны согласованные назначение очереди, привязка к поколению и вариант подтверждения оригиналов на живом синтетическом маршруте. Сейчас допуск OpenRouter для ограниченного синтетического маршрута распознаёт только формы работы harness `primary`, `lead`, `verify` и привязывает `inputRefs` к `reader_evidence.run_id`. Нужна явная поддержка нового вида в этом стыке.
