# Комплектность · шаг 5 v1.1

Модуль читает версию каталога шага 2 и настройки выбранной области. Отдельный вопрос создаётся на каждую обязательную часть, в том числе при нуле кандидатов. Смена правила пересчитывает затронутые вопросы и возвращает список их ID и прежних решений в `change`. Неизменённая часть сохраняет свою версию зависимости. История открывается с каталогом, итогом, решением и цитатами на соответствующую дату.

## HTTP для шага 13

Пути под `/api/v1` и `/api`. Для мутаций применяются сессия, `Origin`, `X-CSRF-Token`, `Idempotency-Key` и сильный `If-Match: "n"`. Ответы имеют `Cache-Control: no-store`.

| Метод и путь | Контракт |
| --- | --- |
| GET /projects/:projectId/assessments/current?scopeId=… | Снимок области. Поля `scope: { id, name, stage }`, `catalogVersionId`, `version`, `inputGeneration` (десятичная строка), `holds`, `outcome`, `limitations`, `questions`, `conclusion`, `change`. Без `scopeId` выбирается единственная доступная область. |
| GET /projects/:projectId/assessments?scopeId=…&before=…&limit=… | `{ items, nextCursor }`, сначала последние версии оценки. Значение `nextCursor` передаётся в `before`. |
| GET /projects/:projectId/assessments/:version?scopeId=… | Сохранённый снимок области с `historical: true`. |
| POST /questions/:questionId/decisions | `{ action, reason, startWorkCritical?, requestExternal?, outcome?, observationIds?, exclusion? }` → `{ id, questionId, version, scopeId, assessmentVersion, outcome }`. `If-Match` — версия вопроса. Для внешнего пункта явно передавайте `requestExternal: true`. |
| POST /projects/:projectId/conclusions | `{ scopeId, startWork, reason }` → `{ id, scopeId, version, basedOnVersion }`. `If-Match` — версия оценки. `startWork`: `can_start`, `cannot_start`, `can_start_with_limitations`. |

Действия по вопросу: `confirm` принимает машинный вывод, `correct` фиксирует проверенную правку, `exclude` устанавливает исключение, `revoke` отменяет решение записью в истории. При `correct` передаётся `outcome` и при необходимости `observationIds` из текущего результата проверки. Изменение вывода перепроверяется по этим опорам. `exclude` принимает `exclusion: { kind: "not_required" | "work_without_data", until }`, где `until` — время ISO 8601 с поясом. Пропуск или `null` сохраняют исключение до пересмотра зависимостей. Автор и момент записи назначаются сервером. `startWorkCritical` указывает обязательность позиции для начала работ, общий вывод фиксируется самостоятельной командой.

Вопрос содержит `id`, `version`, `dependencyVersion`, `requirement`, `machine`, `decision`, `previousDecisionId` и `outcome`. Исходы вопроса: `covered`, `confirmed_missing`, `confirmed_conflict`, `needs_review`, `excluded`. Исходы области: `sufficient`, `confirmed_problems`, `needs_review`, `mixed`. В `machine` раздельны `delivery` (в том числе `received_in_other_format`), `readability`, `limitations`, `receiptIds`, `citations` и при доказанной непередаче `inventory`. Цитата содержит `observationId`, `evidenceId`, `receiptId`, `documentId`, `versionId`, `sha256`, `address`, `quote`, исходные `value` и `unit`, ветвь и `href`. Конфликт содержит все подтверждённые адресуемые опоры сопоставимого утверждения, начиная с пары, установившей расхождение. Для одного значения в одной версии оригинала сохраняется одна цитата, включая совпавшие чтения A/B и эквивалентные единицы. Формат и значения в текст письма преобразует шаг 6.

Проверка на стенде описана ниже. Для первого UI-сценария откройте пустой каталог, затем закрепите каталог с плоскими строками `{ key, part, applicability, formats, equivalents, sourceRoles, completenessCriterion, addressee }` по контракту шага 2. `applicability` принимает общее правило `all`, имя выбранной области, название стадии, `scope:<UUID>` или `stage:<название>`. Незнакомое выражение видно как `applicability_unknown`. Синтетический пример с двумя значениями относится к разным действующим адресам северного фасада. Южный остаётся на внутренней проверке. После смены формата старая версия доступна из истории.

## Порты для шагов 2, 3, 4, 6, 7 и 12

- Шаг 2 владеет каталогом, областью и настройкой состава. Модуль сверяет их актуальные версии на текущем чтении и допуске. Для фиксации каждой смены каталога, включая промежуточную смену между чтениями, доступен `refreshScopeAssessment(tx, projectId, scopeId)`. Владелец команды каталога вызывает его после изменения, под общим замком, если нужна синхронная публикация новой оценки. Для команды, которая вызывает этот порт или блокирует области, порядок блокировок при совместной интеграции начинается с `lockIntakeProject(tx, projectId)`. Затем выбираются строки областей в порядке UUID.
- Шаги 3 и 7 владеют причинами удержания. Модуль использует тот же порядок `lockIntakeProject` → `lockProjectScopes` → `getIntakeGate`, что при декларации и допуске к актуальному письму. При действующей причине команда возвращает 409 `scope_held`. Пустая сессия загрузки оценку не меняет. При закрытии одной причины шаг 7 сначала применяет установленные изменения к вопросам в той же транзакции. Другая действующая причина продолжает удерживать область. Версии независимых вопросов и фасадов сохраняются. Публикуется событие `assessment.changed` с ID области и номером оценки.
- Шаг 4 владеет доказательством. Модуль берёт сохранённое наблюдение по ID, проекту и области, сверяет хэш с картой оригинала и восстанавливает адрес, точную цитату, исходные величину и единицу. Из таблиц шага 12 исключаются замещённые версии. Черновые кандидаты без проверенного адреса не дают основания письма.
- Шаг 6 импортирует `selectConfirmedGrounds(tx, { projectId, scopeId, recipient?, items? })`. `items` — `{ questionId, questionVersion, decisionId }[]`. Возвращается `{ assessmentVersion, scope, holds, items }` с неизменяемым ядром и цитатами. Без `items` и `recipient` это просмотр доступных оснований. При удержании просмотр возвращает пустую выборку и причины. Для попытки допуска по адресату или явному списку активное удержание даёт 409, устаревшая ссылка — 412 `letter_basis_stale`. Явно пустой список даёт пустой результат. Шаг 6 отвечает 422 `no_eligible_items` и не создаёт письма. Исторический путь читает сохранённый снимок.
- Шаги 7 и 12 вызывают `applyAssessmentUpdate(tx, { projectId, scopeId, eventId, reason, changes })`. Для открытия пересмотра передайте `{ questionId }`. Для результата передайте `{ questionId, expectedDependencyVersion, review: { inputGeneration, remaining, completenessChecked, findings, inventory? } }`. Каждый `finding` задаёт `{ observationId, kind, sourceRole, comparisonKey, applicability }`. `comparisonKey` — общий ключ проверенного предмета, исполнения, условий и приоритета. Значения `kind`: `value`, `delivery`, `absence`. Значения `applicability`: `active`, `superseded`, `unknown`. Старая версия зависимости или входов возвращает 412. Совпадающий повтор события возвращает прежнюю версию. Вычисленное исследованием поколение сверяется под тем же замком. Формат `Review` с полными цитатами дополнительно поддерживается внутренними вызывающими сторонами при свободном шлюзе intake.
- Для доказательства нехватки `inventory` включает `assessmentId`, `kind: "explicit_non_delivery" | "exhaustive_inventory"`, `receiptIds`, `currentCompositionChecked` и `alternativesChecked`. Проверка чтений связывает фразу о непередаче с конкретным требованием или адресным исчерпывающим составом. Модуль повторно проверяет закрытие описи, ограничения распаковки и отсутствие пропущенных применимых поставок. Значение из требуемого или эквивалентного формата и неопределённая применимость блокируют внешний запрос о нехватке.

## Автоматическая проверка

Выполните сборку сервера и миграции на новой отдельной базе. Затем запустите `ASSESSMENT_TEST_DB=1 node --test src/modules/assessment/assessment.test.mjs`. Тест использует штатные Fastify, PostgreSQL, intake, reader и письма. Синтетические оригиналы генерируются в тесте. Внешние вызовы не выполняются. При параллельной разработке `ASSESSMENT_TEST_MODULES_ONLY=1` запускает только штатные модули access, intake, pdf, assessment, supplements и letters с теми же HTTP-маршрутами.

## Явное свидетельство непередачи · стык шага 9

Единая передача от worker использует `kind: "absence"` и `nonDelivery: { kind: "explicit_non_delivery", subjectQuote, questionId, receiptId }` на той же записи `finding`. Наблюдение хранит целиком дословное утверждение из открытого текстового фрагмента. `subjectQuote` — дословное название предмета внутри этого утверждения. Протокол 2 инструмента читателя принимает `deliveryStatement: { status: "not_delivered", item, context? }` вместе с полной цитатой. В `item` передаётся дословное название предмета, а в `context` при необходимости передаются `{ lineId, quote }` из того же чтения. Поля `value` и `unit` остаются пустыми. Worker переносит `item` в `subjectQuote` и подставляет ID назначенного вопроса и поступления из сохранённого адреса. Assessment сверяет тип с записью, закреплённой reader. Роль такого источника — `inventory`, `receipt_inventory` или `transmittal`. Роль указывается по назначению фрагмента. Ссылка на документ, запрет применения, условие будущей передачи, отрицание об ином предмете и запись из прежней поставки сами по себе остаются обычными наблюдениями либо открытой проверкой. Тип передаётся только после чтения полного утверждения о конкретном предмете текущей поставки.

В `applyAssessmentUpdate` worker передаёт этот же `nonDelivery` с `observationId` и добавляет в `review` серверный `researchGenerationId` из текущего задания. Для этой передачи worker оставляет `inventory` пустым. Assessment строит подтверждённый состав из БД по текущему поколению и заново проверяет совместимость с каталогом, областью, редакциями, закрытием описи и результатами обхода альтернативных оригиналов. Для внешнего основания нужны две независимые ветви на одном применимом утверждении. Новые или неразобранные входы удерживают допуск. Положительное утверждение об этом предмете требует проверить предъявленные оригиналы. Появление нового применимого оригинала отправляет прежнее основание на пересмотр с причиной `research_inventory_changed`. Обычный `value`, даже с буквальной строкой «не передана», никогда не преобразуется в `absence`. Прежний порт `inventory` остаётся для уже проверенного перечня вне worker.

Для приёмочной строки «Схема герметизации верхнего торца в текущей поставке не передана.» передаются полная цитата, `subjectQuote: "Схема герметизации верхнего торца"` и роль документа поставки. В этом каталоге роли требуемого чертежа — `drawing`, `reference`, `scheme`. Роли описи и сопроводительного сообщения разрешаются для типизированного утверждения отдельно от ролей самого чертежа. Числовой или строковый `value` в расчёте такого свидетельства не участвует. Для отрисованного фрагмента требуется получить адресуемую текстовую опору. Пересчитайте оценку после изменения состояния последнего обязательства A/B, даже если состав ID наблюдений совпал.

## Адрес и редакция источника для письма · стык шага 6

`Citation.address` и `versionId` сохраняются в основании для каждой цитаты. Для TXT точную строку берите из `address.locator.line`, а для DOCX используйте `table`, `row` и `column`. Технический UUID редакции остаётся в `versionId`. Обозначение из документа передаётся отдельно в опциональном `documentRevision: { label, quote, address, evidenceId }`. У него собственный адрес шапки, а адрес утверждения остаётся в `Citation.address`.

Шаг 5 предоставляет `createDocumentRevisionReader(reader)` в `assessment/document-revision.js` и принимает его результат как `readDocumentRevision` в опциях `selectConfirmedGrounds`. Шаг 6 создаёт штатный reader через `createRuntimePdfService(app.db, app.config)` и передаёт функцию в порт. Она читает только сохранённые хэш-сверенные текстовые представления той же версии оригинала. Поле появляется при новом отборе основания, в том числе для сохранённого инженерного решения, если сохранилась однозначная шапка. TXT допускает исходный заголовок с полями «название · стадия · обозначение», PDF и DOCX — явно отмеченную редакцию в начальной шапке. Поля сохранённого решения и прежнего снимка письма читаются по собственной версии.

## Повторная сверка и адресное обновление · стык шага 12

`applyAssessmentUpdate` получает полный результат по каждому указанному `questionId` и сверяет `expectedDependencyVersion` под замком области. Повторный обход с теми же применимыми фактами сохраняет версию вопроса и решение. Входной номер поколения, порядок находок и новые ID чтений того же источника сами по себе не меняют основания. Для защищённого удержанием решения промежуточные причины `inventory_open`, `primary_coverage_pending` и `dispute_pending` означают ожидание результата. При явном замещении версии источника `refreshScopeAssessment` оставляет независимые опоры того же вопроса, а решение переносит в историю. `review: null` остаётся явной командой пересмотра указанного вопроса.

Для автоматической классификации шага 12 завершение обхода берётся из текущего поколения и обязательств gateway. Последняя версия оценки при отсутствии предметного изменения может принадлежать более раннему поколению входов. Проверки `source_token`, состава затронутых вопросов и версии в самой команде продолжают действовать.


## Состав подтверждённого конфликта · стык шага 6

`Ground.citations` содержит все действующие документальные опоры для сопоставимого утверждения в области вопроса. Пара разных значений по-прежнему задаёт вывод о конфликте. В итоговом составе одна версия одного оригинала даёт одну опору на каждое отдельно установленное значение. Сохраняются исходные величина, единица, адрес и версия. При новом подтверждении сохранённой проверки оценка использует весь её действующий состав. Явно выбранные инженером опоры при исправлении определяют границы его основания. Сохранённые оценки, решения и снимки отправок продолжают читаться по своим версиям.
