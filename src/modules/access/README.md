# Доступ и команды · шаг 2

## Контракт соседних модулей

Импорт из `../access/index.js`. Серверный реестр вызывает `register(app)` с общим `app.db: pg.Pool`.

- `requireAccess(db, request, requirement)` проверяет действующий сеанс и возвращает субъект `{ userId, organizationId, sessionId, role }`. Для проекта передавайте `{ action: "project:read" | "project:engineer" | "project:manage", projectId }`. Для служебной команды используйте `{ action: "operator:diagnose", organizationId }`. Для организационных действий существуют `organization:admin` и `organization:create-project`. Используйте `{ action: "session" }` для проверки входа без предметного допуска.
- ID проекта для непрямого маршрута берётся из связи объекта в БД. После проверки обращайтесь к данным по паре объекта и проекта. UUID и хэш объекта сами по себе права не дают. Не возвращайте данные или сведения о чужих объектах до проверки. Используйте нейтральный 404 для чужого проекта, 403 для запрета действия на доступном проекте.
- `executeCommand(db, request, { operation, requirement, input, version? }, async (tx, actor) => ({ body, status?, audit? }))` возвращает `{ status, body, replayed }`. `input` — проверенный JSON, включая параметры цели и всё, влияющее на исход. `version` — функция `(tx, actor) => Promise<{ current: number, href?: string, details?: … }>` для правки с `If-Match`. Захватывайте предметные блокировки в этой функции до чтения версии. При подтверждении зависимостей воспользуйтесь `lockProjectScopes(tx, projectId, scopeIds)`. Блокировки действуют до конца транзакции. Доменная запись, аудит и квитанция выполняются через переданный `tx`. Вызовы внешних систем делайте из отдельного обработчика устойчивого намерения. Тело квитанции содержит устойчивый ID и исход, без защищённого текущего текста, эфемерных ссылок и секретов.
- `lockProjectScopes(tx, projectId, scopeIds)` блокирует существующие строки `project_scopes` в порядке UUID, проверяет принадлежность всех ID и возвращает строки `id, projectId, stage, name, version`. Порядок для входов, подтверждений и текущего экспорта одинаков. Удержания и поколения входов принадлежат соседним шагам. Храните их в своих таблицах с FK на область. Для входа с неизвестной применимостью вызывайте `lockProjectScopes(tx, projectId)`, чтобы заблокировать набор областей целиком вместе с созданием новой области.
- В PostgreSQL используются `organizations(id)`, `users(id, organization_id)`, `projects(id, organization_id)`, `project_memberships(project_id, user_id)`, `project_scopes(id, project_id)`. Миграция `02_access_schema.sql`.
- Перед выдачей объекта, при запросе Range и на каждом цикле подписки проверяйте право заново. При утрате права закрывайте подписку. Для потока, который пишет заголовки в raw response, явно назначайте `Cache-Control: no-store`. Хук API устанавливает этот заголовок для штатных ответов Fastify, включая ошибки.
- `transaction(db, work)` передаёт один `pg.PoolClient` и закрывает транзакцию после результата или ошибки. Проверяйте доступ для HTTP-действий через `requireAccess` или `executeCommand`.
- `writeAudit(db, event)` записывает `actorId, organizationId, projectId, role, action, objectId, version, outcome, requestId, details`. Для атомарного успешного действия передавайте клиент той же транзакции. В `details` допускаются служебные поля события.
- `projectActions(role)` возвращает список проектных действий для интерфейса. `requireMutationProtection(request)` проверяет Origin и CSRF для HTTP-мутаций, которые пользуются отдельным исполнителем.
- `AccessError` имеет `statusCode` и `code`. Формат ошибки `{ code, message, requestId }`, для 412 возможны `currentVersion, href, details`.
- При мутации с cookie передавайте `X-CSRF-Token` из сессии и Origin того же приложения. Идемпотентный повтор возвращает исходный статус и тело. Иное тело или `If-Match` под тем же ключом дают 409. Новая правка со старой версией — 412. Клиент посылает сильную версию в кавычках, например `If-Match: "3"`.

## Браузер

Пути под `/api`, сессия в HttpOnly cookie `facade_session`.

| Метод и путь | Вход и результат |
| --- | --- |
| POST /sessions | `{ login, password }` → `{ user, csrfToken }`. Устанавливает cookie |
| DELETE /sessions/current | Отзывает сеанс и очищает cookie |
| GET /me | `{ user, csrfToken, actions, projects }`. Сверка активной вкладки и возврата из истории |
| POST /invitations/complete | `{ token, password }`. Активация приглашения |
| POST /password-resets/complete | `{ token, password }`. Сброс и отзыв прежних сеансов |
| POST /projects | `{ mode: "intake", name }` или прежний вход `{ name, catalogVersionId, stage?, scopeName? }` → проект. Инициатор становится владельцем |
| GET /projects/:projectId | Проект, роли и действия текущего пользователя, области и закреплённый каталог |
| GET /projects/:projectId/members | Версия членства и список участников для владельца |
| PUT /projects/:projectId/members/:userId | `{ role }`, при временном назначении также `expiresAt, reason`. Версия проекта через If-Match |
| DELETE /projects/:projectId/members/:userId | Снимает право, проверяет версию проекта |
| PUT /projects/:projectId/catalog | `{ catalogVersionId }`. Версия проекта через If-Match |
| GET /projects/:projectId/catalog-options | Варианты назначения и причина для владельца проекта |
| PUT /projects/:projectId/stage | `{ stage, reason, evidenceIds? }`. Владелец проекта, If-Match проекта |
| GET /projects/:projectId/versions/:versionId/stage | Стадия редакции или адреса из `?evidenceId=` |
| PUT /projects/:projectId/versions/:versionId/stage | `{ target: "document" \| "place", stage, reason, evidenceId }`. Инженер, If-Match цели |
| POST /projects/:projectId/scopes | `{ stage, name }` → область |
| PUT /projects/:projectId/scopes/:scopeId/requirements | `{ requirements }`. Версия области через If-Match |
| GET /catalogs | Доступные версии каталогов организации |
| POST /catalogs | Новая неизменяемая версия каталога, роль администратора |
| POST /users/invitations | Выпуск одноразового приглашения |
| POST /users/:userId/password-resets | Выпуск токена сброса |
| POST /users/:userId/revoke-sessions | Отзыв сеансов |
| PATCH /users/:userId | Организационные назначения/отключение |

### Первичный приём и рабочий профиль

- Новый проект в режиме `intake` сохраняет `catalogVersionId: null`, `catalog: null`, `catalogState: "unassigned"`, `stage: null`, `stageStatus: "unknown"`, `confirmedFacadeKinds: []` и `scopes: []`. Сеанс менеджера видит проект сразу. Приём и первичное чтение используют право уровня проекта. Операция редактирования требований без рабочей версии возвращает `catalog_required`.
- У прежнего проекта области сохраняют исторический `stage`, включая автоматически записанное `design`. `stageStatus: "legacy_unconfirmed"` обозначает отсутствие подтверждения на уровне проекта. Пустое старое закрепление читается как `catalogState: "legacy_empty"`. Назначение через прежний API сохраняет старые версии оценки. Новое явное подтверждение стадии возвращает `stageStatus: "confirmed"`. Документ или место имеют собственный ETag, начальное значение `"1"`. Адрес для места извлекается из сохранённого доказательства именно этой редакции. История подтверждений записывается в `access_audit`. Подтверждение редакции или места не изменяет стадию проекта и ACL.
- После утверждения предметной матрицы и сценария владельцем продукта администратор публикует непустой каталог через `POST /api/catalogs`. Дополнительное поле `defaultProfile: { stage, facadeKinds, approvalReference }` связывает версию с точным кодом стадии, множеством устойчивых кодов **типов** фасадов и ссылкой или номером решения владельца. Это запись организационного утверждения под ответственностью администратора. Обычная публикация без этого поля сохраняет прежний контракт. Установочная миграция не публикует прикладных требований.
- Поле строки `level` может принимать `"facade"` для экземпляра требования по каждому фасаду и `"common"` для одного экземпляра на общем уровне. Отсутствие поля сохраняет прежний формат строки и её правило области.
- `updateConfirmedFacadeKinds(tx, { projectId, expectedVersion, facadeKinds, actor })` вызывается из авторизованной команды `executeCommand` с `project:engineer` или `project:manage` в транзакции подтверждения фасадов, до других блокировок области или строки проекта. Передавайте полный актуальный набор достоверно подтверждённых кодов типов после правки. Кандидаты, названия фасадов конкретного проекта и ACL не являются кодами профиля. Хук сохраняет состояние применимости, повторяет разрешение и возвращает новую версию проекта. При устаревшей версии вся команда получает 412.
- Разрешение проверяет актуальные стадию и типы фасадов после подтверждения и при публикации профиля. При единственном точном совпадении непустая утверждённая версия закрепляется, если проект в режиме `intake` и закрепления ещё нет. При неоднозначности `catalog-options` возвращает все подходящие версии постранично. Менеджер может сменить закрепление явной версионируемой командой. В оценке `getProject` и `getCatalog` из `project-state.js` читают текущую конфигурацию, а `matchesDefaultProfile(project, catalog)` показывает, подходит ли ранее закреплённый профиль режима `intake` при новых подтверждениях. Команды доступа не планируют работу reader.

Проверка текущего права для уже открытого проекта — `GET /api/projects/:projectId`. По 401/404 очищайте защищённое состояние вкладки, запросы, подписки и объектные URL. Окно показа без успешной проверки — 30 секунд.

### Форматы и сценарии браузера

- `GET /me` возвращает `user: { id, organizationId, login }`, `csrfToken`, организационные `actions` и `projects: [{ id, name, version, role, scopeId, actions }]`. Разрешения проекта — `project:read`, `project:engineer`, `project:manage`. Пользователь с временным доступом к одной области открывает `GET /projects/:projectId/scopes/:scopeId` и запросы модулей, которые явно проверяют эту область. `GET /projects/:projectId` требует охвата всего проекта.
- `POST /projects` по умолчанию создаёт стадию `design` и «Общую область». Для явного выбора используйте `{ name, catalogVersionId, stage, scopeName }`. Успешный ответ содержит `id, organizationId, name, catalogVersionId, version, scopes`. При чтении добавляются `catalog, role, actions`. Списки пользователей, проектов, участий, областей и каталогов отдают `nextCursor` и принимают `?cursor=`.
- Каталог публикует администратор через `POST /catalogs` с `{ key, name, requirements }`. Сервер присваивает возрастающую `revision` для этого ключа и новый `id`. Владелец закрепляет точный `catalogVersionId`. Требование имеет `{ key, part, formats: string[], equivalents: string[], applicability, sourceRoles: string[], completenessCriterion, addressee }`. Смена закреплённой редакции переводит области на требования новой редакции и повышает их версии. Команда через порт оценки сохраняет предыдущий и новый снимки каждой области и публикует события в той же транзакции. Если предыдущий снимок уже соответствует области, модуль оценки переиспользует его. Повтор команды и закрепление уже выбранной редакции не создают новых снимков. Прежние настройки доступны по сохранённым версиям в `scope_requirements`. Соседние модули получают действующие требования через версию области и закреплённый каталог.
- Владелец назначает участника через `PUT /projects/:projectId/members/:userId`. Ответ `{ member, version }`. Значение `project_manager` передаёт владение, прежний владелец становится инженером. Администратор организации выполняет передачу через `PUT /projects/:projectId/owner` с `{ userId }` и `If-Match` проекта. Служебному оператору доступ к содержимому выдаётся отдельно через `{ role: "viewer", expiresAt, reason, scopeId? }`. Сеансы пользователя с изменёнными назначениями отзываются. Новый вход выдаёт новый идентификатор.
- `GET /users` возвращает учётные записи организации администратору. `POST /users/invitations` принимает `{ login }`. Приглашение и сброс возвращают `{ id, userId, expiresAt, token }` при выдаче. Повтор по тому же ключу возвращает метаданные квитанции. При потере ответа новый ключ выпускает новый токен и отзывает прежний. Пароль меняется также через `POST /password/change` с `{ currentPassword, password }` и CSRF. Команда отзывает все сеансы пользователя и токены сброса.
- Для теста используйте только синтетические роли и токены. Вход владельца, публикация каталога, закрепление, назначение инженера, вход инженера, проверка просмотра и отзыв описаны в [исполняемом HTTP-сценарии](../../../test/access.integration.test.mjs). Запросы к связанным оригиналам, выгрузкам и событиям подключают соответствующие модули.

## Установка и проверка

После миграций первый администратор создаётся один раз командой `node dist/src/modules/access/bootstrap.js "Организация" "admin"`, пароль передаётся через защищённый stdin. Логин приводится к нижнему регистру после NFKC и проверки допустимых ASCII-символов. Начальный профиль Argon2id v19 использует 19 МиБ, 2 прохода и 1 канал. Сеанс имеет абсолютный срок 8 часов и срок бездействия 30 минут. Приглашение действует 24 часа, сброс — 30 минут. Окно входа 15 минут с пределами 8 попыток на логин и 30 на источник. Настройки задаются переменными `FACADE_SESSION_ABSOLUTE_SECONDS`, `FACADE_SESSION_IDLE_SECONDS`, `FACADE_INVITE_SECONDS`, `FACADE_RESET_SECONDS`, `FACADE_LOGIN_WINDOW_SECONDS`, `FACADE_LOGIN_ACCOUNT_LIMIT`, `FACADE_LOGIN_SOURCE_LIMIT`.

Для TLS задайте внешний origin, например `FACADE_PUBLIC_ORIGIN=https://127.0.0.1:18443` на стенде. Сервер ставит `Secure` для заданного HTTPS-origin. Без внешнего origin поддерживаются запросы с совпадающими Origin и Host на loopback, включая адрес `http://127.0.0.1:18080`. Источник для ограничения входа — `request.ip`. За TLS-прокси доверенные адреса должны быть настроены на уровне Fastify или развёртывания, иначе клиенты прокси делят лимит источника.

Проверка в собственной новой БД с применёнными миграциями:

```sh
npm run build:server
npm run migrate
FACADE_ACCESS_TEST=1 node --test test/access.integration.test.mjs
```

Для отдельной сборки модуля и платформы можно передать каталог вывода через `FACADE_ACCESS_BUILD_DIR`. Тест запускает обычный Fastify API на временном локальном порту и пользуется PostgreSQL со своими синтетическими данными.

### Блокировки и квитанции

Запрашивайте все нужные области одним вызовом. В рабочей транзакции порядок — организационная блокировка доступа, блокировка сеанса, ключ квитанции, затем (для зависимостей входов) `lockIntakeProject`, `lockProjectScopes`, зависимые строки. После вызова для отдельных областей не расширяйте ту же транзакцию до блокировки всех областей. Внутри `executeCommand` используйте `authorizationWrite: true` для действий, которые меняют полномочия или отзывают сеансы. Если квитанция ссылается на ресурс с отдельным правом чтения, проверьте это право в `authorizeReplay(tx, actor, storedBody)`. Например, при повторе создания проекта после передачи владения сервер проверяет доступ к созданному проекту.

Если соседний обработчик использует свой обработчик ошибок, `sendAccessError(error, request, reply)` передаёт клиенту разрешённые подробности 412. Для проектного чтения `requireAccess` принимает дополнительный `scopeId`. Передавайте его только после определения точного связанного объекта в БД. Все запросы с мутацией через `requireAccess` и `executeCommand` проходят CSRF даже при отдельной регистрации модуля.
