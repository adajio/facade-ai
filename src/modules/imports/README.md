# Импорт и раскрытие архивов · шаг 10

## Браузер и автоматическая проверка

Маршруты относительны `/api`. Запись требует доступа инженера, сеанса, CSRF и `Idempotency-Key`. У чтения действует проверка проектного доступа.

| HTTP | Вход и результат |
| --- | --- |
| POST /receipts/:receiptId/imports | `{url, scopeIds?}` → 202 `{importId, receiptId, status: "queued"}`. Без `scopeIds` применимость пока неизвестна. |
| GET /receipts/:receiptId/imports | `{imports: Import[]}` с текущими состояниями импорта. |
| POST /receipts/:receiptId/imports/:importId/cancel | `{}` → `{importId, status: "cancelled"}` либо 409 после приёма материала или при активном импорте. |
| GET /receipts/:receiptId/import-inventory | `{entries, nextCursor}` с техническими узлами, цепочками путей и исходами импорта и архивов. Параметры `limit`, `cursor`. |
| GET /imports/capabilities | Поддерживаемые каналы и форматы, лимиты распаковки и ожидаемая изоляция. Лимит передачи, размер части и срок докачки отдаёт шаг 3. |

`Import` содержит `importId, status, reason, unknownRemainder, directUploadAvailable, updatedAt`. Первичные состояния `queued, running, paused, completed, limited, failed, cancelled`. Пауза сохраняет принятые части. Для закрытого исхода с неизвестным остатком используется `limited`. `completed` у импорта относится к передаче источника. Состояние раскрытия показывает опись контейнера. Для недоступной, отозванной или защищённой ссылки интерфейс предлагает прямую загрузку. Список поступлений, выбор папки с исходными относительными путями, карта частей и доступ к неизменяемым оригиналам остаются на API шага 3.

Сценарий R01 для интеграции. Остановить обработчик импорта, вызвать POST для двух отдельных досылок с одним проектом и областью, до первого байта проверить текущую выдачу и предыдущий отправленный снимок. Отменить первую из очереди, проверить продолжение удержания второй, затем отменить вторую и проверить восстановление прежнего допуска. После публикации синтетического оригинала отмена по этому маршруту возвращает 409. Пароль и URL скачивания не передаются в ответах и журналах.

## Стыки backend

- Шаг 1 и 8. `startImports(context: WorkerContext): Promise<void>` включается в отдельном worker вместе с harness, с общим `AbortSignal`. HTTP-регистрация только подключает маршруты. Штатный загрузчик Яндекс.Диска не использует учётные данные и платный шлюз.
- Шаг 3. Вызывает `queueArchive(tx, input)` из `archive-queue.ts` в транзакции публикации контейнера, с `{projectId, receiptId, occurrenceId, versionId, relativePath, mediaType}`. Возвращённое `true` устанавливает `inventoryPending` до окончания раскрытия. Для бинарных данных предпочтителен физический тип, затем MIME/суффикс как подсказка. Очередь хранится в PostgreSQL.
- Шаг 3. Модуль использует транзакционные `declareImport/updateImport/cancelImport`, а для каждого файла — `declareOriginal/writePart/finalizeOriginal/openOriginal/completeOccurrenceInventory`. Вхождение импортированного файла связано с `importId`, а дочернего — с `parentOccurrenceId`. Для повторов нужна устойчивая идентичность декларации от задания и номера узла; путь не уникален. Согласование точных сигнатур следует контракту `intake`.
- Шаг 8. Для горизонта 4/16/200 распаковка использует общий тяжёлый слот, а временные байты резервируются до запуска дочернего процесса. Нужны экспорт резерва диска с учётом резерва загрузки и идентификатор общей блокировки слота.

## Запуск распаковщика

```sh
docker build -t facade-v11-import-extractor:step10 src/modules/imports
docker image inspect facade-v11-import-extractor:step10 --format '{{.Id}}'
```

ID образа служит значением `FACADE_ARCHIVE_IMAGE` у [брокера конвертеров](../converter-port/README.md). Worker получает только путь к сокету `FACADE_CONVERTER_SOCKET` и передаёт по нему проверяемый поток оригинала. Одноразовый контейнер читает seekable файл `/source`. Аргументы его entrypoint задают максимальные раскрытые байты, число элементов и время в секундах. Формат его stdout подтверждается транспортной квитанцией брокера. Используется один слот распаковки и тяжёлого чтения с DB-ключом `hashtextextended('facade/heavy-local-slot', 0)`. Если брокер недоступен, архивы остаются на паузе с `archive_isolation_unavailable`.

Пиковые байты передачи, временного раскрытия и публикации учитываются под общей блокировкой диска приёмки. Экспорт для шага 3 — `importScratchUnwrittenBytes(tx)` из `reserve.ts`. Шаг 3 учитывает зарезервированные частями байты и место на оригинал, шаг 10 добавляет предстоящие записи во временную рабочую область. Квалификация общего ресурса 4/16/200 относится к шагу 14.

Для Яндекс.Диска модуль использует публичный API и отдельно проверяет HTTPS-хост, DNS-адрес и каждое перенаправление. На контейнерной установке `FACADE_IMPORT_HTTPS_PROXY` указывает на ограниченный CONNECT-прокси. Прокси проверяет и закрепляет публичный IPv4, а worker проверяет сертификат исходного HTTPS-хоста. Отказ прокси завершает попытку. Внешний транспорт в тесте управляется синтетическим сценарием. При обрыве повтор сверяет хэши подтверждённых частей и повторно записывает только отсутствующие. Если ответ источника изменился, сохраняется причина ограничения. При пустой отмене состояние удержания и запись задания меняются в одной транзакции шага 3.

## Контрольные сценарии

`GET /api/receipts/:receiptId/archive-inventory/:occurrenceId` возвращает `{occurrenceId, versionId, depth, state, reason, unknownRemainder}`. Для списка узлов только этого контейнера задайте `sourceId=occurrenceId` на маршруте `import-inventory`. Поля узла `sourceId, containerOccurrenceId, parentId, originalPath, relativePath, kind, ordinal, status, reason, size, sha256, mediaType, occurrenceId, versionId, uploadId` позволяют связать технические записи с обычной описью. Для отображения неподходящего исходного имени используйте `originalPath`, даже если безопасный `relativePath` отсутствует. Клиент показывает оригинал через `documentId/versionId` штатной описи. Закрытый исход контейнера с ограничением сохраняет `unknownRemainder` и причину, открытый контейнер остаётся в описи.

```sh
IMPORTS_TEST_BUILD="$PWD/dist" IMPORTS_TEST_DB=1 \
  FACADE_CONVERTER_SOCKET=/path/to/converter.sock \
  node --test src/modules/imports/imports.test.mjs
```

Для прогона нужны выделенный синтетический PostgreSQL с миграциями, приватный S3-бакет стенда и брокер с настроенным образом распаковщика. Набор генерирует ZIP/RAR/7z, использует локальные `python3`, `bsdtar` и `zip`. Тест R01 обращается к маршрутам текущего экспорта и отправленной истории, загружая подтверждённые основания из синтетической фикстуры. Проверка ранней доступности подтверждает неизменяемый оригинал и задачу reader до закрытия описи. Качество первой находки проверяется совместно с этапами reader и harness.
