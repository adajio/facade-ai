# W3.1. Профиль внешнего S3 и проверка приёма

## Профиль

API и offline worker используют один закрытый бакет через `FACADE_S3_ENDPOINT=https://s3.example.net`,
`FACADE_S3_BUCKET`, `AWS_REGION` (регион S3) и учётные данные SDK из защищённого окружения.
На внутреннем TLS-прокси сохраняются Host и путь подписанного запроса. При частном CA перед запуском Node
задайте `NODE_EXTRA_CA_CERTS` с файлом цепочки доверия. Публикуется только HTTPS-интерфейс S3 для серверных ролей.
Браузер получает оригиналы через авторизованный API приложения. На хосте приложения нужен постоянный
`FACADE_DATA_DIR` с `intake-parts`, доступный процессам, которые принимают, публикуют и очищают загрузки.
Хранилищу нужен собственный запас места и срок очистки незавершённых S3 multipart. [TLS Garage](https://garagehq.deuxfleurs.fr/documentation/cookbook/reverse-proxy/)

### Локальная проверка S3

Из корня соберите сервер, выделите окружение по [инструкции стенда](README.md#отдельная-база-для-проверки) и запустите
локальный TLS-прокси в отдельном терминале. Он соединяется с уже запущенным Garage через выделенный loopback-порт стенда.
Это проверяет путь SDK → TLS → Garage 2.5.0. Прокси пишет статус и байты HTTP-тел по запросам.

```bash
npm run build:server
db_env="$(infra/test-stand/stand new-db step3_w31)"
source "$db_env"
```

```bash
umask 077
mkdir -p .local/w31
openssl req -x509 -newkey rsa:2048 -nodes -sha256 -days 7 -subj /CN=127.0.0.1 \
  -addext 'subjectAltName=IP:127.0.0.1' \
  -keyout .local/w31/s3-key.pem -out .local/w31/s3-cert.pem
node infra/test-stand/intake-s3-tls.mjs 19431 .local/w31/s3-cert.pem .local/w31/s3-key.pem \
  > .local/w31/s3-tls.jsonl
```

Там, где загружен `db_env`, задайте endpoint и доверие. Для отдельного внешнего S3 укажите его посвящённый испытанию
бакет и TLS-endpoint. Проверка создаёт и в конце удаляет только свои ключи с префиксом `qualification/`.

```bash
export FACADE_S3_ENDPOINT=https://127.0.0.1:19431
export NODE_EXTRA_CA_CERTS="$PWD/.local/w31/s3-cert.pem"
node --test infra/test-stand/intake-s3.test.mjs
node --test src/modules/intake/intake.integration.test.mjs
```

Первый тест проверяет подписанные PUT, multipart, HEAD, Range, полный SHA-256, отказ анонимного GET и условное
создание по занятому ключу. Второй проверяет прикладной путь через отдельную свежую БД
`step3`, включая сохранение частей при перезапуске API, откат публикации, конкурентное завершение и доступ к старой версии.

Garage 2.5.0 на локальном стенде принял повторный PUT и повторное завершение multipart при `If-None-Match: *`.
Это открытый критерий квалификации провайдера. Прикладная публикация сериализована по ID загрузки в PostgreSQL, проверяет
наличие объекта по неизменяемому ключу и повторно использует подтверждённую публикацию. Смена провайдера или принятие
гарантии на уровне приложения требуют решения о том, кто ещё имеет право записи в бакет и какая гарантия нужна от самого S3.

## Докачка и пик диска

Поднимите отдельный API и при проверке браузера добавьте offline worker с той же синтетической БД, бакетом и каталогом
данных. Для нативной карты одностраничного PDF нужны штатные инструменты reader. Укажите origin и учётную запись теста
в `FACADE_STEP14_LOGIN`, `FACADE_STEP14_PASSWORD` или в `FACADE_E2E_ADMIN_LOGIN`, `FACADE_E2E_ADMIN_PASSWORD`.

### HTTP

```bash
python3 -B infra/test-stand/diagnose-intake.py \
  --origin "${FACADE_E2E_BASE_URL:?}" --transfer-mib 9 --rate-mib 1 \
  --disk-path "$FACADE_DATA_DIR" --staging-dir "$FACADE_DATA_DIR/intake-parts" \
  --scratch-dir "$FACADE_DATA_DIR/import-scratch" --scratch-dir "$FACADE_DATA_DIR/reader-scratch" \
  --evidence .local/w31/http-small
```

9 МиБ рассчитаны на настройку части 8 МиБ. При другом размере части задайте тестовый файл больше одной части.
Для пограничного режима в свободный тяжёлый слот замените `--transfer-mib 9 --rate-mib 1` на `--large --rate-mib 32` и
укажите новый каталог результатов. При частном CA прокси приложения передайте `--ca-file`. Сценарий проверяет
индивидуальный и суммарный предел +1 байт, обрыв посередине части, новую сессию, докачку, повтор завершения,
параллельный PDF второго проекта, HEAD, Range и полный потоковый SHA-256 скачанного оригинала.

`disk.jsonl` содержит замеры через 0,5 с и в контрольных точках. `disk-summary.json` фиксирует минимум свободных байтов
на выбранной файловой системе, выборочные максимумы выделенных байтов для каждого временного каталога и максимум их
суммы в одной пробе. Для scratch брокера добавьте его отдельный путь. Версия стенда и режимы конвертации должны войти
в протокол. Снятие выборки с диска приложения не включает диск внешнего S3. Для общей файловой системы
`free_min` отражает соседние процессы. Времена передачи и объём SDK ↔ S3 берутся из HTTP-лога и лога прокси
или метрик конечного S3. Сравнивайте пробы разных стадий одного запуска и учитывайте гранулярность выборки.

### Браузер

```bash
export FACADE_E2E_INTAKE_RESUME=1
export FACADE_E2E_OUTPUT="$PWD/.local/w31/browser-small"
npm --prefix web run test:stand -- intake-resume.spec.ts
```

Playwright передаёт одностраничный PDF и вложенный ZIP в одном поступлении, обрывает вторую часть ZIP, проверяет
нативную карту PDF, закрывает браузерную сессию и входит заново. Видны зафиксированный PDF и незавершённый вход.
Тест повторно выбирает тот же ZIP, проверяет отправку только неподтверждённых частей и сверяет итоговый SHA-256.
Для сценария ровно 10 ГиБ суммарно установите `FACADE_E2E_INTAKE_RESUME_LARGE=1` и отдельный каталог
`FACADE_E2E_OUTPUT` на внешнем SSD. Генерация входа требует ещё 10 ГиБ места на файловой системе браузерного теста.
Для совместного пика запустите команду Playwright через `diagnose-intake.py` с теми же дисковыми аргументами,
свежим `--evidence` и последним аргументом `--observe npm --prefix web run test:stand -- intake-resume.spec.ts`.
Установите `FACADE_E2E_INTAKE_ARCHIVE_SETTLE=1`, чтобы выборка продолжалась до закрытия описи. Для измерения
распаковки подготовьте выделенный брокер и по итоговой описи различайте успешно раскрытый архив и явное ограничение.
Следуйте [очерёдности тяжёлых проверок](README.md#очерёдность-тяжёлых-испытаний). Браузерная проверка карты PDF
покрывает физическую единицу и состояние открытого входа. Полное покрытие чтения по R04 предъявляется отдельно с
разрешённым сохранённым ответом reader и инженерной оценкой.

### Решение о потоке частей

Текущая схема хранит подтверждённые части локально. Перед публикацией она прочитывает их для SHA-256, загружает
в S3 multipart и перечитывает готовый объект для подтверждения. Перед допуском сервер учитывает
`2 × размер − подтверждённые байты` по незавершённым загрузкам плюс обещанный scratch и защитный остаток.
Эта оценка исходит из одного дискового пула. На внешнем S3 второе слагаемое за готовый объект резервируется на хосте
приложения консервативно, а реальный объект занимает диск S3.

Если на целевом профиле совместный пик частей, раскрытия и конвертации укладывается в выделенные ресурсы, сохраняется
нынешний поток. Если приём упирается в завышенный резерв, проверяется раздельный учёт приложенческого диска и S3.
Если упираются физические временные байты, сравнивается хранение частей в S3 с теми же условиями докачки и полного SHA-256.
Отдельными результатами остаются отказ связи с внешним S3, восстановление БД вместе с объектами и прежней опорой,
полная нагрузка двух проектов на конечной сети и допуск пилота.
