# Локальный стенд Facade AI

Стенд предназначен для синтетических проверок в этом рабочем дереве.
PostgreSQL 16.15 доступен по `127.0.0.1:15432`, закрытый S3 Garage 2.5.0 по `http://127.0.0.1:13900`.
Старт и изменения среды ведёт владелец стенда.

Действующий Linux-стенд для шагов 7, 13 и 15 открыт на [https://127.0.0.1:18443](https://127.0.0.1:18443).
На нём работает Git-срез `f11ac1b7685493fc164cb55c1598385fbf802f79`. Точные идентификаторы, результаты и границы
зафиксированы в [протоколе](RESULTS.md).

## Отдельная база для проверки

Из корня репозитория выполните команды в отдельном shell или subshell. Замените `step10` на имя проверки.

```bash
db_env="$(infra/test-stand/stand new-db step10)" &&
  source "$db_env"
```

Команда выдаёт путь к файлу с правами `0600`, содержащему `DATABASE_URL`, `FACADE_DATA_DIR`, `TMPDIR` и параметры S3.
Каждый запуск выделяет новую базу и роль, каталог прикладных файлов, отдельный бакет и ключ с правами на этот бакет.
Для проверки продолжения повторно загрузите тот же файл окружения.
Если база создана на первом этапе до добавления S3, добавьте бакет командой `infra/test-stand/stand add-s3 "$db_env"`.
Применяйте миграции и запускайте команды приложения в этом окружении, начиная с `npm run migrate` после сборки.
В тестах передавайте URL через окружение. Вывод команд и артефакты не должны содержать содержимое env-файла.

Локальный сертификат для `curl --cacert` и тестового браузера хранится в
`/Volumes/ADATA SE920/OrbStack/facade-ai-test-server/secrets/cert.pem`.
`http://127.0.0.1:18080/readyz` проверяет доступность API и его соединения с базой.
Для параллельной проверки с собственной базой можно запустить приложение локально с `HOST=127.0.0.1` и своим свободным `PORT`.
Такой запуск наследует сетевой доступ Mac. Для модельных проверок используйте закрытый стенд и согласованный управляемый транспорт.

Для автоматических проверок действующего стенда в его каталоге есть синтетический `step14_admin`.
Параметры берутся локально из защищённого файла.

```bash
stand_dir='/Volumes/ADATA SE920/OrbStack/facade-ai-test-server'
run_env="$(sed -n '2p' "$stand_dir/current-runtime")"
export FACADE_ACCEPTANCE_LOGIN=step14_admin
export FACADE_ACCEPTANCE_PASSWORD="$(cat "$(dirname "$run_env")/synthetic-admin-password")"
```

## Запуск сборки владельцем стенда

```bash
infra/test-stand/stand up
image="$(infra/test-stand/stand build)"
db_env="$(infra/test-stand/stand new-db release_smoke)"
infra/test-stand/stand migrate "$image" "$db_env"
infra/test-stand/stand run "$image" "$db_env"
infra/test-stand/stand status
```

API и worker используют один образ с серверной сборкой, миграциями и `web/dist`. Тэг фиксирует SHA-256 манифеста файлов
снимка общего дерева. Манифест и лог сборки сохраняются в `builds/` на внешнем SSD.
Для точного Git-среза используйте `stand build reader "$revision"`. Переменная `FACADE_STAND_EXPECTED_MANIFEST`
останавливает сборку до запуска Docker при несовпадении с согласованным хэшем.
Для начальной учётной записи передайте синтетический пароль на stdin команды
`infra/test-stand/stand bootstrap "$image" "$db_env" "Synthetic organization" acceptance_admin`.
Учётная запись создаётся один раз в новой базе.

Для повторного запуска последней поднятой сборки в закрытом режиме используйте
`infra/test-stand/stand resume`. Команда `infra/test-stand/stand stop-app` останавливает API, worker и их вспомогательные
сервисы, сохраняя общие PostgreSQL и S3 для компонентных проверок. `infra/test-stand/stand stop` останавливает весь стек
с сохранением томов, баз и ключей. Перед полной остановкой дождитесь завершения соседних проверок.
Свежий запуск базы использует `--no-recreate`. Переключение приложения использует `--no-deps` и оставляет общую БД в работе.

Контейнеры работают во внутренней сети Docker. У них нет опубликованных портов. На Mac TCP-реле слушает только loopback,
а HTTPS завершается локальным сертификатом. В конфигурации стенда отсутствуют ключи и живой маршрут OpenRouter.

## Журнал намерений и исходящие маршруты

### Серия шага 15 с нативным журналом

Нативный PostgreSQL для серии работает в macOS на `127.0.0.1:15435`. Его PGDATA лежит на ADATA SE920 в `step15/data`,
за пределами образа OrbStack. Отдельный relay связывает внутреннюю сеть API и worker этой серии с нативным PostgreSQL.
Клиенты проверяют сертификат и предъявляют SCRAM-пароль выделенной роли. Сеть API используется также для штатной операторской
сверки. Общий стенд продолжает работу на `https://127.0.0.1:18443`.

Подготовленный [файл оператора](</Volumes/ADATA SE920/OrbStack/facade-ai-test-server/step15/step15.env>) имеет права `0600`.
Оператор шага 15 заполняет ключ и оба JSON-профиля локально. `step15 prepare` проверяет существующую привязку и возвращает
путь до файла. В `step15/database-env-path` указан файл отдельной прикладной БД. Локальную синтетическую учётку можно создать
штатной командой `stand bootstrap`, передав эту БД и согласованный reader-образ.
Для согласованного синтетического опыта оператор явно задаёт `FACADE_HARNESS_LIVE_POLICY=synthetic-research`.
Профиль по умолчанию — `strict-zdr`. Проект, область и SHA-256 синтетических оригиналов проверяет harness.

```bash
# Выполнять из корня репозитория. image — согласованный тэг reader от стенда.
infra/test-stand/step15 offline "$image"
infra/test-stand/step15 balance
# Только оператор шага 15, после заполнения приватного файла и проверки остатка.
infra/test-stand/step15 start "$image"
infra/test-stand/step15 balance
# После завершения работ серии закрыть worker и его прокси.
infra/test-stand/step15 offline-worker
```

API серии доступен по `http://127.0.0.1:18085`. `start` монтирует профиль с ключом только в worker и добавляет к нему
внутреннюю сеть выделенного прокси OpenRouter. Исходящий HTTPS ограничен `openrouter.ai`, `eu.openrouter.ai` и
`us.openrouter.ai` на 443. `verify-egress` проверяет отсутствие прямого маршрута и отклонение адреса вне списка без обращения
к OpenRouter. Включение маршрута импорта выполняется отдельно от серии.
Для просмотра существующих результатов и журнала без исполнения очереди используйте `infra/test-stand/step15 offline-api "$image"`.
Профиль обновляет API на прежней БД и оставляет worker и прокси остановленными.
Для пакета с DOC, XLS или DWG передайте `FACADE_STAND_WITH_BROKER=1` перед этой командой и перед операторским `step15 start`.
API и worker получат существующий Unix-сокет брокера через том с доступом только на чтение. Брокер должен уже работать.

Все пакеты и повторные запуски используют одну прикладную БД серии и один UUID журнала. `balance` читает расход и удержания
непосредственно из журнала. Команда `start` проверяет закреплённую идентичность журнала перед запуском worker.
Смена образа и остановка worker оставляют журнал и его остаток на месте. При утрате PGDATA восстановите исходный журнал перед
продолжением серии. Перед заменой работающего worker дождитесь завершения отправок либо зафиксируйте состояние для сверки.

### Встроенные диагностические профили

`infra/test-stand/stand add-journal "$db_env"` создаёт журнал для одного испытания.
Команда применяет `src/modules/gateway/journal.sql` и закрепляет UUID ledger. Отдельный контейнер PostgreSQL,
роль, база и том журнала используют тот же внешний SSD. Этот профиль позволяет проверить границу подключения и устойчивость
отдельного процесса. Приёмка внешнего журнала требует независимого сервера и носителя.

`stand run` оставляет worker в закрытом режиме. Для отдельно разрешённого модельного прогона предусмотрена команда
`infra/test-stand/stand run-step15 "$image" "$db_env" "$step15_env"`. Она требует reader-сборку, отдельный журнал и файл
`step15.env` с правами `0600` в каталоге прогона на SSD. Для OpenRouter укажите `FACADE_GATEWAY_OPENROUTER_KEY`,
`FACADE_GATEWAY_STEP15_PROFILES` и при необходимости `FACADE_GATEWAY_OPENROUTER_ENDPOINT`. Для CheaperInference
укажите отдельные `FACADE_GATEWAY_CHEAPERINFERENCE_KEY` и `FACADE_GATEWAY_CHEAPERINFERENCE_PROFILES`.
Без `FACADE_HARNESS_PROFILE` используются новые назначения из [профиля worker](../../src/modules/harness/README.md).
Профили маршрутов и лимиты проверяет сам шлюз.

Только worker получает отдельную сеть до модельного прокси. В него попадают адреса явно настроенных транспортов.
Прямой маршрут Featherless использует `FACADE_GATEWAY_FEATHERLESS_KEY` и
`FACADE_GATEWAY_FEATHERLESS_PROFILES`. Для него задайте профиль исходящего proxy
`featherless` или `cheaperinference+featherless` для совместного запуска Terra и Qwen.
Разрешён адрес `api.featherless.ai` на порту 443.

Для OpenRouter разрешены `openrouter.ai`, `eu.openrouter.ai`, `us.openrouter.ai`, для CheaperInference —
`api.cheaperinference.com`. Прокси разрешает HTTPS CONNECT на порт 443. TLS остаётся между worker и провайдером.
У API, PostgreSQL, S3 и worker сохраняются внутренние сети без прямого внешнего маршрута.
Утилиты Poppler и Tesseract запускаются с очищенным окружением, ограничением CPU и запретом сокетов.

Для разрешённого публичного импорта выполните `infra/test-stand/stand run-public-import "$image" "$db_env"`.
Worker получает `FACADE_IMPORT_HTTPS_PROXY` и собственную сеть до этого прокси. Разрешены только `cloud-api.yandex.net`,
`downloader.disk.yandex.ru` и `downloader.disk.yandex.net` на 443. Клиент проверяет URL и редиректы, прокси проверяет
и закрепляет публичный IPv4, TLS остаётся сквозным. В собранном образе присутствует явный CONNECT-транспорт импорта.
Включение импорта оставляет OpenRouter закрытым.

## Брокер конвертеров

Для архива и Office используются установленные Linux ARM64 образы.
Для DWG стандартный `broker-up` выбирает ODA File Converter 27.10 через
обёртку Linux AMD64. На Apple Silicon этот контейнер запускается через эмуляцию.

```bash
docker --context orbstack build --platform linux/amd64 --network=none --pull=false \
  -t facade-dwg-oda:local -f src/modules/formats/oda.Dockerfile src/modules/formats
export FACADE_ODA_ROOT=/absolute/private/ODAFileConverter_27.10.0.0
export FACADE_ODA_RUNTIME=/absolute/private/desktop-runtime/root
export FACADE_ODA_BINARY_SHA256='<закреплённый SHA-256 ODAFileConverter>'
infra/test-stand/stand broker-up "$archive_image" "$office_image" facade-dwg-oda:local
FACADE_STAND_WITH_BROKER=1 infra/test-stand/stand run "$image" "$db_env"
```

Образ обёртки содержит Debian и сценарий запуска. Бинарник, плагины и
среда Xvfb находятся в закрытых неизменяемых каталогах, видимых локальному
демону Docker. Брокер передаёт их только в контейнеры конвертера и только
для чтения. Состояние профиля видно в `/v1/info`. Удержание при
недоступности ODA сохраняет исходник. Локальный запуск использует
поставку, доступную оператору для этого испытания.
[Официальный CLI ODA](https://www.opendesign.com/guestfiles/oda_file_converter)

Явный откат на существующий LibreDWG сохраняет историю карт. После смены
конвертера перезапустите reader и откройте актуальную карту.

```bash
FACADE_DWG_ENGINE=libredwg infra/test-stand/stand broker-up "$archive_image" "$office_image" "$libredwg_image"
FACADE_STAND_WITH_BROKER=1 infra/test-stand/stand run "$image" "$db_env"
```

Пустой аргумент пропускает соответствующее семейство.

Брокер закрепляет установленные ID образов. Его scratch и Unix-сокет живут на томах Linux на внешнем SSD. Worker монтирует том
с Unix-сокетом. Docker-сокет доступен только отдельному брокеру. Брокер и одноразовые конвертеры работают без сети.
Восстановите брокер той же командой `broker-up` перед повторным запуском worker с ним.

## Учётная запись для перехода к UAT

Владелец может подготовить независимое окружение и локальную учётную запись после решения о начале UAT.

```bash
db_env="$(infra/test-stand/stand new-db uat)"
uat_dir="$(dirname "$db_env")"
infra/test-stand/stand migrate "$image" "$db_env"
(umask 077; openssl rand -hex 24 > "$uat_dir/uat-password")
infra/test-stand/stand bootstrap "$image" "$db_env" "Local UAT" uat_admin < "$uat_dir/uat-password"
```

Логин в примере — `uat_admin`, пароль хранится в локальном файле с правами `0600`. В существующем окружении отдельного участника
добавляет владелец через «Администрирование». При переключении общего URL на UAT используйте
`infra/test-stand/stand run "$image" "$db_env"` в согласованное окно. Квалификация внешних моделей включается отдельно.

## Размещение

Данные и образы размещаются на физическом SSD ADATA SE920. Каталоги объектов, секретов, резервных копий и логов используют
`/Volumes/ADATA SE920/OrbStack/facade-ai-test-server`. Корень APFS-тома защищён ACL, доступна запись в существующий каталог OrbStack.
Рабочие тома PostgreSQL и S3 используют файловую систему Linux в `/Volumes/ADATA SE920/OrbStack/data.img.raw`.
Стек имеет собственные Docker-проект, сеть, контейнеры и тома. Общие настройки OrbStack принадлежат хосту.

Четыре логических CPU для процессов стека задаёт `cpuset`. Linux VM OrbStack разделяет с другими проектами 6 ГиБ RAM.
Диск разделяется через APFS с другими проектами и Time Machine. Результаты стенда используются для функциональной проверки и диагностики.
Для приёмки целевого профиля 4 vCPU, 16 ГиБ и 200 ГиБ требуется отдельная среда с этим профилем.

## Диагностика PostgreSQL

```bash
python3 -B infra/test-stand/diagnose-db.py
```

Сценарий выделяет собственные базы, запускает `pgbench` с одной и двумя нагрузками, при двух копирует базу и синтетический файл.
Для восстановления поднимается отдельный одноразовый контейнер без сети. Сценарий проверяет строки, последнюю отметку снимка,
SHA-256 и обнаружение изменения одного байта. Отчёт, архив, объект и первичные логи сохраняются в `backups/diagnostic-*/`.
Копии размещены на том же физическом SSD и имеют общий риск его потери. Замеры описывают только синтетическую нагрузку PostgreSQL.

## Очерёдность тяжёлых испытаний

HTTP-прогон 10 ГиБ, восстановление и установка DWG завершены. На едином адресе доступны проверки шагов 7, 13 и 15.
При 6 ГиБ общей RAM Linux VM последовательно выполняйте одну Docker-сборку, короткую проверку нового образа,
сборку нужных конвертеров, один сценарий приёма 10 ГиБ, затем сценарий двух проектов и восстановление в отдельном контейнере.
Поддерживайте паузу между тяжёлыми фазами при росте macOS swap или таймаутах. Контроль до каждой фазы включает
`df -h . '/Volumes/ADATA SE920'`, готовность API и PostgreSQL, фактические обращения соседних задач и отсутствие второй сборки.
Рестарты PostgreSQL и отключение источника для восстановления выполняйте на копии. На общей БД допускаются тесты в выделенной базе.
