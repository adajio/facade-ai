# Отдельный PostgreSQL журнала · W3.3 / D3

Журнал размещается вне VPS приложения. Кандидат для пилота — назначенный владельцем узел `179.67.199.197` с S3. Для PostgreSQL выделяется собственный смонтированный том с отдельным бюджетом ёмкости и наблюдением за I/O. Для S3, журнала и Arcada сохраняются отдельные каталоги, роли и процессы. Эксплуатационный ответственный за доступность журнала, резервное копирование, восстановление и сверку назначается до допуска пилота.

## Первичная установка

Профиль использует системные `initdb` и `pg_ctl` PostgreSQL 16, Node.js и зависимость `pg` из lockfile кандидата. Локально проверена версия PostgreSQL 16.15. Оператор выбирает точную сборку для Linux, фиксирует её версию и проверяет на ней этот же профиль. Кластер работает от выделенного непривилегированного пользователя ОС. Его роль администратора PostgreSQL доступна через приватный Unix-сокет с peer-аутентификацией. У API и worker отдельная роль `facade_journal_app` с SCRAM, TLS и правами на рабочие операции журнала. Обновление UUID, лимитов проекта и схемы требует административной роли.

1. Подготовьте новый том, например `/srv/facade-journal`, и проверьте его монтирование и принадлежность выделенному пользователю. Сверьте точку монтирования, устройство, свободные байты и файловую систему. Выберите приватный адрес узла и сетевой доступ только с адреса VPS приложения. Закройте порт на внешнем интерфейсе.
2. В отдельном каталоге оператора с правами `0700` подготовьте `server.crt` и `server.key` для приватного имени журнала. Выдайте клиенту удостоверяющий CA. Приватный ключ и `app-password` храните с правами `0600`. Пароль — 32 случайных байта в hex (`openssl rand -hex 32`). В `ledger-id` запишите назначенный UUID установки и сохраните его на независимой площадке вместе с эксплуатационными метаданными.
3. От имени пользователя журнала выполните из корня кандидата, где установлены зависимости. Значения адресов ниже иллюстрируют формат частной сети.

```bash
export JOURNAL_PG_BIN=/usr/lib/postgresql/16/bin
export JOURNAL_PGDATA=/srv/facade-journal/pgdata
export JOURNAL_STATE=/var/lib/facade-journal
export JOURNAL_SOCKET=/var/lib/facade-journal/socket
export JOURNAL_LISTEN=10.24.1.20
export JOURNAL_CLIENT_CIDR=10.24.1.10/32
export JOURNAL_PORT=5432

mountpoint -q /srv/facade-journal &&
  infra/journal/init
```

Скрипт применяет [DDL выбранного кандидата](../../src/modules/gateway/journal.sql), привязывает UUID и останавливает кластер после настройки. Для уже существующего журнала применяется миграция из [инструкций шлюза](../../src/modules/gateway/README.md), с прежним UUID и сохранением попыток. После миграции отдельно проверьте grants на новых таблицах. При частичном отказе установки проверьте журнал PostgreSQL и состояние тома до любого повторного запуска.

Для запуска на Linux проверьте mount и маркер `initialized`, затем используйте штатный супервизор с зависимостью от точки монтирования или следующий операторский вызов. Зафиксируйте удалённую проверку по TLS под прикладной ролью на этом же UUID до допуска worker.

```bash
mountpoint -q /srv/facade-journal &&
  cmp -s "$JOURNAL_STATE/ledger-id" "$JOURNAL_STATE/initialized" &&
  "$JOURNAL_PG_BIN/pg_ctl" -D "$JOURNAL_PGDATA" -w -t 30 -l "$JOURNAL_STATE/postgres.log" start
```

В приватной конфигурации API и worker задайте `FACADE_GATEWAY_LEDGER_ID` и `FACADE_GATEWAY_JOURNAL_URL`. URL формируйте как `postgresql://facade_journal_app:<secret>@<private-dns>:5432/facade_journal?sslmode=verify-full&sslrootcert=<ca-path>`, кодируя параметры URL. Если установлен отдельный потолок журнала, закрепите его согласно контракту шлюза. Проверьте отказ при блокировке TCP и несовпадении UUID до включения маршрутов. Проверка доступности должна выполнять запрос к журналу с ожидаемым UUID через клиентский TLS. Одного открытого порта недостаточно.

## Восстановление оператором

1. При недоступности журнала удерживайте новые модельные отправки. Определите исход последней попытки по исходному UUID и независимо сохранённой квитанции. Запишите время отказа, обнаружения и фактическую точку восстановления. Сохраните прежний PGDATA и его логи.
2. При сохранном томе поднимите PostgreSQL из прежнего PGDATA. При потере тома восстанавливайте согласованную копию в выделенной среде с прежним UUID, ролями и проверенной точкой WAL. Для PITR проверьте полноту WAL до требуемой точки и архив вне узла приложения и узла S3/журнала. Учитывайте конфигурацию доступа и ключи отдельно от данных PostgreSQL. [PostgreSQL 16 · восстановление на момент времени](https://www.postgresql.org/docs/16/continuous-archiving.html)
3. Проверьте закреплённый UUID, доступ из приложения, попытки после восстановленной точки, открытые резервы и актуальный допуск маршрутов. Примените штатную сверку шлюза с прежним ключом эффекта. Отсутствие доказательства оплаты оставляет попытку и резерв в удержании. При подтверждённом списании восстанавливайте исходный результат по квитанции. Если внешний журнал отстал и полнота попыток за этот интервал неизвестна, оставьте выход затронутого проекта или маршрута закрытым до независимой сверки.
4. Перед допуском сверяйте прикладную БД и объекты с внешним журналом. Проверьте старое письмо и исходную опору, потерянные части загрузки и ранее исполненные удаления по сквозному D1/D3/D12. Копия на том же хосте оставляет общий отказ хоста. RPO и RTO для узла приложения, тома журнала и общего отказа S3/журнала остаются открытыми до назначения целевых значений и отдельного зачётного восстановления.

## Условия совместного размещения на VPS

**42,9 ГиБ** — остаток после согласованной очистки по переданному замеру. Перед зачётом снимите остаток по каждой файловой системе и проверьте, как выделенный том влияет на доступное место. Отдельный Docker-том на том же заполненном разделе не даёт отдельной ёмкости. Для общей физической среды сохраните раздельные бюджеты, учитывая существующие нагрузки Arcada и все 69 сохранённых Docker-томов.

Считать по состояниям загрузки и восстановления:

```text
потребность в свободном месте =
  пик новых S3-байтов (живые объекты + части + фактическое дублирование)
  + рост данных Arcada и прочих процессов за окно пилота
  + прирост журнала, пик WAL и служебных логов
  + пик резервных копий и временных файлов на том же носителе
  + согласованный оперативный запас
```

Для одного полностью размещённого объекта 10 ГиБ из исходных 42,9 ГиБ останется 32,9 ГиБ до остальных расходов. Если замер покажет, что при финализации дополнительно удерживается полная копия частей 10 ГиБ на том же носителе, в этот момент останется 22,9 ГиБ. Повторите расчёт для двух прерванных поступлений, базы объектов и горизонта хранения. Локальный scratch приложения учитывайте отдельно на его VPS. Для журнала измеряйте пиковый размер `pg_wal` при нагрузке и отставании архива. `max_wal_size` — мягкий ориентир PostgreSQL. [PostgreSQL 16 · WAL](https://www.postgresql.org/docs/16/wal-configuration.html)

На фактической сети снимите базовые показатели с работающим Arcada, затем повторите замеры во время приёма 10 ГиБ, докачки, финализации и резервного копирования. На том же интервале выполняйте через штатный API/worker управляемые операции резерва, подтверждения и сверки. Запишите:

- По PostgreSQL — частоту успешных запросов, p50/p95/max и таймауты соединений и подтверждений, число соединений и ожидания Pg/пула, длину и ожидание очереди шлюза, объём и скорость WAL, возраст последнего архива и минимальный свободный остаток. Источники — `pg_stat_activity`, `pg_stat_wal`, `pg_stat_archiver`, трасса шлюза и метрики файловой системы.
- По хосту — CPU/steal, доступную память, swap, I/O-задержки и очередь диска по устройствам. По S3 — одновременно занимаемые байты и время каждой фазы. По Arcada — доступность и задержку согласованной штатной операции до, во время и после нагрузки.
- По инвариантам — подтверждённые отправки только после durable-резерва, ноль отправок при недоступности журнала, один учтённый эффект при потере ответа и восстановлении. Пороги доступности, задержек, остатка и RPO/RTO утвердите до зачётного прогона. Изменения настроек PostgreSQL обоснуйте наблюдаемой причиной в соединениях, очереди или WAL.

Если бюджет места или доступности не сходится, вынесите журнал на отдельный узел либо перенесите S3 на внешнее хранилище, сохранив журнал вне VPS приложения и независимые резервные копии. До квалификации новой топологии сохраняйте управляемые локальные проверки и удержание живых модельных отправок.

## Локальное повторение

Из корня проверяемого кандидата с установленными зависимостями укажите каталог бинарников PostgreSQL 16. Сценарий выделяет каталоги под `.local`, свободный TCP-порт loopback и закрытые временные Unix-сокеты. После завершения останавливает только свои экземпляры, удаляет свои PGDATA и секреты, оставляет журналы работы.

```bash
export JOURNAL_PG_BIN=/path/to/postgresql/bin
node infra/journal/verify-local.mjs --profile-only
npm run build:server
node infra/journal/verify-local.mjs
```

Первый вызов проверяет установку, права, обязательный TLS, повторную инициализацию и аварийный перезапуск. Второй запуск использует опубликованный W1.4, штатный шлюз и управляемый транспорт. Он проверяет недоступность журнала до отправки. Затем завершает процесс исполнителя после приёма эффекта имитатором, аварийно останавливает PostgreSQL журнала, восстанавливает прикладную БД из шаблона до отправки и сверяет исходный эффект. Промежуточные результаты, счётчики отправок, баланс и длительности выводятся в stdout. Локальный снимок и оба экземпляра используют один физический SSD. Проверка охватывает резерв и контрольную точку чтения шлюза. Прежнее письмо, исторический оригинал, совместная нагрузка на целевом узле и фактический RPO/RTO проверяются в D1/D3/D12.
